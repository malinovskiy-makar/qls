## Разведка Фазы 0.1 — НАСТОЯЩАЯ ПРИЧИНА (гипотеза промпта не подтвердилась)

**Гипотеза промпта:** «механика подпунктов наложилась на тесты, каждый
вариант стал пунктом со своим баллом». **Проверена и ОТВЕРГНУТА.**
`part_grading.applies(item)` возвращает `False` для любого теста (признак —
`item.is_test`), а `assignment_rows.answer_parts()` для теста отдаёт `[None]`
(вид ввода не `ANSWER_TEXT`). То есть тест в механику пунктов не заходит
вообще; `row['answer_parts']` у него пустой список.

**Настоящая причина — в другом месте и старше на две сессии.**
`student/views.py::auto_check_submission` (автопроверка КАТАЛОЖНОГО теста,
написана в эпоху «В2», до появления `AssignmentItem`) ставит балл
**жёстко зашитой единицей**:

```python
score = 1.0 if is_correct else 0.0     # ← максимум задачи не спрашивается
```

Максимум при этом везде читается из `AssignmentItem.points`
(`work_review._item_max`). В демо-данных у «все верные» `points=3`, у
«верно/неверно» `points=2` — отсюда «1 / 3 б.» и «1 / 2 б.» при полностью
верном ответе, а `work_summary` по правилу `score >= points → correct,
score > 0 → partial` честно печатает «ЧАСТИЧНО».

Комментарий «Верно ✓» пишет ТА ЖЕ функция — поэтому карточка и
противоречила сама себе: вердикт брался из проверки ответа, а состояние —
из сравнения балла с максимумом.

**Почему свои задачи репетитора не сломались:** соседняя
`auto_check_custom` написана уже в платформенной сессии и балл берёт
правильно — `max_points = float(item.points) if item.points is not None
else 1.0`. Один и тот же вопрос был решён в двух местах по-разному, и
устарело то, которое никто не трогал.

## Разведка поиска (Фаза B.1) — семь ответов

**1. Что индексировано.** `problem_to_text` (`build_embeddings.py`), 7 блоков:
`title` + `statement[:500]` + подпункты (≤500 суммарно) + «Темы: …» +
«Навыки: …» + `ai_blurb[:400]` + «Теги: …». **Решение и ответ в отпечаток НЕ
входят.** Отсюда и слепота на терминах, которые живут в решении («по лемме
Хотеллинга…») — их закрывает новый словарный поиск.

**2. Режим BGE-M3 — только ПЛОТНЫЙ.** `catalog/semantic.py` использует
`SentenceTransformer(...).encode()`, а это один плотный вектор. Разреженный и
многовекторный режимы требуют `FlagEmbedding`/`BGEM3FlagModel`, своего формата
хранения и полного пересчёта 31 472 задач. То есть «включить второй режим» —
не настройка, а новый индекс.

**3. Обычный поиск по словам.** До сессии — только `icontains` по
`statement`/`title` в каталоге (`catalog/views.py:104,323`) и грубый фолбэк в
`hw_generator._search_row` (до 2 слов длиннее 4 символов). В подборе домашки
словарного поиска не было. Теперь есть `catalog/hybrid.lexical_search`.

**4. Порога отсечки НЕТ и не было.** В `semantic.search` есть только `top_k =
limit × 10` — это потолок кандидатов, а не порог похожести. Пороги 70%/50% в
шаблоне `smart_search.html` красят бейдж, ничего не отсекая.

**5. Тема применялась ЖЁСТКИМ ФИЛЬТРОМ**, причём ПОСЛЕ отбора топ-K:
`qs.filter(topics__id=topic_id)` внутри `semantic.search`. Худший из вариантов
— фильтр режет уже сокращённый список, поэтому неверная тема схлопывает
выдачу почти в ноль. Это и был механизм провала на КПВ/КТВ.

**6. Дедупликация по источнику** — в `find_problems`: не больше 3 задач на
источник (`_source_of` берёт ПЕРВУЮ ссылку `source_references`). Раньше это
был запрет: при 8 запрошенных задачах из одного сборника возвращалось 3.
Теперь потолок отступает, когда иначе не набирается квота.

**7. ЗАПАСНОЙ ПУТЬ НА ПРОДЕ — И ЭТО ГЛАВНОЕ.** `sentence-transformers` в
`requirements.txt` НЕТ (только в `requirements-local.txt`). На проде
`catalog.semantic` падает на импорте, `hybrid.dense_search` ловит исключение и
возвращает пусто. Значит **смыслового поиска на проде нет вовсе**: до этой
сессии подбор домашки деградировал до `icontains` по двум словам плюс
`order_by('?')` — то есть выдавал почти случайные задачи по теме. После сессии
на проде работает полноценный словарный поиск с ранжированием по числу
совпавших слов; это хуже гибрида, но честно и предсказуемо. Полное решение —
карточка «Деплой поиска на прод» (упирается в память free-tier).
