## 5. Идемпотентность по `ref_key`

- Комплект: `update_or_create(olympiad, kit_key)`. Задание: `update_or_create(ref_key)`.
- Повторный прогон того же пакета: 0 создано, 0 изменено (сравнение по хешу содержимого записи, хеш хранить в `content_hash`).
- Новый пакет с теми же ключами: текст обновляется, **но не затирает ручную правку** — если у задания
  `manually_edited=True` или `human_review` не пусто, обновление пропускается и попадает в отчёт «расхождения».
- Задание, которого нет в новом пакете, **не удаляется**, а получает `absent_in_last_import=True`.
- `ref_key` не пересчитывать и не нормализовать (правило README). Кириллица, двоеточия — допустимы, длина ≤ 50 → CharField(100) с запасом.
- Файл: ключ `(variant, sha256)`; тот же sha256 — файл не перекладывается.
- Каждый запуск пишет отчёт `reports/olympiads_import_<время>.json` (создано/обновлено/пропущено/ошибки) и работает в одной транзакции на комплект.
- Команда: `import_olympiads_pkg <папка> [--dry-run] [--only SLUG] [--no-files]`; по умолчанию — сухой прогон, запись только с `--apply`.

## 8. Где лежат файлы и как отдаются

- Объём к хранению: оригиналы **0,64 ГБ** (1 413 pdf, 21 docx, 3 html) + рисунки заданий **0,49 ГБ** (из них 0,40 ГБ — `mosh-fingram`,
  стоит пережать) = ~1,1 ГБ. Картинки банка (0,44 ГБ) — отдельная задача банка, не раздела.
- Место: том `media` на сервере (`MEDIA_ROOT`), путь `olympiads/<слаг>/<event_id>/<sha8>_<имя>`; в git и в образ — не класть.
  Том `media` бэкапится с 24.09.2026 (tar.gz ежедневно), надо следить за его размером: сейчас в нём почти нет данных.
- Заливка на сервер — `docker compose cp` внутрь тома (как описано в `docs/SERVER.md`, раздел о заливке в media), по 1 слагу за раз, затем `import … --files-only` проверяет sha256.
- Отдача: **не** прямой `/media/`, а вьюха с проверкой «комплект опубликован» (чтобы скрытые комплекты не утекали), `Content-Disposition: inline` для PDF, `X-Accel-Redirect` из nginx для скорости. Правило границ доступа — через `weco-security-boundary-review`.
