# Безопасность

Что здесь: границы доверия, чем что защищено, известные дыры и как сообщить о новой.
Эксплуатационные процедуры — в [RUNBOOK.md](RUNBOOK.md).

---

## Границы доверия

| Кто | Что видит | Чем ограничен |
|---|---|---|
| Аноним | Главная, каталог, задача, подборки по токену, `/game/` | Шлюз качества прячет зафлагованные задачи; черновики недоступны |
| Ученик | Свои домашки, свой прогресс | Не видит чужие работы и чужой прогресс |
| Репетитор | Свои группы, свои ученики, свои работы | На чужого ученика — 403, проверяется в view, а не в шаблоне |
| Родитель | Прогресс **своего** ребёнка, только чтение | Ни одного показателя работы репетитора (осознанное решение) |
| Админ | Всё через `/admin/` | — |

**Правило:** владелец объекта берётся из `request.user`, а не из данных запроса.
Если во view есть `owner_id` из POST/GET — это дыра, пока не доказано обратное.

**Токен подборки — не защита.** `Collection.token` даёт доступ по ссылке кому
угодно. Подборки не содержат персональных данных, поэтому это приемлемо; класть
туда что-то чувствительное нельзя.

## Как проверяется доступ: сначала сузить, потом взять

Принят один образец на весь проект (сессия 3А, 2026-08-19). Разница между
двумя способами не стилистическая, а в том, чем оборачивается ошибка.

**Плохо — взять объект, потом проверить:**

```python
submission = get_object_or_404(Submission, pk=pk)
if submission.student_id != request.user.pk:      # забыли — дыра
    raise PermissionDenied
```

**Хорошо — сузить выборку до доступного, потом взять из неё:**

```python
submission = get_object_or_404(visible_submissions(request.user), pk=pk)
```

> **Забытая проверка — это дыра. Забытое сужение — пустая выдача.**
> Первый способ по умолчанию открыт, второй по умолчанию закрыт.

Готовые сужения живут в [`teacher/access.py`](../teacher/access.py):
`own_group_or_404`, `group_assignment_or_404`, `_own_assignment`
(в `calendar_stub`). Новое право заводится там же, а не отдельной проверкой
внутри view.

⚠️ **404, а не 403, когда объект чужой.** Для репетитора чужая группа не
«запрещена» — её для него не существует, и номер чужой группы не должен
подтверждаться сообщением об ошибке. 403 уместен там, где отказ идёт по РОЛИ
(ученик в кабинете репетитора), а не по владению.

### Проверка роли — одна на проект

Систем ролей две: старая `User.role` и новая `UserProfile.role`. Обе живы
намеренно и ни одна не покрывает всех: у пользователей, заведённых до
профилей, профиля нет, а на `User.role` висит `limit_choices_to` у
`StudentGroup`. Синхронизация **односторонняя** (профиль → юзер), поэтому
правка `User.role` через админку профиль не подтянет.

Единственно верный ответ — «репетитор хоть по одной системе», и он записан
**один раз** в `teacher/access.is_tutor` / `is_student`. Своих копий не
заводить: до сессии 3А их было три (`teacher_required`, `calendar_stub`
дважды), и репетитор из профиля получал 403 на шести маршрутах.

### Кто какие объекты видит

| Объект | Кто | Чем сужено |
|---|---|---|
| `Assignment` / `AssignmentItem` | автор работы, преподаватель её группы, назначенные ученики | `students=user`, `group__teacher=user`, `author=user` |
| `Submission` / `AnswerDraft` | сам ученик и репетитор его работы | `student=user`, `AssignmentItem.is_tutor_for` |
| `ExamAttempt` | сам ученик, в своё окно времени | `students=user` + `exam_engine.can_accept` |
| `StudentGroup` / `Lesson` | только её преподаватель | `own_group_or_404` |
| `CustomProblem` | только автор | `owner=request.user` |
| `SavedFolder` / `SavedProblem` / `SavedGraph` | только владелец | `owner=request.user` |
| `ProblemComment` | пара «ученик ↔ его репетитор» | `ProblemCommentQuerySet.visible_for` |
| `TutorNote` | **только автор-репетитор** | `tutor=request.user`; до ученика не доходит нигде |
| `CalendarEvent` | автор, его группы, глобальные | `_visible_qs`; правка и удаление — только автор |
| `Problem` | опубликованные и не забракованные | `status=PUBLISHED, needs_quality_review=False` |
| `AiUsageLog` | только `is_staff` | видна лишь через `/admin/` |

### Граница «ученик ↔ репетитор»: ответы и решения

Отдельное правило, потому что здесь мало 403 — данные не должны попадать в
браузер вовсе.

**Контекст страницы собирается по состоянию попытки, а не «взяли объект и
отдали в шаблон».** В `assignment_rows.build_rows`:

- `show_correct` и `option_review` собираются **только после сдачи**;
- `solution_text` кладётся, **только если** `is_solution_visible_for` дал
  добро; рядом остаются `has_solution` и `solution_hint` — ученику надо
  сказать, что решение есть и когда откроется, не показывая его.

⚠️ **Прятать шаблоном — не защита.** Проверено опытом: до сессии 3А
`solution_text` уезжал в контекст безусловно, и достаточно было убрать один
`{% if %}` в `student/_problem_card.html`, чтобы эталонное решение оказалось
в браузере посреди контрольной. Шаблонов, рисующих эту строку, четыре.

Держится тестом `problems/tests/test_answer_leakage.py` — он смотрит **сырое
тело ответа**, а не экран.

## Активный контент: почему корпус задач — это исполняемый код

31 690 задач приехали из внешних источников, свои задачи пишут репетиторы,
комментарии — ученики, часть текста дописывает модель. Всё это попадает на
экран ученика, репетитора и **в админку — под учётную запись с полными
правами**. Строка в условии задачи это не текст, а потенциальный скрипт.

### Правило одно: экранируем всегда

Сырой HTML корпусу **не нужен** — и это не мнение, а факт, проверяемый
кодом: публичная страница задачи всегда выводила `{{ problem.statement }}`
экранированным, и каталог этим живёт. Значит, `|safe` у того же поля в
кабинете ученика ничего не добавлял, кроме дыры.

Поэтому в проекте **нет** библиотеки очистки HTML (`nh3`, `bleach`) и она
не нужна: очищать нечего, если ничего не разрешено. Заводить зависимость
ради белого списка тегов, которыми никто не пользуется, — это лишний
пакет в боевом локе и лишний слой, в котором можно ошибиться.

⚠️ Если однажды HTML в условии действительно понадобится (например,
таблицы из импорта), правило меняется так: хранить исходник, а очищенное
представление получать **при показе**, не при сохранении, — то же правило,
что у `problems/text_clean.py`. Тогда и появится `nh3` с верхней границей
версии в `requirements/base.in`.

### Что было найдено и закрыто (сессия 3Б, 2026-08-19)

| Место | Что было | Серьёзность |
|---|---|---|
| [catalog/templates/catalog/problem_list.html](../catalog/templates/catalog/problem_list.html) — окно предпросмотра | Условие задачи из JSON склеивалось в строку разметки и уезжало в `innerHTML`. Задача с обработчиком события в тексте выполняла бы чужой код в браузере **любого посетителя каталога — вход не нужен** | **высокая** |

### Где `|safe` остался — и почему это законно

| Место | Что там | Почему допустимо |
|---|---|---|
| `platform/stats.html`, `catalog/problem_list.html`, `game/game.html`, `calendar_stub/calendar.html` | JSON внутри `<script>` | значение готовит `dumps_for_script`: выйти из тега им нельзя |
| `registration/password_change_form.html` | `{{ field.help_text\|safe }}` | текст пишет сам Django, не пользователь |

Других `|safe`, `{% autoescape off %}` и `mark_safe` в проекте нет.
`format_html` в `problems/admin.py` (9 мест) безопасен по устройству: он
экранирует каждый подставляемый аргумент.

### KaTeX

`trust: false` проставлен **явно** во всех 14 вызовах `renderMathInElement`
(9 шаблонов, включая печатную версию `teacher/assignment_print.html`).
По умолчанию KaTeX 0.16 и так идёт с `trust: false`, но «по умолчанию» —
не то же самое, что «решено»: один `trust: true`, вписанный ради картинок,
открыл бы `\href{javascript:…}` сразу везде.

⚠️ **`strict: true` НЕ включён, и это осознанно.** Строгий режим ругается
на кириллицу в математике (`$Q_д$`), а ею набрана заметная часть банка:
формулы стали бы красными по всему каталогу. К защите от выполнения кода
`strict` отношения не имеет — за неё отвечает ровно `trust`. Включать
строгий режим имеет смысл как проверку качества набора, отдельной работой
и с замером, сколько задач он подсветит.

### Единственный путь ввода клиента во внешний процесс

`calc2:export_pdf` принимает `.tex` от браузера и запускает `pdflatex`
([calc2/views.py](../calc2/views.py)). На проде компилятора нет и маршрут
отвечает 503, но код живой.

Было: список запрещённых команд (`\write18`, `\input`, `\include`…).
Список перечисляет команды поимённо, а в TeX их сотни: `\usepackage{verbatim}`
плюс `\verbatiminput{…}` читает чужой файл, не встретив ни одного
запрещённого слова.

Стало: список остался как первый рубеж, а настоящая защита — **ограничение
самого TeX**. Компилятор запускается с `openin_any=p`, `openout_any=p`,
`shell_escape=f` и флагом `-no-shell-escape`. Это ограничивает чтение и
запись рабочей папкой независимо от того, какой командой файл открыли.

## Заголовки ответа и политика безопасности

Что ставит Django своими настройками (`config/settings_production.py`):
`X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`,
`X-Frame-Options: DENY`, `Secure`/`HttpOnly`/`SameSite=Lax` у кук,
`SECURE_SSL_REDIRECT`.

Что добавлено сессией 3Б ([config/security_headers.py](../config/security_headers.py)):

* **`Permissions-Policy`** — строгая: ни камеры, ни микрофона, ни
  геолокации, ни оплаты, ни USB. Разрешён только `fullscreen=(self)` —
  им пользуются печать работы и разворот графика.
* **`Content-Security-Policy-Report-Only`** — политика в **режиме отчёта**.

⚠️ **Почему отчёт, а не бой.** KaTeX сегодня грузится с `cdn.jsdelivr.net`,
а встроенных `<style>` и `<script>` в разметке сотни. Боевая политика
отрезала бы часть из этого в первый же день, и «безопасность» выглядела бы
как сломанный сайт. Режим отчёта ничего не блокирует, но браузер сообщает
о каждом нарушении на `/csp-report/`, и в журнале копится настоящий список
того, что придётся починить.

**Перевод в боевой режим — отдельная работа ПОСЛЕ самостоятельного
размещения статики.** Списка источников «пошире, чтобы не шумело», в
политике нет намеренно: тихая политика в отчёте не расскажет ничего, а в
бою не защитит.

Приёмник отчётов ([config/csp_report.py](../config/csp_report.py)) —
публичный адрес, который пишет в журнал, поэтому: тело обрезано 8 КБ, в
запись уходят четыре поля по 300 символов, ответ всегда пустой 204, а
отчёт без названия правила не логируется вовсе (иначе `{}` в цикле забьёт
журнал).

### Страницы ошибок

`templates/400.html`, `403.html`, `404.html`, `500.html` — все четыре в
общем стиле сайта и **без единого технического слова**: ни трассировки, ни
`DJANGO_SETTINGS_MODULE`, ни SQL, ни имён внутренних объектов.

⚠️ Основа `templates/_error_base.html` **самостоятельная** и не наследует
ни один `base.html`. Причина в странице 500: Django рисует её с пустым
контекстом, а общая шапка `_nav.html` спрашивает `user.profile.is_parent`,
то есть ходит в базу. Если упала база, шапка упадёт следом — и вместо
страницы «что-то сломалось» человек получит вторую ошибку внутри первой.

Найдено собственным тестом и починено заодно: прежняя `404.html`
наследовала `teacher/base.html` и звала «К ученикам» — то есть в панель
репетитора, которую три из четырёх посетителей не увидят. На наборе
адресов без пространства `catalog` она падала с `NoReverseMatch`, то есть
**404 превращалась в 500**.

Держится тестом `problems/tests/test_security_headers.py`.

## Вход в аккаунт

⚠️ **В проекте есть только вход, выход и смена пароля.** Регистрации,
восстановления пароля, подтверждения почты и приглашений **нет** —
проверено обходом `config/urls.py`. Поэтому ограничений частоты для них
тоже нет: ограничивать нечего. Когда поток появится, он берёт своё имя
счётчика (`SCOPE`) в [`problems/ratelimit.py`](../problems/ratelimit.py) и
получает ступени запрета бесплатно.

**Иностранных провайдеров входа в проекте нет.** Проверено поиском по
`allauth`, `social_auth`, `oauth`, `google`, `apple`, `facebook`,
`github`: ни пакета, ни настройки, ни кнопки, ни маршрута. Единственные
совпадения — два комментария про вид теплокарты «как на GitHub».
Закреплено тестом `NoForeignAuthProvidersTests`.

### Ограничение частоты

Django из коробки принимает попытки входа бесконечно. Счётчики — в кэше
Django, ступени нарастающие:

| Промахов | Запрет |
|---|---|
| 5 | 30 секунд |
| 8 | 2 минуты |
| 12 | 10 минут |
| 20 | 30 минут |

**Ключ комбинированный — имя И адрес в сети.** Только по имени обходится
перебором имён и, хуже, позволяет запереть чужой аккаунт десятком попыток.
Только по адресу — наказывает школу за общий выход в интернет. У адреса
лимит в 6 раз мягче: за ним может сидеть класс.

⚠️ **Пока запрет действует, пароль не проверяется вовсе** — форма даже не
собирается связанной. Иначе ограничение считало бы попытки, но не мешало
бы их делать.

⚠️ **Счётчик адреса не гасится удачным входом**, а счётчик имени — гасится.
Иначе перебор снимал бы запрет входом в собственный аккаунт нападающего.

⚠️ **Счётчики живут в памяти процесса** (`LocMemCache`): не переживают
перезапуск, при нескольких воркерах у каждого свои. На бесплатном хостинге
процесс один. Переезд на Redis — смена словаря `CACHES`, ни строки кода.

### Что не разглашается

* **Существование аккаунта.** Ответ на неверный вход одинаков по тексту,
  по коду и по содержимому для существующего и несуществующего имени —
  проверяется побайтовым сравнением двух ответов.
* **Время ответа.** Обеспечивает Django: `ModelBackend` при отсутствии
  пользователя всё равно считает хэш вхолостую. Тест проверяет **механизм**,
  а не секунды: замер времени краснел бы на любой занятой машине.
* Сообщение о запрете говорит только «слишком много попыток» — это про
  частоту, а не про учётную запись.

### Сессии и пароли

* Ключ сессии меняется при входе (`login()` зовёт `cycle_key()`) — значит,
  идентификатор, подсунутый до входа, после него не работает.
* Смена пароля обрывает **все остальные** сессии этого человека: Django
  сверяет хэш пароля с сессией на каждом запросе.
* Минимальная длина пароля — **10 символов** (было 8 по умолчанию), плюс
  штатные валидаторы Django: похожесть на имя, словарь частых, только цифры.

Держится тестом `problems/tests/test_auth_hardening.py`.

## Что попадает в журналы

**Запрещено писать:** пароли, куки, CSRF-токены, токены приглашений и
публичные токены подборок, коды ссылок на результат игры, полные запросы к
модели и решения учеников, адрес почты в составе URL, содержимое
загруженных файлов.

**И обратное правило.** Если наружу отдаётся человеческий текст вместо
ошибки — в журнал обязана уйти НАСТОЯЩАЯ причина. `providers.log_cause`
появился ровно после случая, когда подбор падал из-за несовместимости
`urllib3` с LibreSSL, а в журнале стояло «Сервис разбора запроса
недоступен» — то есть та же фраза, что на экране.

`AiUsageLog` хранит только метрики: модель, токены, стоимость, токены
кэша, задержку, статус. Полей с запросом и ответом в ней нет и не должно
появиться.

⚠️ **Своей настройки `LOGGING` в проекте не было**, и работала настройка
Django по умолчанию — а в ней у консольного обработчика стоит фильтр

## Разбор находок bandit

18 находок средней важности, доставшихся по наследству, разобраны в
сессии 3Б. **Базовая линия `.bandit-baseline.json` удалена**: она
собиралась на Windows, а CI идёт на Linux, и bandit сравнивает находки в
том числе по имени файла — `problems\management\…` и `problems/management/…`
для него разные файлы. Ни одна из 18 записей не сопоставлялась, и джоб
падал. Правкой линии это не чинится: любой JSON с путями внутри верен
ровно на одной из двух систем.

Каждая находка закрыта точечным `# nosec BXXX` с объяснением по-русски
прямо у строки. Такой маркер работает одинаково на Windows, Linux и macOS
и ничего не выключает глобально.

| Корзина | Сколько | Что это |
|---|---|---|
| **Настоящая** | 1 (2 находки) | Раскрытие сущностей при разборе XML из `.docx`. Внешние сущности стандартный `ElementTree` не тянет (XXE нет), но внутренние раскрывает — «бомба» из девяти объявлений раздувается без ограничений. Закрыто `_xml_from_docx`: в OOXML `DOCTYPE` не бывает, файл с ним не разбирается. Без новой зависимости — `defusedxml` нет в боевом локе |
| **Ложная** | 15 | 10× B608: в строку запроса подставляются только знаки `?` либо имя таблицы из метаданных Django, значения уходят отдельным аргументом. 4× B108: предсказуемый путь распаковки в разовых импортёрах, которые идут только на машине владельца. 1× B310: адрес собирается из константы, схема проверяется явно |
| **Отложенная** | 2 находки, 1 строка | Ассеты KaTeX тянутся с внешнего CDN — зависимость от чужой инфраструктуры и обращение на зарубежный домен. Самостоятельное размещение статики идёт следующей сессией; карточка в Notion |

Проверено в контейнере `python:3.13-slim` на Linux командой из CI: находок
средней и высокой важности ноль, код возврата 0. То же на Windows — обе
системы теперь дают один результат, потому что артефакта с путями больше
нет.

## Секреты

- **Единственный источник — переменные окружения.** В коде секретов нет.
  Ключ модели читается только из `ANTHROPIC_API_KEY`; нет ключа — функция
  деградирует с внятным сообщением.
- `config/settings_production.py`:
  - `SECRET_KEY = os.environ['SECRET_KEY']` — именно `[ ]`, а не `.get()`:
    без ключа сервис обязан упасть при старте, а не подняться с тихим дефолтом;
  - переменная `DJANGO_DEBUG` роняет старт — отладочный режим на проде запрещён;
  - `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SECURE_PROXY_SSL_HEADER` —
    выставлены; HTTPS-редирект и HSTS делает сам Render (`security.W004/W008`
    заглушены осознанно).
- `config/settings.py` (локальная разработка) содержит `django-insecure-…` ключ.
  Это **не** секрет прода: боевые настройки его перекрывают. Но и коммитить туда
  что-то настоящее нельзя.
- `.gitignore` закрывает `.env`, `*.sqlite3`, `deploy_fixtures/`, дампы базы,
  `load_to_render.sh`, `anthropic_key.txt`.

## Известные дыры

### 1. Дамп боевой базы в истории git — ОТКРЫТА

`prod_backup_20260622_0210.dump` (15 МБ, PostgreSQL custom format) и каталог
`deploy_fixtures_backup_20260622_012745/` (16 МБ) попали в репозиторий коммитом
`f46fdf9` («WIP: municipal import», классический `git add -A`). Дамп — полная
копия боевой базы, включая таблицу пользователей с хэшами паролей.

Репозиторий приватный, поэтому это не публичная утечка. Но:
- удаление файлов из HEAD **не** убирает их из истории;
- любой, кто получит доступ к репозиторию, получит и снимок базы.

**Что делать:** решение за владельцем. Варианты — оставить как есть (приватный
репозиторий), либо переписать историю (`git filter-repo`), что требует
принудительного пуша и согласования со всеми, у кого есть копии. `.gitignore`
уже закрыт от появления новых таких файлов.

### 2. Публично известные дев-пароли — ЗАКРЫВАЕТСЯ КОМАНДОЙ

`admin12345`, `teacher12345`, `student12345`, `demo12345` лежат в открытом коде
(`seed_demo`, `seed_platform_demo`) и в документации. На проде эти учётные записи
приехали из дампа вместе с паролями.

```bash
python manage.py lockdown_dev_accounts            # показать найденное
python manage.py lockdown_dev_accounts --apply    # погасить
```

Команда ставит случайный пароль на 32 символа, отключает неслужебные аккаунты,
завершает их сессии. Пароли печатаются только в stdout. **Прод она сама не трогает** —
запустить против прод-базы должен владелец руками (см. RUNBOOK).

Страховка: тест `problems/tests/test_no_default_passwords.py` краснеет, если
активный аккаунт с известным дев-паролем появится снова.

⚠️ У Django нет встроенного флага «требовать смену пароля при первом входе».
Служебным аккаунтам пароль меняется вручную через `/admin/password_change/`.
