# Чек-лист переезда с Render

Что раньше обеспечивал Render (отключён 2026-08, истёк пробный период) и что
нужно настроить и проверить на новом хостинге. Это чек-лист для сессии
переезда, а не сама сессия — решений здесь нет, только вопросы и ссылки на
код. Устройство деплоя вообще — [ARCHITECTURE.md](ARCHITECTURE.md) и
[RUNBOOK.md](RUNBOOK.md).

---

## 1. HTTPS-редирект и HSTS

**Было.** Редирект HTTP → HTTPS делает сам Django (`SECURE_SSL_REDIRECT = True`),
опираясь на заголовок `X-Forwarded-Proto`, который проставлял прокси Render.
Render проверял живость сервиса сканом TCP-порта, а не HTTP-запросом — поэтому
301 на health-check не мешал. HSTS выключен намеренно
(`SECURE_HSTS_SECONDS = 0`) — не был включён и на Render, ждал покупки домена.

**Сейчас** (Render отключён) — ни редирект, ни HSTS не обеспечивает никто.

**Проверить/настроить:**
- Прокси/nginx нового хостинга обязан слать `X-Forwarded-Proto: https` —
  без этого Django будет считать HTTPS-запросы незащищёнными.
- Как хостинг проверяет живость сервиса — TCP-сканом (как Render) или
  HTTP-запросом? Если HTTP — 301 от редиректа сломает проверку, нужно
  добавить адрес проверки в `SECURE_REDIRECT_EXEMPT`, а не выключать
  `SECURE_SSL_REDIRECT`.
- После покупки домена и когда известны все поддомены — включить HSTS
  постепенно: 300 → сутки → год, с проверкой на каждом шаге. Убрать
  `'security.W004'` из `SILENCED_SYSTEM_CHECKS`, когда включите.

**В коде:** `config/settings_production.py` — `SECURE_SSL_REDIRECT`,
`SECURE_PROXY_SSL_HEADER`, `SECURE_HSTS_SECONDS`, `SILENCED_SYSTEM_CHECKS`.

## 2. Проверка живости сервиса

**Было.** Render сканировал TCP-порт (не HTTP-путь, `healthCheckPath` не был
задан). `gunicorn` обязан был открыть порт за ~3 минуты от старта — иначе
деплой падал с `Timed Out`.

**Проверить/настроить:**
- Каким способом новый хостинг проверяет живость — TCP-сканом, HTTP GET на
  путь, чем-то ещё.
- Если HTTP — см. пункт 1 (конфликт с `SECURE_SSL_REDIRECT`), возможно
  понадобится отдельный `healthCheckPath`.
- Сколько времени даётся на старт до первой успешной проверки — тяжёлые
  операции (миграции, collectstatic) должны укладываться до неё.

**В коде:** `Procfile` (команда `gunicorn`); предупреждение уже стоит в
`config/settings_production.py` у `SECURE_SSL_REDIRECT`.

## 3. Бэкапы базы

**Было.** На бесплатном тарифе Render встроенных бэкапов не было — делали
вручную (`pg_dump`), см. `docs/RUNBOOK.md` → «Бэкап и восстановление».

**Проверить/настроить:**
- Даёт ли новый хостинг встроенные автобэкапы БД. Если да — уточнить
  частоту и срок хранения, этого может быть достаточно.
- Если нет (или недостаточно) — сохранить ручной процесс `pg_dump` из
  RUNBOOK.md, завести расписание (cron/планировщик).
- Куда складывать дампы вне репозитория (`.gitignore` уже закрывает
  `*.dump` и `prod_backup_*` — это универсальное правило, менять не надо).

**В коде:** `docs/RUNBOOK.md` → «Бэкап и восстановление» (команда `pg_dump`).

## 4. SECRET_KEY

**Было.** `render.yaml` генерировал ключ сам (`generateValue: true`) и
подставлял его в переменную окружения `SECRET_KEY`.

**Проверить/настроить:**
- На новом хостинге сгенерировать ключ вручную, например:
  `python -c "import secrets; print(secrets.token_urlsafe(50))"`
- Положить его в переменные окружения хостинга под именем `SECRET_KEY`.
- Код уже требует ключ обязательно и падает при старте без него — менять
  ничего не нужно, только сам факт генерации теперь ручной, не автоматический.

**В коде:** `config/settings_production.py` — `SECRET_KEY = os.environ['SECRET_KEY']`.

## 5. ALLOWED_HOSTS → weconomics.ru

**Было.** `render.yaml` задавал `ALLOWED_HOSTS=.onrender.com` переменной
окружения.

**Проверить/настроить:**
- На новом хостинге задать переменную окружения
  `ALLOWED_HOSTS=weconomics.ru,www.weconomics.ru`.
- Если фронт и бэкенд окажутся на разных адресах — заполнить
  `CSRF_TRUSTED_ORIGINS` (сейчас пуст по умолчанию, это нормальное
  значение для одного домена).
- Код падает при старте, если `ALLOWED_HOSTS` пуст, и запрещает `*` —
  менять ничего не нужно, только значение переменной на новом хостинге.

**В коде:** `config/settings_production.py` — `ALLOWED_HOSTS`,
`CSRF_TRUSTED_ORIGINS`.

## 6. Версия Python

**Было.** `render.yaml` фиксировал `PYTHON_VERSION: 3.13.12` переменной
окружения. Файл удалён вместе с отказом от Render.

**Проверить/настроить:**
- Чем новый хостинг фиксирует версию интерпретатора (переменная окружения,
  файл `.python-version`, Docker-образ, настройка PaaS) — способ зависит
  от выбора хостинга.
- Локально уже стоит 3.13 (`venv313/`), лок `requirements/base.txt` собран
  под неё — ориентир для версии на проде.

**В коде:** раньше — `render.yaml` (удалён); `requirements/README.md`
подтверждает, что лок собирается на 3.13.

## 7. Раздача статики

**Было и остаётся.** WhiteNoise раздаёт статику
(`whitenoise.middleware.WhiteNoiseMiddleware`,
`CompressedManifestStaticFilesStorage`) — это НЕ Render-специфика, работает
на любом хостинге, трогать не нужно. Но шаг `manage.py collectstatic --noinput`
раньше запускал `startCommand` из `render.yaml` перед стартом `gunicorn` —
`Procfile` сам этот шаг не делает.

**Проверить/настроить:**
- На новом хостинге прописать запуск `collectstatic --noinput` (и `migrate
  --noinput`) в build- или start-команде деплоя — раньше это делал
  `render.yaml`, теперь этот шаг нигде не прописан.

**В коде:** `config/settings_production.py` (`STATIC_ROOT`, `STORAGES`),
`Procfile` (не содержит `collectstatic`/`migrate`).

## 8. Ограничение на длинные внешние транзакции

**Было.** PostgreSQL на free-тарифе Render обрывала долгие внешние
транзакции — большой дамп в одной транзакции не доезжал. Решение — грузить
данные порциями (по файлу), каждая в своей короткой транзакции.

**Проверить/настроить:**
- Есть ли у нового хостинга похожий лимит на длительность транзакции.
- Если лимита нет — порционная заливка всё равно практична (меньше памяти
  на разбор каждого файла), укрупнять порции не обязательно, но можно.

**В коде:** `problems/management/commands/dump_for_deploy.py` (порции по
`--chunk`), `docs/RUNBOOK.md` → «Данные: заливка в прод». Механизм не
менялся, менять и не планируется.

## 9. Память и процессор — нижняя граница

**Было.** Render free-tier: 1 общий CPU, 512 МБ памяти. Под это ограничение
приняты решения:
- `LOAD_EMBEDDINGS_MODEL = False` — модель эмбеддингов (`sentence-transformers`,
  ~2,12 ГБ с индексом) на проде не грузится вообще, эмбеддинги считаются
  локально и доливаются в базу;
- `gunicorn` запускается с 2 воркерами (`Procfile`).

**Проверить/настроить:**
- Указать 512 МБ / 1 CPU как **нижнюю границу** требований к новому
  хостингу — меньше означает переделывать то, что уже подстроено под этот
  потолок.
- Если новый хостинг даёт заметно больше — можно пересмотреть
  `LOAD_EMBEDDINGS_MODEL` и число воркеров, но осторожно: в
  `docs/ARCHITECTURE.md` → «Три мины многопроцессной выдачи» описано, что
  при нескольких воркерах модель размножается в памяти по числу воркеров
  (9 воркеров × 2,12 ГБ = 19 ГБ) — есть готовый план выноса поиска в
  отдельный процесс с int8-ONNX ([ADR 0008](adr/0008-search-separate-process-int8.md)),
  прежде чем поднимать число воркеров.

**В коде:** `config/settings_production.py` (`LOAD_EMBEDDINGS_MODEL`),
`Procfile` (`--workers 2`), `docs/ARCHITECTURE.md` («Три мины многопроцессной
выдачи», ADR 0008).
