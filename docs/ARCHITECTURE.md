## Стек

- **Python 3.13** + **Django 5.2 LTS** + **PostgreSQL 17**.
  Переход сделан 2026-08-19 — [ADR 0007](adr/0007-target-stack-python313-django52.md).
  Локально доступны обе базы: SQLite для повседневной работы, PostgreSQL 17 в
  контейнере — для доказательства корректности ([ADR 0009](adr/0009-postgres-local-dev.md)).
- Проект: `config/`. Основное приложение: `problems/`. Локальная база — `db.sqlite3`.
- Кастомный пользователь `problems.User` с полем `role`; роли платформы —
  в отдельной модели `UserProfile` (`problems/models_platform.py`).
- Зависимости: исходники `requirements/*.in`, локи `requirements/*.txt`
  (собраны `pip-compile` на 3.13). Корневые `requirements.txt` и
  `requirements-local.txt` — указатели на них.
- Драйвер PostgreSQL — см. раздел «Локальная СУБД» ниже.
- Виртуальное окружение — `venv313/`. Рядом сохранены `venv/` (3.9) и
  `venv312/` (мост) до подтверждения владельцем.

Синтаксис `int | None` разрешён с 2026-08-19 (union через `|` требует Python
3.10+). Массово переписывать существующие `Optional[int]` не надо — это шум в
диффе; снят только запрет на новое.

⚠️ **Путь к интерпретатору зависит от машины.** На macOS — `./venv313/bin/python`,
на Windows — `venv313/Scripts/python.exe`. В старых записях проекта встречается
`venv/` без цифр — это окружение на Python 3.9, оно оставлено как страховка
перехода и боевым больше не является.

## Локальная СУБД, драйвер и CI

### Локальная СУБД

`docker-compose.dev.yml` в корне поднимает **PostgreSQL 17** и **Redis 7**
одной командой. SQLite остаётся для повседневной работы, но доказательством
корректности больше не считается ([ADR 0009](adr/0009-postgres-local-dev.md)).

```bash
docker compose -f docker-compose.dev.yml up -d
manage.py test --settings=config.settings_test_pg
```

Порты наружу **55432** и **56379** — нестандартные намеренно, чтобы не
столкнуться с чужой установкой PostgreSQL на 5432 и не начать молча писать не
в ту базу.

**Redis подключён как контейнер, но не к Django.** Кэш и сессии подключаются
отдельной работой, и она идёт ПОСЛЕ аудита границ доступа: кэш, розданный до
того, как разобрано, кто что имеет право видеть, раздаёт и чужие страницы тоже.

### Драйвер PostgreSQL

**`psycopg[binary]` 3.3.4** (с 2026-08-19). Раньше был `psycopg2-binary`.

Настройки менять не пришлось: `dj-database-url` отдаёт движок
`django.db.backends.postgresql`, а он с Django 4.2 сам определяет, какой
драйвер установлен. Смена драйвера — это одна строка в `requirements/base.in`
и пересборка локов.

Проверено отдельно то, где драйверы расходятся: `BinaryField` (там лежат
эмбеддинги — сырые байты numpy float32), дата и время с часовым поясом,
`JSONField` с кириллицей, сырые курсоры, `bulk_create`. Байт в байт, 4 096 из
4 096, вектор восстанавливается.

⚠️ **Одно отличие есть, и проект к нему уже готов.** psycopg2 отдавал `bytea`
как `memoryview`, psycopg3 отдаёт `bytes`. Код везде оборачивает результат в
`bytes(...)` (`catalog/semantic.py`, `find_similar`, `admin`), поэтому от
драйвера не зависит. Новый код обязан делать так же.

### Проверки в CI

`.github/workflows/ci.yml` — пять джобов на каждый пуш:

| Джоб | Что делает |
|---|---|
| `lint` | `ruff check .` по набору из `ruff.toml` |
| `security` | `bandit` с базовой линией, `pip-audit` по боевому локу |
| `migrations` | `migrate` с нуля на PostgreSQL 17, затем `makemigrations --check` |
| `tests` | весь набор против PostgreSQL 17 + Redis 7, с node и playwright |
| `deploy-check` | `check --deploy --fail-level WARNING` на боевых настройках |

**Ни одного `continue-on-error`.** Джоб, который «падает, но не считается», —
это зелёная галочка напротив непроверенного кода.

⚠️ **Две осознанные оговорки, чтобы их не приняли за недоделку.**

1. **Форматтер не включён.** `ruff format` переписал бы 448 файлов из 574 —
   95 639 строк. Настройки готовы, включение — отдельной работой после слияния
   открытых веток.
2. **У bandit есть базовая линия** (`.bandit-baseline.json`, 18 находок).
   Каждая НОВАЯ находка роняет джоб; старые ждут сессии аудита. 29 находок
   высокой важности не в линии — они починены по-настоящему
   (`usedforsecurity=False` у `md5`, который считает `content_hash` для
   дедупликации, а не для защиты).

Полная карта маршрутов с отметками мест, где владелец объекта берётся не из
`request.user`, — в [SECURITY-MATRIX.md](SECURITY-MATRIX.md).

## Приложения и их границы

| Приложение | За что отвечает | Чего в нём быть не должно |
|---|---|---|
| `problems` | Ядро: **все** модели, команды импорта, движки (эмбеддинги, дедуп, темы, шлюз), слой ИИ | Публичные страницы каталога |
| `catalog` | Публичный каталог, подборки, экспорт, семантический поиск | Модели (кроме прокси), логика кабинетов |
| `student` | Кабинет ученика: домашки, ответы, прогресс | Проверка работ учителем |
| `teacher` | Панель преподавателя: проверка, группы, конструктор работ | Публичные страницы |
| `game` | Econ Rush — игра на скорость по тестовым вопросам | Работа с `Problem` напрямую (есть свой `GameQuestion`) |
| `calc2` | Собственный графический калькулятор (D3 + Math.js) | Модели и миграции — их **нет** и не заводим |
| `calendar_stub` | Календарь занятий | — |

**Правило границ:** модели живут только в `problems`. Приложение, которому нужна
новая сущность, заводит её в `problems/models*.py`, а не у себя. Исключение —
`game.GameQuestion`: игровой пул намеренно отделён от банка задач, чтобы удаление
задачи не ломало журнал забега.

### Публичные страницы

- `/` — главная: поиск по центру, живая статистика, карточки разделов.
- `/catalog/` — каталог: фильтры (23 канонические темы, сложность, источник, тип,
  наличие решения), поиск, пагинация, три вида (строки / таблица / галерея),
  атлас тем как нулевое состояние. Шлюз качества прячет зафлагованные задачи.
- `/catalog/<id>/` — задача: условие, подпункты, ответ, решение
  (скрыто при `solution_needs_review`), блок «Похожие задачи».
- `/catalog/collection/...` — конструктор подборок (по токену, без логина) и
  экспорт в `.tex` / PDF.
- `/catalog/smart-search/` — «Подобрать похожие» (семантический поиск).
- `/student/`, `/teacher/` — кабинеты. `/game/` — Econ Rush (без логина).
- `/calc2/` — графический калькулятор. `/admin/` — управление контентом.

Регистрация на проде **закрыта** (живых пользователей нет).

## Модели — сводка

Полный список — в `problems/models.py` и `problems/models_platform.py`.

- **Контент:** `Topic`/`Subtopic`, `Tag`, `Source`/`SourceReference` (поле `grade`
  живёт здесь, не у задачи), `FileAsset`, `Problem`, `ProblemPart`, `ProblemVersion`.
- **`Problem`** — ядро. Ключевые поля: `statement`, `answer`, `solution`,
  `problem_type` (тесты — с префиксом «тест:»), `difficulty`, `status`,
  `embedding` (BinaryField, numpy float32), `content_hash`, `similar_problems` (M2M),
  `needs_quality_review` и `solution_needs_review` (флаги шлюза).
- **Педагогика:** `Skill`, `MistakeTag`, `Hint`, `Rubric`/`RubricCriterion`,
  `TheoryPage`, `StudentSkillProgress`, `StudentTopicProgress`.
- **Цикл ученик↔учитель:** `Lesson`, `Assignment`, `Submission`,
  `TeacherFeedback`, `StudentGroup`.
- **Инфраструктура:** `Collection`, `Job`, `Template`, `ExportRecord`,
  `ImportSession`, `DuplicateCandidate` (инвариант `a.id < b.id`),
  `AutoTopicAssignment`.

**Решение по M2M «задача ↔ навык/ошибка»:** объявлены ОДИН раз на стороне
`Problem` (`related_name='problems'`), доступны с обеих сторон. Иначе Django
создаст две таблицы связей под одну связь.

⚠️ **`Lesson` держит три отдельных M2M к `Problem`** (основные / со звёздочкой /
домашние) с разными `related_name`. Это три независимые таблицы, и так задумано:
задача бывает основной на одном занятии и домашней на другом.

🌐 **Боевой сайт:** https://qls-platform.onrender.com

- Хостинг **Render.com** (free, Frankfurt). БД — **PostgreSQL** `qls-db`.
- Репозиторий приватный `github.com/malinovskiy-makar/qls`, ветка `main`.
- Python **3.13** на проде (`render.yaml`). Docker не используется → **нет TeX** → PDF-экспорт

- `sentence-transformers` на проде **не грузится**: эмбеддинги считаются локально
  и лежат в базе, «похожие» работают по кэшу M2M.
- Файлы деплоя: `requirements.txt` (указатель на `requirements/base.txt` — лок
  без ML), `config/settings_production.py`, `Procfile`, `render.yaml`.

**Деплой = пуш в `main`** (Auto-Deploy On Commit, 2–4 минуты; Start Command
прогоняет `migrate` и `collectstatic`).

### Ограничения free-tier — известные мины

- **Shell недоступен.** Management-команды на проде напрямую запустить нельзя.
  Только локально против внешней базы либо временно через `startCommand`.
- **Port-scan timeout ~3 минуты.** `gunicorn` обязан стартовать первым; долгая
  операция до него убивает деплой с вердиктом `Timed Out`.
- **1 общий CPU / 512 МБ.** Тяжёлая фоновая операция душит `gunicorn`,
  health-чек падает, сервис уходит в петлю перезапусков.
- **Сон после 15 минут** без HTTP; просыпается ~30 секунд.
- **Срок бесплатного PostgreSQL — 90 дней.**

## Целевая архитектура (после переезда в РФ)

Решения приняты владельцем 2026-08-19 по итогам разбора архитектуры под запуск
в России. Пока не реализованы — это то, куда идём.

**Целевой стек: Python 3.13 + Django 5.2 LTS + PostgreSQL 17**
([ADR 0007](adr/0007-target-stack-python313-django52.md)).

✅ **Python 3.13 и Django 5.2 достигнуты 2026-08-19** (сессия 2Б). Осталось
**PostgreSQL 17** — это следующая сессия, вместе с Redis и CI.

⚠️ Пока выкатки не было, на сервере всё ещё крутится прежний рантайм.
`render.yaml` уже требует Python 3.13.12 — **до пуша в `main` проверить, что
хостинг эту версию даёт**, иначе сборка упадёт.

Не 6.x, потому что 6.0 и 6.1 не LTS (следующий LTS — 6.2 в апреле 2027), Channels
не поддерживает 6.1, а 6.1 отказался от PostgreSQL 14. Django 5.2 LTS живёт до
апреля 2028.

Не меняем при переезде: шаблоны Django вместо SPA, D3 + Math.js в `calc2`, numpy
для векторного поиска (31 500 × 1024 — **2,81 мс**, векторная база не нужна).

### Три мины многопроцессной выдачи

На бесплатном хостинге процесс один, и все три не видны. Они срабатывают ровно в
тот момент, когда мы поставим несколько воркеров.

**1. Модель в каждом воркере.** В `catalog/semantic.py` модель и индекс — ленивый
синглтон в памяти процесса. При 9 воркерах это **9 копий BGE-M3 по 2,12 ГБ = 19 ГБ**;
сервер умирает по памяти на девятом уникальном запросе к «Подобрать похожие».
Решение — вынести поиск в отдельный процесс с моделью в int8-ONNX
([ADR 0008](adr/0008-search-separate-process-int8.md)): ~700 МБ вместо 19 ГБ.

**2. Кэш не общий.** Локальный кэш процесса означает столько разных представлений
о свежести данных, сколько воркеров. Инвалидация индекса должна идти **по версии
в Redis**, а не в памяти.

**3. Сессии в базе.** `SESSION_ENGINE` не задан, сессии лежат в БД — на каждый
запрос игрока это лишний поход в PostgreSQL. Забег Econ Rush пишет состояние в
сессию на каждый ответ.

### Дуэль и переписка

PvP-дуэль строится на **Server-Sent Events + POST**, без WebSocket и Channels;
процесс `asgi` (uvicorn) резервируется на случай по-настоящему двусторонней
механики. **Свободный ввод текста между игроками запрещён архитектурно** — только
фиксированный набор реплик. Это снимает риск обязанностей организатора
распространения информации (хранение три года, содержимое сообщений, СОРМ).
[ADR 0003](adr/0003-duel-sse-not-websocket.md).
