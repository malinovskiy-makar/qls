# Поиск и эмбеддинги

Это рабочая инструкция для сессий по улучшению поиска: как он устроен сейчас,
почему промахивается и в каком порядке это чинить.

---

## Кто пользуется поиском

Три потребителя, у них разные требования — менять формулу отпечатка, глядя
только на один из них, нельзя.

1. **Страница «Подобрать похожие»** (`/catalog/smart-search/`). Пользователь
   описывает задачу словами, получает 15–20 похожих. Это НЕ «найди ровно ту
   самую» — это подбор материала для листка, и в этом качестве уже работает.
2. **Подбор домашней работы по описанию** (кабинет репетитора). Тот же движок,
   но результат сразу уходит в корзину работы, поэтому цена промаха выше.
3. **Будущий ИИ-ассистент.** Поиск станет его инструментом извлечения: модель
   будет спрашивать банк и опираться на то, что вернул поиск.

## Как устроено сейчас

**Модель — `BAAI/bge-m3`**, вектор **1024** измерения, sentence-transformers,
CPU, ~1,4 ГБ. Имя и размерность — в `problems/embedding_config.py`
(`EMBEDDING_MODEL_NAME`, `EMBEDDING_DIM`). **Все** команды и поиск обязаны
импортировать оттуда, а не дублировать строку.

**Хранение:** `Problem.embedding` — `BinaryField` с numpy float32.
⚠️ `BinaryField` отдаёт `memoryview`, а не `bytes` — нужна обёртка `bytes(blob)`,
иначе `np.frombuffer` падает.

**Индекс** (`catalog/semantic.py`): ленивый синглтон, матрица строится при первом
запросе и живёт в памяти процесса. Матрица — нормализованные эмбеддинги
published-задач без флага шлюза. Косинус считается как скалярное произведение,
топ-K отбирается через `np.argpartition`. Векторная база не нужна: грубый
перебор по ~31 тысяче векторов работает быстрее, чем стоит её обслуживание.

**Кодирование запроса — отдельный процесс** (С4, 22.08). `embed_query` больше
не поднимает модель у себя: он ходит по HTTP в контейнер `search`. Подробности
ниже, раздел «Сервис кодирования».

**Гибрид** (`catalog/hybrid.py`): dense-нога (эмбеддинги) и лексическая нога
складываются через **RRF** — `1/(k + место)`, `RRF_K = 60`. RRF выбран потому,
что не требует знать шкалы обеих ног и подбирать веса на глаз: у косинуса и у
лексического счёта разные единицы, и любые коэффициенты были бы подгонкой.

⚠️ **Модель на проде не грузится.** Эмбеддинги считаются локально и заливаются в
базу; «похожие» на проде работают по кэшу M2M `similar_problems`.

✅ **Мина №1 снята (С4, 22.08).** Раньше здесь стояло предупреждение: модель —
ленивый синглтон в памяти процесса, а при девяти воркерах это девять копий
BGE-M3 по 2,12 ГБ = 19 ГБ, и сервер умирает по памяти на девятом уникальном
запросе. Теперь модель живёт в отдельном контейнере `search`, а Django-воркеры
её не импортируют вовсе — это сторожится тестом, который ловит саму ПОПЫТКУ
импорта (`catalog/tests/test_search_service.py`, `test_django_не_лезет_за_моделью…`).

Модель запущена в **fp32**, а не в int8-ONNX, как предполагал
[ADR 0008](adr/0008-search-separate-process-int8.md): после переезда в отдельный
процесс экономия перестала решать, а цена квантизации (сдвиг косинуса + полный
пересчёт корпуса) осталась и неизмерима без эталонного набора запросов.
Обоснование — [ADR 0015](adr/0015-search-service-fp32.md).

## Сервис кодирования (С4)

```
браузер → nginx → Django (9 воркеров, модели НЕТ)
                     │  HTTP, внутренняя сеть Docker
                     ▼
                  search (1 процесс, BGE-M3 fp32, 2,12 ГБ)
```

| Что | Где |
|---|---|
| Сам сервис | `search_service/app.py` (FastAPI + uvicorn, **1 воркер**) |
| Клиент в Django | `catalog/search_client.py` (стдлибный `urllib`, без новых зависимостей) |
| Описание контейнера | `search_service/Dockerfile`, сервис `search` в обоих compose |
| Кэш векторов запроса | Redis, **база 7**, алиас кэша `search` |
| Настройки | `SEARCH_SERVICE_URL`, `SEARCH_SERVICE_TIMEOUT` |

⚠️ **Порт наружу не публикуется.** У сервиса `search` нет секции `ports` ни в
`deploy/docker-compose.yml`, ни в `docker-compose.dev.yml`. `/encode` работает
без авторизации: опубликованный порт раздавал бы нашу CPU-молотилку кому угодно.
Сторожится тестом `ComposeIsolationTests` (читает конфиги текстом) плюс ручной
проверкой curl — порядок в `docs/SERVER.md`.

⚠️ **Сервис отдаёт СЫРОЙ выход модели, без нормализации.** В `Problem.embedding`
лежит тоже сырой вектор, а нормализуют обе стороны в `catalog/semantic.py`
(`_build_index` для корпуса, `embed_query` для запроса). Нормализуй сервис у
себя — вектор запроса прошёл бы нормализацию дважды, корпусный один раз, и
косинус поехал бы молча.

⚠️ **Векторы едут base64, а не списком чисел JSON.** Требование «побитово тот же
вектор» проще выполнить, чем доказать: base64 от сырых байтов float32 не зависит
от реализации сериализатора на обоих концах. Проверяется сравнением `tobytes()`,
а не `allclose()` — «примерно равно» пропустило бы ровно ту потерю точности, ради
которой тест написан.

⚠️ **Отката на локальную модель при отказе сервиса НЕТ, и это намеренно.**
Соблазн «сервис лёг — посчитаем сами» вернул бы мину №1, причём незаметно: она
срабатывала бы только когда сервис недоступен, то есть в худший момент. Вместо
этого `SearchServiceUnavailable` → лексический поиск. В журнал идёт ОДНА строка
`search service unavailable: причина`, без traceback: пока сервис лежит, сюда
приходит каждый запрос, и простыни трассировок утопили бы настоящую аварию.

⚠️ **Версии ML-стека в `search_service/requirements.txt` закреплены и обязаны
совпадать с `requirements/local.in`** — тем билдом, которым посчитан корпус.
Модель одна и та же, но токенизация и пулинг живут в библиотеке: мажорный
подъём сдвинет вектор запроса относительно корпуса, и ни одна проверка не
покраснеет.

`/healthz` сервиса намеренно **не трогает модель**: пока она грузится (минуты),
контейнер обязан считаться живым, иначе compose убивал бы его по кругу и модель
не догрузилась бы никогда.

### Формула отпечатка `problem_to_text`

В `build_embeddings.py`, семь блоков: `title` + `statement[:500]` + тексты
подпунктов `ProblemPart.statement` (≤500 символов суммарно) + «Темы: …»
(канонические, кроме технической «Тест») + «Навыки: …» + `ai_blurb[:400]` +
«Теги: …» (только из `CANONICAL_TAG_NAMES`).

**Решение и ответ в отпечаток не входят** — иначе поиск начнёт находить задачи
по методу решения, а не по условию. Пустые блоки не добавляются. Требуется
`prefetch_related('parts', 'topics', 'skills', 'tags')`, иначе это N+1.

### ⚠️ Ловушка done-файла

> **С5 (22.08) закрыл эту ловушку для `build_embeddings`.** У `Problem`
> появились `embedding_version`, `embedding_model_build`,
> `embedding_source_hash` и `embedding_built_at` (миграция 0044), а у команды —
> флаг **`--stale`**: он сам сравнивает хеш текущего текста и версии констант
> с тем, что записано при последнем расчёте. Внешний файл больше не нужен, и
> «забыть вычистить id» стало нечем. Легаси-строки (посчитаны до С5) имеют
> пустые поля версии и потому считаются устаревшими — это ожидаемо, не баг.
>
> Раздел ниже остаётся про **`night_embeddings`**: он по-прежнему работает по
> файлу, и ловушка в нём живая.

`night_embeddings` вычитает из очереди все id, уже записанные в
`reports/night_session/embeddings_done_ids.txt`. Если у задачи изменился текст, а
её id уже в done-файле, **повторный запуск молча её пропустит** — и напишет
«осталось 0», что выглядит как успех. Флага `--force` нет.

Правильный порядок: сначала удалить нужные id из done-файла, потом запускать.

```bash
python3 -c "
ids = set(open('ids_to_recompute.txt').read().split())
p = 'reports/night_session/embeddings_done_ids.txt'
kept = [l for l in open(p) if l.strip() not in ids]
open(p, 'w').writelines(kept)
print('removed', len(ids))
"
./venv/bin/python manage.py night_embeddings --ids-file ids_to_recompute.txt
```

**После любой правки `statement` или подпунктов эмбеддинги изменённых задач
обязательно пересчитать.** Иначе поиск деградирует именно на тех задачах,
которые только что починили.

## Почему промахивается

Три причины, и они разной природы.

**1. Сюжетность условий.** Олимпиадное условие намеренно завёрнуто в историю —
бабушка, ресторан, две страны. Это свойство домена, а не дефект данных: сюжет
занимает бо́льшую часть текста и забивает экономический смысл в отпечатке. Две
задачи про одну и ту же монополию с разными сюжетами оказываются далеко друг
от друга.

**2. Асимметрия «сухой запрос ↔ условие-рассказ».** Пользователь пишет
«монополия, линейный спрос, найти оптимум» — три строки без сюжета. В корпусе
такого текста нет ни у одной задачи. Лечится **HyDE**: дешёвая модель придумывает
гипотетическое условие-магнит, и ищем уже им. Проверено вручную — подняло задачу
с «не найдено» до 88%. Работает на «чистых» задачах, слабее на сюжетных.

**3. Лексическая нога не знает русской морфологии.** «Эластичности» и
«эластичность» для неё разные строки. На русском языке с его словоизменением это
режет вторую ногу гибрида заметно сильнее, чем на английском.

## Словарь терминов — лексический слой (С6, 22.08)

`data/econ_terms.json` собирается командой `manage.py build_econ_terms` из
`data/econ_terms_source.md` (13 341 строка, машинный перебор десяти учебников
на 6 743 страницы). Читается через `problems/econ_terms.py`.

| Что | Сколько |
|---|---|
| Канонических терминов | 1 772 |
| Русских алиасов / English / обозначений | 651 / 1 291 / 916 |
| Тематических разделов | 32 |
| Символов в обратном индексе | 503 (из них 56 неоднозначных) |

Словарь бьёт по причине №3 выше: он даёт синонимы, английские эквиваленты,
обозначения и словоформы в четырёх падежах — то, чего IDF не умеет в
принципе, потому что видит разные строки.

⚠️ **Обозначение с более чем одним термином НЕ нормализуется автоматически
вовсе.** `P` — цена, уровень цен и опцион пут; `S` — предложение и базисный
актив; `C` — потребление, купон и опцион колл; `π` — прибыль и инфляция.
Правило контринтуитивно (кажется, что чем больше сопоставлений, тем лучше) и
исходит от самого словаря: замена без контекста УХУДШАЕТ поиск. Проверяйте
`auto_normalize` или зовите `normalizable_notation()`, которая сама вернёт
`None` для неоднозначного символа.

⚠️ **Лемматизировать по `parse(word)[0]` НЕДОСТАТОЧНО.** Замер 22.08 на
контрольном наборе словаря (7 057 словоформ): разбор по первому — самому
вероятному — варианту не сводит 184 формы к их термину, это **2,61 %
молчаливых промахов**. Ломается на омонимии: «среднее» разбирается и как
прилагательное, и как существительное, «график» спорит с «графикой».
Сравнение по ВСЕМ вариантам разбора даёт 0 промахов. Защищено тестом
`test_наивный_разбор_по_первому_варианту_недостаточен`, который намеренно
краснеет, если кто-то «упростит».

⚠️ **Источник `.md` руками не правится.** Известные пропуски чинятся в
`KNOWN_FIXES` команды сборки — иначе следующая версия словаря тихо откатит
починку. Так закрыт `MISSING: AD–AS` (термин был, но обозначение только через
дефис, а через ен-тире — нет, и в индекс не попадало).

**Словарь НЕ заменяет `CANONICAL_TAG_NAMES`.** Сверка по леммам 22.08: из 222
тегов 53 не находятся в словаре вовсе — 3 из них вообще не термины (тип
задания), 6 составные «X и Y», остальные ~44 — настоящие пробелы словаря.
Решение и список — в Notion.

## Почему увеличение размерности вектора — не рычаг

Соблазн «взять модель на 2048 или 4096 измерений» надо снять сразу.

- **Потолок ставит вход, а не ёмкость.** Мы эмбеддим сюжетный текст. Больший
  вектор аккуратнее закодирует тот же сюжет — и промахи останутся теми же.
- **Цена кратная.** Размерность вдвое — вдвое больше индекс в памяти, вдвое
  больше поле в базе, плюс полный пересчёт всех ~31 тысячи векторов.
- **Облачные API дают МЕНЬШЕ измерений, а не больше.** У Яндекса — 256. Переход
  на облако размерность не поднимет.
- **Корпус и запрос обязаны кодироваться одной моделью.** Сменили модель —
  пересчитывайте весь корпус, иначе сравниваете несравнимое. Это делает смену
  модели дорогой операцией, а не экспериментом.

**Правило:** корпус и запрос кодируются одним и тем же билдом модели. Если
запросы когда-нибудь будет обслуживать int8-ONNX ради скорости, корпус
пересчитывается тем же int8-ONNX.

## Порядок работ по убыванию отдачи

1. **Измеритель.** Пока нет числа, любое улучшение — вопрос вкуса. Есть
   `catalog/management/commands/benchmark_search.py` (5 запросов, топ-10) и два
   эталона: `reports/bge_benchmark/before_minilm.txt` и `after_bge_m3.txt`.
   Расширить набор запросов и зафиксировать метрику ДО остальных работ.
2. **Лексическая нога с морфологией.** Самая дешёвая содержательная правка:
   привести слова к нормальной форме, и вторая нога гибрида начнёт работать.
3. **HyDE по порогу.** Не на каждый запрос, а когда лучший счёт ниже порога:
   короткий сухой запрос — включаем, развёрнутый — нет.
4. **Обогащение корпуса.** «Дано / найти», контекстная аннотация, темы — сухая
   выжимка сути рядом с сюжетом. Главный рычаг качества и самая большая работа.
   Пилот: 300 задач меньше чем за доллар, эмбеддить резюме, посмотреть глазами;
   помогает — полный прогон.
5. **Формула отпечатка v2 и полный пересчёт.** Только после того, как измеритель
   покажет, что новые блоки дают прирост.
6. **Реранкер.** Только по результату замера. Это самый дорогой шаг и первый
   кандидат на выброс, если предыдущие пять закрыли задачу.

## Команды

```bash
build_embeddings --limit N      # первые N задач без эмбеддинга
build_embeddings --reset        # пересчитать все
build_embeddings --stale        # только устаревшие: изменился текст (по хешу)
                                # или сменились версия формулы/сборка модели.
                                # Замена done-файлу, см. С5 выше.
night_embeddings --ids-file F   # по списку id (см. ловушку done-файла)
find_similar --problem-id N --limit 10
cache_similar                   # залить похожие в M2M (этим живёт прод)
benchmark_search                # замер качества
build_econ_terms                # словарь терминов: .md -> data/econ_terms.json
build_econ_terms --check        # только сверить числа, не записывать
```

⚠️ На Mac с BGE-M3 обязательно `--device cpu`; на 8 ГБ памяти — `--encode-batch 8`.
