# CORPUS-FORMAT.md — целевой формат банка задач

Разведка перед конвертацией двух выгруженных корпусов (SolveHub, 6 121 задача,
Markdown+LaTeX; Школково, 3 414 задач, чистый LaTeX) в формат, который
реально отрисовывает наш каталог. Конвертер и правки сайта — отдельные
сессии по итогам этого документа.

**Вывод одной строкой: вариант Б.** Сайт корректно рендерит математику
(и одиночный `$`, и `$$`), но не рендерит вообще ничего из структурной
разметки — ни markdown SolveHub, ни нематематические LaTeX-команды
Школково. Ни один из двух корпусов не эталон, приводить нужно оба.

## Раздел 2. Минимально необходимая правка сайта

**Не реализуется в этой сессии** — только описание, для отдельной сессии
по итогам этого документа.

### а) Только переносы строк

Самая дешёвая правка: `{{ problem.solution|linebreaksbr }}` (и аналогично
для `statement`/`answer`/`ProblemPart` полей) в пяти местах
`problem_detail.html`. Django-фильтр, экранирование сохраняется
полностью (`linebreaksbr` сначала эскейпит текст, потом вставляет
`<br>` — не открывает дыру, которую закрывала сессия 3Б).

Почему это нужно **при любом решении по разделу 3**: задача 6 (SolveHub,
без единой LaTeX-команды кроме математики) на живой проверке всё равно
показала «решение с критериями — одним сплошным абзацем». Абзацы
теряются не из-за markdown/LaTeX-разметки, а из-за отсутствия обработки
`\n` в принципе. Даже если весь корпус привести к «чистому тексту без
разметки», без этой правки он всё равно будет нечитаем.

Объём: 1 коммит, пять строк шаблона, без миграций, без новых зависимостей.

### б) + рендерер Markdown с санитайзером

Больше объёма, два отдельных вопроса, которые нельзя пропустить.

**Безопасность.** Ровно в этом месте — текст задачи, уезжающий в
разметку, — сессия 3Б нашла единственную дыру уровня «высокая» за весь
аудит (превью каталога, `innerHTML`, публичная страница без входа,
корпус 31 690 задач из внешних источников). Подключение markdown-рендерера
возвращает ровно тот риск, который закрывали: рендерер по определению
превращает пользовательский текст в HTML.

Обязательно нужен санитайзер с allow-list (не deny-all экранирование,
как сейчас) — `nh3` (Rust-биндинг Ammonia, поддерживается, единственный
кандидат, `bleach` в Python-экосистеме считается unmaintained с 2023).
Белый список тегов — по факту того, что реально порождает рендер
markdown из целевого формата (раздел 3): `p`, `strong`, `em`, `ul`, `ol`,
`li`, `br`, `code`, `pre`. **Явно НЕ включать**: `a` (ссылки — вектор
`javascript:`, `urlize` в проекте нигде не используется намеренно —
`test_xss_payloads.py:349-361`), `img` (см. раздел 3 — картинки идут
через `FileAsset`, не через тег в тексте), `script`, `style`, `iframe`,
любые `on*`-атрибуты. Тест `test_xss_payloads.py` (6 нагрузок, 4 роли)
нужно прогнать заново на **выходе рендерера**, а не на сыром тексте —
он сейчас проверяет, что `{{ }}` без `|safe` не пропускает теги; после
подключения рендерера источник риска другой (сам рендерер + `|safe` на
его выходе), тест должен переехать вместе с ним.

**Порядок операций — техническое требование, не опция.** LaTeX-формулы
(и в SolveHub, где 56.7% задач их содержат, и в приведённом к
markdown-формату Школково) состоят из `_` (нижние индексы: `$x_1$`,
`$P_D$`) и могут содержать `*`. Стандартный markdown-парсер не знает о
`$...$` как о границе — если пропустить текст через него **до** или
**без учёта** математики, `$x_1$` превратится в `$x<em>1</em>$` до того,
как формула доедет до KaTeX. Рендерер обязан быть math-aware: сначала
вырезать/защитить `$...$`/`$$...$$`/`\(...\)`/`\[...\]`-диапазоны
плейсхолдерами, применить markdown-правила к остальному, вернуть
математику на место нетронутой. Библиотеки вроде `markdown-it-py` это
не делают «из коробки» — нужен кастомный препроцессор (не рендерер
целиком, четыре регулярки на границы + подстановка).

**Совместимость: как не сломать существующие ~31 690 задач.**

Предложение к обсуждению (то, что просил оценить): поле-признак формата,
`content_format = 'plain' | 'markdown'` на `Problem`. Рендерер применяется
только к `'markdown'`. Легаси получает `'plain'` по умолчанию (через
миграцию с `default`) и не трогается вообще — путь в шаблоне: если
`plain` → текущее поведение (autoescape + `linebreaksbr`), если
`markdown` → рендер + `nh3` + `|safe`.

Оценка подхода: **правильный, потому что дешёвый и обратимый.** Один
булев переключатель на объект, а не глобальный флаг — откатить можно
точечно по одной задаче, если рендер что-то испортил, не трогая
остальные 31 690. Ровно та же логика, что уже принята в проекте для
флага `ai_generated` (SolveHub) — «откат бесплатный, решение не
цементируется» (Notion, решение от 2026-08-20).

Лучше не вижу — единственная альтернатива (детектировать markdown
эвристикой по содержимому вместо явного поля) добавляет непредсказуемость
ровно там, где предсказуемость важнее всего: 31 690 работающих сегодня
задач не должны зависеть от того, угадает эвристика правильно или нет.

Риск даже для `'markdown'`-контента (см. Шаг 1, пункт 3 ниже) — реальный,
но управляемый через math-aware препроцессор выше, а не через отказ от
рендерера.

Объём: рендерер + санитайзер (новые зависимости), миграция на одно
поле с default, кастомный math-aware препроцессор, перенос/расширение
`test_xss_payloads.py`, ревью шаблонов на пяти местах.

## Раздел 3. Целевой формат корпусов

| Конструкция | Что делаем | Почему |
|---|---|---|
| `$...$`, `$$...$$`, `\(...\)`, `\[...\]` | Не трогаем | Сайт уже умеет, оба корпуса используют |
| Голые `\begin{equation\|align\|gather}...\end{...}` (113 задач Школково, см. Шаг 1) | Обернуть в `$$...$$` | Сами по себе не ловятся auto-render'ом (он ищет строки-разделители, не команды) — 173 вхождения сегодня показались бы сырым текстом |
| `\begin{cases}...\end{cases}` | Не трогаем (почти всегда уже внутри `$`/`$$`/`\[...\]`, см. Шаг 1) | Уже работает |
| Markdown `**жирный**`, `*курсив*`, LaTeX `\textbf{}`, `\textit{}`/`\emph{}` | Убрать разметку, оставить только текст (вариант а) сайта) ИЛИ конвертировать в `**`/`*` формат-агностично (вариант б) — конвертер пишет ОДИН слой независимо от решения по сайту | И markdown-, и LaTeX-варианты сегодня не рендерятся; конвертер должен привести оба к ОДНОМУ промежуточному представлению, чтобы решение по разделу 2 принималось один раз, не по каждому корпусу отдельно |
| Списки нумерованные (`1.`/`1)`/`а)`/LaTeX `\begin{enumerate}`) | Нумерация внутри текста — оставить текстом с явным переносом строки на пункт (после правки (а) сайта — реальный список). Подпункты `а)/б)/в)` — см. решение ниже | `diagnostics.py` уже распознаёт `1.` и `1)` как равноправные варианты — домашний стандарт не выбирает один |
| Списки маркированные (`-`, `•`, LaTeX `\begin{itemize}`) | Аналогично — текст с переносом на пункт | То же |
| Таблицы простые (SolveHub: 4 markdown-таблицы, все просты по построению GFM; Школково: 177 из 189 `tabular`, без `\multicolumn`/`\multirow`) | Конвертировать в markdown-таблицу (`\|...\|`) — рендерится, если сайт получит рендерер (раздел 2б); без рендерера — расплющить в подписанный текст «строка: значение, значение...» | Простая табличная структура однозначно переносится в любую сторону |
| Таблицы сложные (12 задач Школково, с `\multicolumn`/`\multirow`) | Не расплющивать автоматически — в очередь на ручной разбор | Слияние ячеек markdown-таблицей не выражается; автоматическая конвертация даст мусор |
| Картинки (SolveHub: `![]()`, абсолютный внешний URL; Школково: `\includegraphics`) | **→ `FileAsset` у себя** (решение ниже) | — |
| Подпункты `а)/б)/в)` | **→ `ProblemPart`** (решение ниже) | — |
| Критерии оценивания | **SolveHub → `Rubric`, вытащить из текста решения; Школково уже отдельное поле → `Rubric`** (решение ниже) | — |
| `\medskip`, `\bigskip`, `\quad`, `\qquad`, `\noindent`, `\centering` и прочее LaTeX-оформление отступов | Убрать целиком, без замены | Визуальный интервал — задача CSS/шаблона (после правки а), не текста задачи; переносить в любом виде некуда |
| Тире (`---`, `--`, `-`) | Нормализовать в реальные `—`/`–` при конвертации | Задача 8 на живой проверке показала `---` тремя дефисами — LaTeX-лигатуры (`---`→`—`, `--`→`–`) применяет только компилятор TeX, у нас их не будет |
| Кавычки (`<<`/`>>`, `` `` / '' ``, прямые `"`) | Нормализовать в `«»` | `«»` — уже подтверждённый домашний стандарт (`test_fix_latex_junk.py:66`: `<<Ромашка>>` → `«Ромашка»` считается починкой OCR-мусора, не наоборот) |
| Сноски (`\footnote{}`, 40 задач Школково) | Вынести в конец решения отдельным абзацем «Примечание: …», ссылку-маркер в тексте не пытаться имитировать | Сайт не поддерживает всплывающие сноски; лучше видимый текст, чем потерянный |
| Цвет (`\color`/`\textcolor`) | Убрать, оставить содержимое без цвета | 0 задач в инвентаре Школково, у SolveHub не встречается — не нужно решение сложнее «отбросить» |

### Картинки → `FileAsset`

**Решение принято, обоснование ниже.**

Забираем к себе: скачиваем в `FileAsset`, а не оставляем ссылкой на
`api.solvehub.app`/`s3.regru.cloud`. Файлы уже лежат на диске
(`weconomics-data/solvehub/images/`, `.../shkolkovo/images/` +
`image_map.json` с картой соответствий) — повторного скачивания конвертер
не потребует. Решающий довод — «чужой адрес может умереть»: у нас нет
контроля над жизненным циклом чужого S3-бакета или API третьей стороны,
а задача с оборвавшейся картинкой на проде — брак, который сам себя не
чинит и не сигналит.

### Подпункты `а)/б)/в)` → `ProblemPart`

**Решение принято, обоснование ниже.**

Раскладываем по `ProblemPart` — это существующая архитектура (`seed_demo.py`
создаёт подпункты именно так, не текстовым списком) и прямое требование
поиска: формула отпечатка `problem_to_text` (`build_embeddings.py`,
описана в `docs/EMBEDDINGS.md:59-68`) читает `ProblemPart.statement`
отдельным блоком (до 500 символов суммарно) наравне с `title` и
`statement`. Если подпункты SolveHub останутся текстом внутри одного
`statement`, эмбеддинг не увидит в них структуру, которую видит для
всех остальных 31 690 задач банка — поиск по подпунктам конкретно этих
задач будет работать хуже, чем по остальному банку, без видимой причины.

### Критерии оценивания → `Rubric`

**Решение принято, обоснование ниже.**

У Школково критерии уже отдельное текстовое поле (`GradeCriteriaTexSessionId`
→ `criteria_tex`) — переносится в `Rubric`/`RubricCriterion` прямым
маппингом. У SolveHub критерии вклеены в `answer_md` прозой
(`***Критерии****:* *1) Дан ответ...* *(+5 баллов)*` — видно на живой
проверке, задача 6) — конвертер обязан их **вычленить** из текста
решения в структурированный `Rubric`, не оставлять как сплошной текст.
Причина — не только чистота формата: `Rubric`/`RubricCriterion` — та
структура, на которой держится проверка домашних заданий (баллы по
критериям, а не бинарно «верно/неверно»); оставленные прозой критерии
для этой механики не видны и не работают, даже если человек их
прочитает глазами на странице задачи.

Практическое следствие для конвертера: нужен парсер критериев из прозы
SolveHub (заголовок «Критерии:», пункты с баллами в скобках) — отдельная,
менее тривиальная часть спецификации следующей сессии, не входит в эту.

## Раздел 4. Порядок работ

Зависимости между сессиями:

1. **Правка сайта, раздел 2а (переносы строк).** Не зависит ни от чего
   в этом документе. Можно делать хоть сегодня, отдельным
   PR — снижает боль на ЛЮБОМ корпусе, включая нынешние 31 690 задач,
   у которых при длинных решениях та же проблема.
2. **Решение по разделу 2б (рендерер Markdown).** Требует ответа
   владельца: нужен ли `content_format` вообще, или обходимся текстом
   без markdown-разметки (тогда конвертер в разделе 3 приводит оба
   корпуса к чистому тексту, минуя markdown целиком, и раздел 2б не
   нужен вовсе). **Это развилка, которая определяет объём конвертера** —
   писать его до этого решения нельзя, переделка будет дороже, чем
   ожидание.
3. **Конвертер SolveHub → целевой формат** (раздел 3, вся таблица) +
   парсер критериев из прозы. Зависит от (2).
4. **Конвертер Школково → целевой формат** (раздел 3 + обёртка голых
   окружений в `$$`). Зависит от (2). Может делаться параллельно с (3) —
   корпуса не пересекаются, общий только формат-назначение.
5. **Импорт в базу** — `Problem` + `ProblemPart` + `Rubric` + `FileAsset`,
   с дедупликацией между собой и с существующим банком (SolveHub и
   Школково размечены разными олимпиадами, но не исключено пересечение
   с уже импортированными 31 690). Зависит от (3) и (4).
6. **Пересчёт эмбеддингов** для новых задач (`build_embeddings`) —
   зависит от (5), см. ловушку done-файла в `docs/EMBEDDINGS.md`.

(2) — единственная развилка, требующая решения владельца до начала
кодирования; остальное — последовательность с понятными входами и

## Приложение: три измерения (2026-08-21, по данным на диске)

1. **Голые математические окружения (Школково).** 113 задач из 3 414
   (3.3%) содержат хотя бы одно `equation`/`equation*`/`align`/`align*`/
   `gather`, не обёрнутое целиком в `$`/`$$`/`\[...\]`/`\(...\)` —
   173 таких вхождения против 584 корректно обёрнутых (в основном
   `cases`, который почти всегда уже внутри более крупной формулы, просто
   не впритык к границе). Это прямая работа для конвертера Школково.

2. **Таблицы.**
   - Школково: 189 задач (5.5%) с `\begin{tabular}` — 177 простых (без
     `\multicolumn`/`\multirow`), 12 сложных.
   - SolveHub: 4 задачи с настоящей markdown-таблицей (`|...|` с
     разделителем) — GFM-таблицы структурно не поддерживают объединённые
     ячейки, поэтому все 4 «простые» по построению, отдельного класса
     «сложная markdown-таблица» не существует. Ещё 146 задач упоминают
     слово «таблица» в прозе без какой-либо табличной разметки — похоже,
     таблица встроена картинкой, а не текстом; при конвертации не
     трогаем, картинка уже покрыта решением по картинкам выше.

3. **Риск регрессии (`*`/`_` вне математики) для существующего корпуса.**
   Прямых данных мало: фикстур в проекте нет (`find`/`Glob` по
   `fixtures/` — пусто), локально всего 3 задачи + 2 подпункта
   (`seed_demo`) — проверено напрямую по живой dev-базе: **0 вхождений
   `*` и `_` вне LaTeX-формул во всех пяти объектах.** Прямой измеримый
   риск на доступных данных — нулевой, но выборка непоказательна для
   31 690 боевых задач, к которым доступа с этой машины нет.

   Оценка масштаба косвенно (не то же самое, что «наш» корпус, но
   единственный доступный ориентир по объёму): в самом SolveHub вне
   формул — 19 691 `*` (почти все — легитимный `**жирный**`, ожидаемо
   при 16.2% задач с bold) и 462 `_` (в основном — часть URL, например
   `vk.com/novaya_shkola?w=wall-73441626_142`, а не текст, который
   markdown-парсер трактует как курсив в реальных браузерах — большинство
   парсеров не бьют `_` внутри URL). Практический вывод не про частоту,
   а про архитектуру: `$x_1$` — нижний индекс внутри работающей сегодня
   формулы — есть у ЛЮБОГО корпуса с LaTeX-математикой, включая легаси
   (`Problem.statement.help_text`: «можно использовать LaTeX-формулы»).
   Это и есть довод в пользу math-aware препроцессора в разделе 2б —
   не как перестраховка, а как техническое требование независимо от
   того, насколько часто `_` встречается вне формул на практике.
