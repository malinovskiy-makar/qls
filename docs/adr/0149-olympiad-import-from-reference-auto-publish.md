# ADR 0149 — Импорт олимпиад из эталона и автопубликация уверенных заданий

* **Дата:** 2026-10-14
* **Статус:** принято владельцем (стоп-гейты 1 и 2 сессии «И2, часть 1»; решения Notion 13–14.10: автопубликация без человека для всех импортов, порядок записи «финграм → экономика → материалы»). Ветка `feat/olympiad-import`, в `main` не влито.
* **Связано:** ADR 0005 (ИИ пишет только новые поля), ADR 0141 (официальный эталон), ADR 0142 (эталон v2).

## Контекст

Официальные задания олимпиад оцифрованы (эталон v2: markdown, пункты, рисунки, решения, ответы, критерии). В банке сайта их почти нет. Старый `apply_olympiad_audit --import` умеет только эталон v1: текст, нарезанный из PDF, одна картинка, задачи скрытые.

С 20.08 каталог показывает только проверенное человеком. Владелец решил 13–14.10: задания, у которых строгая автопроверка уверена, публикуются без человека; остальные — скрыто и «на глаза».

Нужен один двигатель на все олимпиады реестра. Первая проверка — ВП финграмотность (89) и основы бизнеса (124). Дальше — МОШ финграм + предпринимательство (2 024 вместе с ВП) и экономика ВП + МОШ v5.

## Решение

1. **Команда `import_olympiad_reference`.** По строке очереди или эталона план — одно из пяти действий:
   - создать;
   - близнец (вторая привязка к новой задаче);
   - привязать к задаче банка;
   - на проверку (`link_review.csv`);
   - пропустить.

   По умолчанию — сухой прогон; запись — `--apply --yes-i-have-owner-approval`. Журнал хранит id всего созданного и дописанного, `--rollback` возвращает базу до единицы.

2. **Автопубликация — `ReviewVerdict` perfect от `auto:strict_check`.** Пакет `auto_import_<слаг>_<дата>` → `human_review=approved`, `published`, `hidden_pending_review=False`. Условия:
   - `auto_publish_ok` строки (страницы чисты по судье или слою ≥ 0,95 и числам, ответ при файле решений, условие, KaTeX, рисунки без флага, нет служебного блока);
   - KaTeX новых текстов без ошибок;
   - все файлы рисунков на диске.

   Иначе — `draft` + `hidden_pending_review` и строка в `human_tasks_import.csv`.

3. **Критерии оценивания** — разделом «Критерии оценивания» в конце решения: обычай ILE, SolveHub и импорта ВП-экономики. Ученик видит его в решении, ИИ-проверка получает его через эталонное решение.

4. **Пункты.** Если в условии пункты стоят сплошным хвостовым списком, хвост вырезается и создаются `ProblemPart`; баллы «(k баллов)» идут в `points`. Иначе страница показала бы пункты дважды. Пункты, вплетённые в рассказ, остаются в условии. Ответ раскладывается по пунктам только при точном совпадении меток.

5. **Рисунки.** `ProblemFigure` с маркером `[[FIGURE:<sha256>]]` встаёт после абзаца, за которым рисунок стоит на странице PDF: порядок блоков расшифровки. Если якоря нет, по очереди — подпись, абзац-метка, упоминание «рис./график», конец текста.

6. **Разметка под рендерер.** Рендерер сайта — подмножество markdown с `html: False`. Поэтому в новых текстах:
   - `<br>` → пробел в ячейке таблицы и перевод строки вне таблицы;
   - `<u>x</u>` → `*x*`;
   - `# X` → `**X**`;
   - `---` → пустая строка.

7. **«Уже в банке?»**
   - Кандидаты — гибрид сайта top-20 (BGE-M3 + BM25, RRF k = 60; решение 09.10).
   - Подтверждение — текстом ≥ 0,90 (сходство или вхождение) и числовым отпечатком (решение 02.09) со склейкой разрядов («300 000», `70\,000`) и без однозначных меток пунктов.
   - Если ≥ 2 заданий одного комплекта целиком в одной задаче банка, это «комплект одной задачей»: одна привязка с `raw_meta.kit_numbers`.
   - Одинаковые задания соседних классов одного сезона — одна новая задача, две привязки.
   - У привязанной задачи дописываются только ПУСТЫЕ ответ и решение (ADR 0005), только при совпадении целого текста и только у markdown-задач.

8. **Обогащение свежего импорта — `merge_enrichment_import`**, наследник `merge_enrichment_v2`.
   - Перевод старых `problem_type` и кодовые особенности сужены до задач журнала.
   - `title`, `problem_type`, `content_status` не перезаписываются; что предлагала модель — в CSV.

## Почему так

- **Автопубликация через вердикт, а не новым признаком.** Пятый признак видимости запрещён (CLAUDE.md). Глобальный `pending_review_gate --apply` прячет всё без `approved` — а вердикт переживает и его, и `human_review_mark --apply` (perfect-only → approved).
- **Отличимость.** Автоодобрение отличимо от человека по `reviewer` и `bundle`. Повторное ревью человеком перекрывает его без `SUPERSEDES`: брак сильнее идеального.
- **Ловушка отката.** `human_review_mark --revert` очищает ревью у ВСЕХ задач банка, поэтому откат идёт только журналом.
- **Двигатель на чистых правилах.** Правила текста — чистые функции (`problems/olympiad_audit/reference_import.py`), сверка — `bank_match.py`. Для экономики v5 меняется только вход.

## Отвергнуто

- **Исключение по списку в `pending_review_gate`.** Правило жило бы в коде шлюза.
- **Видимость как у 9 380 задач 30.08** (`--revert --sources`, `human_review` пусто). Честнее по смыслу поля, но глобальный запуск шлюза прячет такие задачи — сегодня он спрятал бы 9 380.
- **`Rubric` + критерии.** Разбор свободного markdown в `RubricCriterion(name, max_points)` ненадёжен, а на странице задачи рубрику не видно.
- **`merge_enrichment_v2` как есть.** Он пересчитывает кодовые особенности и переводит старые типы по всему банку, а `problem_type` и `content_status` переписывает поверх импорта.
- **Числовой отпечаток без склейки разрядов.** 24 верные пары SolveHub уходили «на проверку» из-за «70 000» ↔ `70\,000`.

## Последствия

- В локальной базе +85 задач (видимо 70), +132 строки `OlympiadRef`, 7 дописанных пустых полей. Журналы — в `audit_finbiz_20261013\<подпапка>\import_journal\`.
- 34 задания «на проверке» в банк не попали: ждут решения по `link_review.csv`.
- 59 заданий бизнеса живут внутри 12 задач-комплектов SolveHub: официальная привязка есть, отдельных задач нет.
- У 79 из 85 новых задач заголовок — заглушка («Задание 2», «ВП по … задание N»); `title_candidate` модели заполнен, применять ли его — отдельное решение владельца.
