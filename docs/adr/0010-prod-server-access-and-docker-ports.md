# ADR 0010. Боевой сервер: как устроен доступ и почему порты базы закрыты

**Дата:** 2026-08-21
**Контекст:** сессия «фундамент боевого сервера», VDS Selectel (Москва),
`weconomics.site`. Django ещё не развёрнут.

---

## Решение 1. Вход только по ключу, `sudo` без пароля

**Что сделано.** Заведён пользователь `makar` (uid 1000, группа `sudo`).
Пароль учётной записи **заблокирован** (`passwd -l`), вход возможен только
по ключу `id_ed25519_weconomics`. При этом `sudo` настроен как `NOPASSWD`.

**Почему.** Это выглядит как ослабление, но альтернативы хуже:

| Вариант | Чем плох |
|---|---|
| Пароль у аккаунта + обычный `sudo` | Пароль пришлось бы держать где-то ещё и вводить при каждой автоматической операции; неинтерактивная работа по SSH становится невозможна |
| Пароль заблокирован + обычный `sudo` | `sudo` не сработает **никогда** — проверять нечего. Пользователь бесполезен |
| Пароль заблокирован + `NOPASSWD` | Выбрано |

Ровно так устроены штатные облачные образы Ubuntu (пользователь `ubuntu`
в AWS и GCP). Пароль в такой схеме не защищает: попасть в сессию можно только
предъявив приватный ключ, а кто предъявил ключ — уже прошёл единственную
настоящую границу.

**Чем компенсировано:** вход по паролю по SSH запрещён совсем; прямой вход
под root по SSH запрещён; `ufw` пускает только 22/80/443; `fail2ban` банит
за перебор.

**Отвергнуто:** вход под root по ключу «чтобы проще» — тогда любая ошибка
выполняется с полными правами без единой паузы.

## Решение 2. У PostgreSQL и Redis нет секции `ports`

**Что сделано.** В `deploy/docker-compose.yml` у служб `postgres` и `redis`
секции `ports` нет вообще. Наружу порты публикует только `nginx` (80 и 443).

**Почему.** Docker пишет свои правила в iptables **выше** правил ufw.
Публикация `"5432:5432"` открыла бы базу всему интернету, при этом
`ufw status` продолжал бы показывать, что всё закрыто. Расхождение между
тем, что показывает firewall, и тем, что видит сканер, — худший вид дыры:
её не замечают, пока не станет поздно.

Службы общаются по внутренней сети Docker `backend`, по именам `postgres`
и `redis`. Django в следующей сессии будет ходить туда же и тоже
без публикации портов.

**Если порт всё же понадобится для отладки** — только с явным адресом:
`"127.0.0.1:5432:5432"`. Без `127.0.0.1` в начале порт открыт всем.

**Проверено:** внешняя проверка с узлов check-host.net (Израиль, Иран,
Польша) — на 5432 все три узла не подключились; `ss -tlpn` на сервере
показывает на внешнем интерфейсе только 22, 80 и 443.

## Решение 3. Конфигурация SSH защищена тремя слоями, а не одним

**Что сделано.** Запрет входа по паролю прописан в трёх местах сразу:
`/etc/ssh/sshd_config.d/00-hardening.conf`, переписанный
`50-cloud-init.conf` и `/etc/cloud/cloud.cfg.d/99-disable-ssh-pwauth.cfg`.

**Почему.** `Include /etc/ssh/sshd_config.d/*.conf` стоит на **12-й строке**
основного конфига, а в OpenSSH выигрывает **первое** встреченное значение
параметра. Cloud-init держит там `50-cloud-init.conf` с
`PasswordAuthentication yes` и может восстановить файл при загрузке.

Правка одного только `/etc/ssh/sshd_config` не подействовала бы вообще —
и это молчаливый отказ: команда отработает, файл изменится, а вход по паролю
останется открыт. Имя `00-hardening.conf` выбрано так, чтобы файл читался
раньше cloud-init по алфавиту.

**Проверено перезагрузкой:** после ребута `sshd -T` показывает
`passwordauthentication no` и `permitrootlogin no`, а сам
`50-cloud-init.conf` остался переписанным.

## Решение 4. Автоматической перезагрузки нет

**Что сделано.** `unattended-upgrades` ставит обновления безопасности сам,
но `Automatic-Reboot` не включён.

**Почему.** Внезапная перезагрузка уронила бы сайт в непредсказуемый момент.
Обновления ядра применяются вручную, примерно раз в месяц — порядок описан
в [docs/SERVER.md](../SERVER.md).

**Цена решения:** между выходом обновления ядра и ручной перезагрузкой
сервер работает на старом ядре. Принято сознательно: доступность важнее.

---

## Что осталось нерешённым

- **Резервных копий базы нет.** Данных в ней тоже пока нет, но настроить
  копирование нужно **до** переноса корпуса.
- **HSTS не включён.** Заголовок кешируется браузерами на месяцы и не
  откатывается; включаем, когда сайт заработает по-настоящему.
