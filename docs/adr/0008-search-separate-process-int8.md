# ADR 0008. Семантический поиск — отдельный процесс, модель в int8-ONNX

**Источник:** разбор архитектуры под запуск в РФ, § 4 «Три мины».

## Контекст — мина, невидимая на бесплатном хостинге

В `catalog/semantic.py` модель и индекс — ленивый синглтон **в памяти процесса**.
На бесплатном хостинге процесс один, и всё выглядит прекрасно.

При **9 воркерах** это **9 копий BGE-M3 по 2,12 ГБ = 19 ГБ**. Сервер умирает по
нехватке памяти на девятом уникальном запросе к «Подобрать похожие».

## Решение

Отдельный **процесс поиска** (FastAPI/uvicorn, один экземпляр, слушает только
`localhost`), внутри — модель в **int8-ONNX**. Django ходит к нему по HTTP.

### Обязательные условия

- **Кэш векторов запросов в Redis:** повторный одинаковый запрос не доходит до
  модели.
- **Инвалидация индекса — по версии в Redis**, а не в памяти процесса.
  Иначе каждый воркер живёт со своим представлением о свежести индекса.
- **Деградация:** сервис недоступен → лексический поиск и кэш
  `similar_problems`, честная плашка. **Никогда не 500.**
- ⚠️ **Корпус и запрос кодируются одним билдом модели.** Если запросы обслуживает
  int8-ONNX, корпус пересчитывается int8-ONNX — иначе систематический сдвиг
  косинуса.

## Отвергнутые варианты

- **B — эмбеддинги через облачный API.** У Яндекса 256 измерений против наших
  1024; качество надо перезамерять заново; плюс полный пересчёт корпуса.
- **C сам по себе (только квантизация).** 541 МБ всё равно множатся на число
  воркеров.

**A + C** даёт ~700 МБ вместо 19 ГБ, ничего не пересчитывая, и перезапуск веба
не выгружает модель.

## Связь с текущим состоянием

Сегодня модель на проде не грузится вовсе — [ADR 0002](0002-embeddings-separate-process.md).
Этот ADR описывает целевую схему после переезда на свой сервер, где поиск должен
наконец заработать в бою.
