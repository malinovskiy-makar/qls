# ADR 0092. Состояние текста — своё поле `content_status`, а не `status='hidden'`

**Дата:** 2026-09-03
**Статус:** принято
**Автор решения:** владелец; реализация — Claude Code

> **Про номер.** Номера 0063–0066 заняты на ветке
> `feat/olympiads-screens`,
> в этой ветке их файлов нет. Взят следующий свободный ЗА пределами обоих
> диапазонов — иначе повторился бы уже известный конфликт «два ADR с одним
> номером на разных ветках» (карточка в Notion про 0050 и 0051).

## Контекст

Боевой прогон обогащения дал две очереди на чистку: 1 596 задач, которые
модель признала «не задачей», и 3 336 задач с серьёзными дефектами текста.
Решение владельца дословно: «чистый мусор 100 % = удаление, есть сомнения
что мусор / ужасный код / другие проблемы = пока скрываем на сайте».
Ручного просмотра не будет.

Скрывать надо было чем-то. В банке уже есть три признака невидимости, и
каждый отвечает на свой вопрос:

* `status='hidden'` — «убрано руками по конкретному поводу»: служебные
  фикстуры, снятое с публикации, задачи без вложения (см. раздел про
  `missing-figure` в `docs/DATA.md`);
* `needs_quality_review` — «скрыто, потому что ПЛОХОЕ» (детекторы качества,
  `quality_gate`);
* `hidden_pending_review` — «скрыто, потому что человек ЕЩЁ НЕ СМОТРЕЛ».

## Решение

Заведено ЧЕТВЁРТОЕ поле `Problem.content_status` (`ok` / `needs_fix` /
`junk`, миграция `problems/0050`). Оно отвечает на вопрос «пригоден ли ТЕКСТ
к показу», а не «хорошая ли это задача» и не «смотрел ли человек».

## Почему не `status='hidden'`

Потому что `hidden` уже несёт два своих смысла, а причина скрытия — это то,
что понадобится через месяц, когда задачи будут возвращать.

Конкретно: снятие `hidden` подняло бы разом и служебные фикстуры, и снятое
с публикации руками, и битые тексты. Отличить их после смешения нечем —
поле одно, а поводов три. Обратная операция («вернуть починенные тексты»)
из `hidden` невыполнима без второго списка, который пришлось бы вести
отдельно; но отдельный список — это и есть отдельное поле, только хуже:
не проверяемое схемой и не видимое в админке.

Тот же довод уже применялся дважды — при заведении `needs_quality_review`
и `hidden_pending_review`. Это третье применение одного и того же правила,
а не новое исключение.

## Что было отвергнуто

**Переиспользовать `needs_quality_review`.** Он означает «детекторы качества
нашли брак рендера» и снимается своим `quality_gate --revert`. Дописать в
него результаты прогона значило бы сделать `--revert` этой команды
разрушительным для чужих данных.

**Держать состояние только в отчёте, без поля в базе.** Тогда фильтр
каталога пришлось бы делать по списку id из файла — 3 836 id в каждом
запросе. Это не работает ни по скорости, ни по смыслу: видимость задачи —
свойство задачи.

## Цена решения

Признаков невидимости стало четыре, и каждый новый запрос каталога обязан
помнить все четыре. Общей функции «видимая задача» в проекте нет — тройка
повторяется по месту в каждом запросе, и теперь это четвёрка в 16 местах:
`catalog/views.py` (10 мест), `catalog/hybrid.py`, `catalog/latex_export.py`,
`catalog/semantic.py`, `problems/hw_generator.py`, `game/views.py`,
`game/management/commands/build_game_pool.py`.

Пятый признак заводить уже нельзя — сначала надо свести четыре в одну
функцию. Это отдельная задача, заведена в Notion.

## Проверка

`problems/tests/test_content_cleanup.py` — 30 тестов. Четыре поломки
предохранителей проверены и краснеют: удаление без взгляда на ссылки,
поиск шаблона мусора внутри текста вместо совпадения целиком, снятая
проверка полноты выгрузки, скрытие задач с опечатками.
