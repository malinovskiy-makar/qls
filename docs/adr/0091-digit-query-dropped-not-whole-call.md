# ADR 0091. Поисковый запрос с цифрой выбрасывается из массива, а не роняет весь вызов

**Дата:** 2026-09-02
**Статус:** действует
**Связан с:** [0061](0090-autostop-counts-final-defects.md) — та же сессия,
вторая половина решения владельца.

## Контекст

§12 правило 3 API_RUN_MASTER: «Ни одной цифры в `given`, `find`,
`econ_concepts`, `plot`, поисковых запросах» — проверка кодом, а не просьбой в
промпте. Правило правильное: цифра из условия, попавшая в поисковый запрос,
превращает смысловой поиск в поиск по конкретной задаче.

На контрольной точке цифра в `search_queries` оказалась **самой частой
причиной повтора — 71 случай из 142 задач**.

## Решение

**Запрос с цифрой выбрасывается из массива до проверки, остальные остаются.**

- осталось 5 и больше — вызов считается прошедшим, выброшенные пишутся в
  журнал полем `dropped_queries` с текстом каждого;
- осталось меньше 5 — мягкое нарушение (`soft_violations`), повтора нет.

Ноль обращений к API, ноль потерянных задач.

## Почему так

Причина отказов была **структурная, а не содержательная**. Проверка «нет
цифр» применялась ко всему массиву целиком, и один плохой запрос из восьми
убивал вызов, где семь были в порядке. Вероятность отказа при этом растёт
почти линейно по числу запросов: восьмикратный усилитель на ровном месте.
Платили повторным вызовом за семь правильных ответов вместе с одним
неправильным.

Само правило при этом **не ослаблено ни на йоту**. Цифра в поисковом запросе
по-прежнему недопустима и в банк не попадает — меняется только реакция:
выбросить один запрос вместо оплаты повторного вызова. Проверка
`search_queries[i] содержит цифру` в `validate_call2` осталась на месте как
последняя линия обороны и как источник инварианта §11 «цифры в запросах = 0».

Для `given` и `find` правило остаётся **жёстким**: там цифра ломает
структурный отпечаток задачи, ради которого поля и заведены, и выбрасывать
там нечего — поле одно, а не массив.

## Что именно изменилось в коде

`drop_digit_search_queries()` и `make_query_sanitizer()` в
`problems/management/commands/pilot_enrich_v2.py`. `call_with_retry()`
принимает `sanitize_fn` и зовёт его на **каждой** попытке — иначе повтор
проверялся бы по другим правилам, чем первая попытка.

## Две вещи, которые пришлось починить попутно

**Журнал снова хранит сырой ответ.** `run_raw.jsonl` для финальной попытки
писал `row['call1']`/`row['call2']` — то есть результат нашей постобработки.
С появлением выброса запросов журнал перестал бы быть сырым: восстановление
метрик из него не увидело бы **ни одного** выброшенного запроса, потому что
выбросили их до записи. Теперь в журнал идёт разбор `reply.text`, а
постобработку (`strip_given_find_prefixes`, `drop_digit_search_queries`)
повторяет читающий код. Восстановление метрик стало чистой функцией журнала.
Это тот же класс бага, что уже был с `images_sent` (журнал молчал — считали,
что картинок не было).

**Не-строка в массиве роняла проверку.** `_DIGIT_RE.search(42)` — это
`TypeError`, а не нарушение: задача целиком уходила в `errors` и терялась.
У Z.AI нет строгой схемы, число вместо строки — реальный сценарий. Теперь
текстовые правила пропускают не-строки, а тип ловит `check_against_schema`,
как и должен.

## Проверяется

`problems/tests/test_pilot_enrich_v2.py::DropDigitSearchQueriesTests` —
зубастость дословно из задания: массив из восьми, где два с цифрами → на
выходе шесть и вызов прошёл; массив из шести, где четыре с цифрами → на
выходе два, мягкое нарушение, повтора нет. Плюс сквозные тесты команды в
`test_glm_enrich_run.py`, включая проверку, что журнал остался сырым.

## Результат

На тех же 142 задачах брак упал **4,2 % → 2,1 %** одним этим изменением,
пересчётом по уже оплаченному журналу, без единого обращения к API.

На полной контрольной точке 300/300: выброшено 58 запросов у 41 задачи
(13,7 %), из них у 30 задач осталось меньше пяти запросов — мягкое
нарушение, повтора не было.
