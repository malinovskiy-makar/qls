# ADR 0011. Кэш и сессии на Redis: разные базы, движок `cached_db`

**Источник:** сессия «мины 2 и 3», 21.08.2026, ветка
`feat/redis-cache-sessions`.

## Контекст

Разбор боевого сервера нашёл три дефекта, невидимых, пока приложение
запущено в один процесс, и опасных, как только воркеров становится девять.
Этот ADR закрывает два из них.

**Мина №2 — кэш не общий между воркерами.** `CACHES` был одним
`LocMemCache`, то есть памятью процесса. Девять воркеров — девять
независимых кэшей. Следствия: попадание примерно один раз из девяти;
счётчик неудачных входов у каждого воркера свой, то есть попыток до
запрета в девять раз больше объявленного; сброс кэша доходит до одного
воркера из девяти.

**Мина №3 — сессии в базе.** `SESSION_ENGINE` не был задан вовсе, то есть
работало умолчание Django — `django.contrib.sessions.backends.db`. Каждое
чтение сессии — отдельный запрос в PostgreSQL, на каждый запрос каждого
вошедшего человека.

Мина №1 (модель поиска весом 2,12 ГБ в каждом воркере) в эту работу не
входила и остаётся открытой.

## Решение

### 1. Раскладка баз Redis — соглашение проекта

| База | Что там живёт |
|---|---|
| 0 | кэш приложения (алиас `default`) |
| 1 | сессии (алиас `sessions`) |
| 2 | брокер Celery — зарезервировано |
| 3 | channel layer для WebSocket — зарезервировано |
| 14 | сессии во время прогона тестов |
| 15 | кэш во время прогона тестов |

Единственная точка правды — словарь `CACHES` в `config/settings.py`.

### 2. Кэш и сессии — в РАЗНЫХ базах и под разными алиасами

`cache.clear()` у Redis-бэкенда Django — это `FLUSHDB`: он вычищает базу
Redis **целиком**, а не только ключи своего алиаса. В наборе тестов
`cache.clear()` зовётся в 18 местах, и на сервере он тоже может
понадобиться. Лежи сессии в той же базе — любой сброс кэша разлогинил бы
всех до одного.

В разработке без Redis у двух `LocMemCache` заданы **разные** `LOCATION`.
Одинаковое имя у `LocMemCache` — это один и тот же склад под двумя
вывесками, то есть та же беда, только локально.

### 3. Движок сессий — `cached_db`, а НЕ чистый `cache`

Это главный выбор этого ADR, и он не самоочевиден.

У Redis на сервере потолок памяти 512 МБ и политика вытеснения
`allkeys-lru`: под нагрузкой он выбрасывает **любые** ключи, включая
сессии. При движке `cache` источник правды — сам Redis, и выброшенный ключ
означает человека, разлогиненного посреди работы, без единой записи в
журнале о том, почему.

У `cached_db` источник правды — таблица `django_session`, Redis только
ускоряет чтение. Вытеснение стоит одного запроса в базу, а не потери
сессии.

Смены движка **миграций не требует**: таблица та же самая, старые записи
в ней остаются рабочими.

### 4. Отсутствие `REDIS_URL` в боевых настройках — падение при старте

`config/settings_production.py` возбуждает `ImproperlyConfigured`, если
переменной нет. Без предохранителя `config/settings.py` молча подставил бы
`LocMemCache`, сайт бы поднялся, страницы бы открылись — и мина №2
вернулась бы целиком, никак себя не проявив. **Тихая деградация хуже
падения:** падение чинят в тот же час, деградацию ищут неделями по
жалобам.

В разработке отсутствие `REDIS_URL` — не ошибка, но печатается
предупреждение в stderr.

### 5. Инвалидация индекса поиска — через общий маркер версии

Перехода на Redis мало. Индекс семантического поиска
(`catalog/semantic._index`) — переменная уровня модуля, то есть память
процесса. `invalidate_index()` очищал её только в том воркере, который
обработал запрос; остальные восемь продолжали бы отвечать по устаревшему
индексу, и снаружи это почти незаметно — поиск работает, просто выдаёт
старое.

Введён общий маркер версии в кэше — ключ `semantic:index_version`.
`invalidate_index()` записывает туда новое значение; перед выдачей индекса
процесс сверяет свой маркер с общим и пересобирает индекс, если они
разошлись. Цена — один `cache.get` на поисковый запрос.

**Маркер — случайный `uuid4`, а не счётчик.** Причина — та же `FLUSHDB`:
`cache.clear()` уносит и сам ключ версии. Если после этого каждый процесс
запишет одно и то же значение (скажем, «1»), то воркер, у которого
локально уже лежала «1», решит, что ничего не изменилось, и останется со
старым индексом — то есть ровно с той бедой, ради которой всё заведено.
Случайный маркер не совпадает ни с чьей локальной версией, поэтому
пересобираются все. Восстанавливается ключ через `cache.add`, а не
`cache.set`: при одновременном обращении нескольких воркеров выигрывает
первый, и все сходятся на одном значении за один круг, а не пересобирают
индекс бесконечно.

Отсутствие ключа означает «перестроить», никогда — «версия 1». Вытеснение
маркера по `allkeys-lru` поэтому безопасно: оно стоит лишнего пересчёта,
но никогда не даёт выдачу устаревшего.

## Отвергнутые варианты

**Сессии на чистом `cache` (Redis как источник правды).** Быстрее всего:
ни одного запроса в базу. Отвергнут из-за `allkeys-lru` — см. выше. Менять
политику вытеснения на `volatile-lru` ради этого тоже отвергнуто: тогда
переполнение памяти начинает валить запись в кэш вместо того, чтобы
вытеснять, и вместо разлогина получаем пятисотки.

**Сессии и кэш в одной базе Redis, разведённые только `KEY_PREFIX`.**
Отвергнут: префикс не спасает от `FLUSHDB`. Разделение, которое держится
на том, что никто не вызовет `cache.clear()`, — это не разделение.

**Счётчик версии индекса через `cache.incr`.** Отвергнут: `incr` требует
существующего ключа и после `cache.clear()` возбуждает `ValueError`, а
восстановление счётчика единицей возвращает исходную беду (см. выше).

**Оставить `LocMemCache` и «просто не ставить девять воркеров».**
Отвергнут: тогда потолок нагрузки задаётся дефектом, а не мощностью
сервера.

**`django-redis` вместо встроенного бэкенда Django.** Пакет уже стоит в
`requirements/base.in`, но не используется. Встроенный
`django.core.cache.backends.redis.RedisCache` появился в Django 4.0 и
закрывает всё, что здесь нужно; лишний слой между кодом и Redis добавлял
бы своё поведение к `clear()` и своим умолчаниям. Снятие `django-redis`
из зависимостей — отдельная работа, в эту сессию не входила.

## Чем держится

`config/tests/test_cache_and_sessions.py` — 22 проверки. Главные:

- сброс кэша не уносит сессию (мина №3), в том числе через настоящий вход;
- `invalidate_index()` доходит до «второго процесса», и `cache.clear()`
  тоже помечает индекс устаревшим (мина №2);
- боевые настройки без `REDIS_URL` возбуждают `ImproperlyConfigured`;
- прогон тестов уводится на базы 15 и 14;
- в CI переменная `REDIS_URL` обязана быть задана — иначе проверки Redis
  тихо пропускались бы, и джоб был бы зелёным по непроверенному пути.

Каждая проверка проверена мутацией: дефект возвращался руками, тест
краснел.
