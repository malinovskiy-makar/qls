# ADR 0095. Реестр миграций, разошедшийся со схемой, заливает в данные имена колонок

**Дата:** 2026-09-07
**Статус:** принято
**Автор решения:** Claude Code; владельцу — карточка в Notion

## Контекст

У 882 задач в полях `title_candidate` и `title_source` вместо значений стояли
их собственные имена: буквально `title_candidate = 'title_candidate'`. Это не
косметика. Число «`title_candidate` заполнен у 41 307 из 41 307», которым
пользовались как доказательством стопроцентного покрытия, было ложью на 882
задачи; массовая замена заголовков кандидатом дала бы 882 карточки с
заголовком «title_candidate» на сайте; а формула отпечатка v2 отправила бы
слово `title_candidate` в поисковый вектор.

## Механизм — воспроизведён, а не предположен

Django при `AddField` на SQLite пересоздаёт таблицу и переносит данные:

```sql
INSERT INTO new_table (…, "title_candidate", …)
SELECT …, "title_candidate", … FROM old_table
```

Список колонок берётся из **состояния модели**, а не из физической таблицы —
`django/db/backends/sqlite3/schema.py`, `_remake_table`:

```python
mapping = {f.column: self.quote_name(f.column)
           for f in model._meta.local_concrete_fields if f.generated is False}
```

Если такой колонки в старой таблице нет, SQLite не падает: двойные кавычки,
не разрешившиеся в идентификатор, он по своему legacy-правилу считает
**строковым литералом**. В каждую строку молча уезжает имя колонки.

Воспроизведение — пять строк SQL, тест
`problems/tests/test_field_name_values.py::SqliteRemakeTableTests`.

## Как возникло условие срабатывания

Реестр миграций разошёлся со схемой. В бэкапе 07.09 05:50 у
`problems_problem` **29 колонок**, `title_candidate`/`title_source` нет вовсе
(база пришла дампом боевого сервера, где их и не было), а в
`django_migrations` миграция `0049_title_candidate_source` значится
применённой 31.08. Журнал `migrate` той ночи применяет 0050, 0051, 0055, 0056
и **не** применяет 0049 — Django считал её сделанной. Первая же перестройка
таблицы залила имена колонок во все 41 307 строк (бэкап 05:56 это и
показывает); мерж обогащения переписал 40 425, осталось 882 — ровно те, кого
прогон не трогал.

## Решение

1. **Поля очищены** обратимой командой `clear_field_name_values` (снимок +
   `--revert`). После чистки `title_candidate` непусто ровно у 40 425 задач.
2. **Заведён сторож** на ЧЕТЫРЕ коротких текстовых поля раскладки
   (`title_candidate`, `title_source`, `enrichment_source`, `text_quality`), а
   не на одно пострадавшее: повтор той же ошибки на соседнем поле не должен
   пройти молча. Состав списка закреплён отдельным тестом — иначе сужение
   списка обессмысливало бы перебор, оставляя его зелёным.
3. **Счётчик покрытия «поле непусто» признан негодным** для полей, которые
   заполняет прогон: `'title_candidate'` — непустая строка. Проверять надо
   «поле не равно своему имени», и это записано в сторож.

## Что отвергнуто

**Чинить только `title_candidate`.** Пострадали два поля, но механизм не знает
про заголовки: он сработает на любой колонке, которой нет в таблице при
следующей перестройке. Сторож на одно поле — это сторож, который в следующий
раз промолчит.

**Заводить в этой сессии проверку «схема базы против реестра миграций».** Она
нужна, и без неё условие срабатывания может возникнуть снова при следующей
заливке дампа. Но это работа про `migrate` и заливку, а не про заголовки, и
делать её мимоходом в чужой сессии — ровно то «заодно», которое запрещено
корневым `CLAUDE.md`. Владельцу заведена карточка.

## Последствия

- Заливка дампа боевого сервера в рабочую копию **обязана** сопровождаться
  сверкой схемы с состоянием миграций. Пока сверки нет, `migrate` после такой
  заливки может молча испортить данные, а не упасть.
- Любой отчёт вида «поле заполнено у N задач» по полям обогащения читается
  вместе со сторожем имён полей, иначе N завышено.
