# ADR 0069. Решение подаётся в вызов 1; уровень рассуждения GLM — 'high', не 'medium'

**Дата:** 2026-09-04
**Статус:** принято
**Автор решения:** владелец; реализация — Claude Code

## Контекст 1: решение в вызове 1

§3.4 `API_RUN_MASTER` («Решение НЕ подаётся в вызов 1») запрещал это явно:
решение не нужно ни для одного из восьми полей вызова 1, а стоит 322 символа
входа на задачу — на корпусе это 41 307 × ~115 токенов × $2/млн = **$9,5
выброшенных денег** (расчёт по цене Terra, $2/млн за вход).

Готовя второй боевой прогон, владелец указал: расчёт устарел. Боевой прогон
идёт на GLM-5.3-Flash по $0,075/млн за вход — та же величина стоит уже не
$9,5, а **36 центов на весь корпус** (около 10 центов для 11 467 задач, у
которых решение вообще есть). Аргумент, на котором стояло решение «не
подавать», обесценился в тридцать раз.

Решение показывает, каким аппаратом задача берётся — ровно то, что
спрашивают теги, понятия и особенности. Капкан, в который уже попадали:
особенность «Графическое решение» определена ЧЕРЕЗ решение
(`graphical_solution_signal`), а спрашивалась в вызове 1, где решения не
было — рассинхрон между тем, что просят определить, и тем, что дают для
определения.

## Решение 1

`problems.enrich.text.solution_hint_for_call1(solution)` — блок решения в
пользовательский текст вызова 1, **только если решение есть**:

* потолок **800 токенов** (тот же порядок, что у чертежа, §3.5), длиннее —
  обрезка с явной пометкой `[…РЕШЕНИЕ ОБРЕЗАНО ПО ПОТОЛКУ N ТОКЕНОВ…]`;
* рядом с блоком — жёсткая формулировка: `given` не берёт величины,
  выведенные в решении; `find` не берёт то, что найдено, вместо того, что
  нужно найти;
* блок дописывается ПОСЛЕДНИМ в `prompts_v2.call1_user_text`, не трогая
  формат «шорт-лист → задача».

**Защита от утечки — двойная.** Текстовая формулировка — первая линия;
вторая, структурная — общий запрет ЛЮБОЙ цифры в `given`/`find` (§12.3,
`pilot_enrich_v2.validate_call1`), который уже существовал ДО этой фазы и
ловит утечку числа из решения как жёсткое нарушение (повтор вызова)
независимо от того, откуда цифра взялась. `SolutionLeakGuardTests`
закрепляет именно этот сценарий.

## Контекст 2: уровень рассуждения

Первый прогон шёл на `low`. Сравнение с gpt-5.6-sol (`medium`) дало 23:5 в
пользу sol, но условия были неравные (sol — `medium`, GLM — `low`). Задание
сессии просило поставить `medium` для GLM тоже, по аналогии.

Разбор показал: **Z.AI для GLM-5.3-Flash реально принимает
`reasoning_effort` только из `{low, high, max}`** — подтверждено официальной
документацией Z.AI и текстом самой ошибки API, уже процитированным в
`providers.py` («This model always engages in thinking… please use low,
high, or max»). `medium` у этой модели не существует физически. Код
`GLMProvider.complete()` уже тогда тихо подменял любое значение не из этой
тройки на `'low'` — `medium` прошёл бы **без единого предупреждения**,
полностью обесценив цель фазы.

Вопрос задан владельцу напрямую (см. протокол сессии — не додумано молча).

## Решение 2

`GLM_VARIANT['call1_effort']` и `['call2_effort']` — **`'high'`**, не
`'medium'` (не существует) и не `'max'` (дороже без замера пользы, `'high'`
— следующая ступень вверх от `'low'` первого прогона).

## Побочная находка: `reasoning_tokens` не читался вовсе

Смок-тест Фазы 6 (задачи 1/13/57130/57144/57149, `effort='high'`) показал
`reasoning_tokens=0` на всех десяти вызовах подряд. Прямой вызов API
подтвердил, что рассуждение реально происходит (41 токен рассуждения на
контрольном запросе), но `GLMProvider._reply_from()` никогда не читал поле
usage, где оно лежит: у Z.AI это `completion_tokens_details.reasoning_tokens`
— другая схема, чем `output_tokens_details` у OpenAI Responses API.
Исправлено отдельно (`problems/ai/providers.py`), закрыто тестом
`GLMReasoningTokensTests`. Значит `reasoning_tokens` в журнале ПЕРВОГО
прогона был тихо нулевым на каждом вызове — это не меняет корректность
самого обогащения (рассуждение происходило и оплачивалось), но обесценивало
любую метрику, построенную на этом поле.

## Что было отвергнуто

**Оставить `low`.** Не решает задачу фазы — сравнение с sol оставалось бы
нечестным, а рассуждение — минимальным из доступного.

**`max` вместо `high`.** Дороже без измеренного выигрыша в качестве; `high`
— осторожный шаг вверх, соответствующий духу «средний, не высокий» из
первоначального задания, адаптированному под реальные значения API.

## Проверка

* `problems/tests/test_pilot_enrich_v2.py::SolutionHintForCall1Tests`,
  `Call1UserTextSolutionBlockTests`, `SolutionLeakGuardTests` — блок решения,
  потолок, защита от утечки.
* `problems/tests/test_glm_enrich_run.py::GlmVariantReasoningEffortTests` —
  `GLM_VARIANT` на `'high'`.
* `problems/tests/test_ai_providers.py::GLMReasoningEffortTests`,
  `GLMReasoningTokensTests` — параметр `reasoning_effort` (не
  `reasoning.effort`), 'medium' молча превращается в 'low' (задокументировано,
  не открытие теста), `reasoning_tokens` читается из `completion_tokens_
  details`.
* Смок-тест на пяти реальных задачах (API): решение ушло в вызов 1 у 4/5,
  обрезано у одной (2520 символов); `given`/`find` без единой цифры; число
  подсказок точно по правилу Фазы 3 на всех четырёх задачах с решением;
  `reasoning_tokens` 145–678 на вызов после фикса; свип-детектор — 0
  расхождений; инвариант «пустое поле» — 0 из 5. Стоимость двух прогонов —
  $0,0151.
