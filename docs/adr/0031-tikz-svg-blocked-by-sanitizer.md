# ADR 0031 — TikZ/PGFPlots → SVG откладывается: рендерить некуда

**Дата:** 2026-08-27
**Статус:** принято (стоп-гейт, требуется решение владельца)
**Контекст:** Фаза 3 сессии «боевой рендер», ветка `feat/corpus-converter-render`

## Задача

Аудит (`weconomics_converter_render_audit.md`, раздел 5) нашёл 825 сырых
TikZ/PGFPlots-команд в 31 карточке из 846: вместо графика ученик видит код.
Владелец решил делать компиляцию графиков в SVG сейчас, а не откладывать.
Бриф прямо разрешил остановиться, если песочница на локальной машине
окажется по-настоящему рискованной, — «честный стоп-гейт важнее выполнения
инструкции».

## Что замерено

Песочница оказалась **выполнимой**, и это проверено, а не предположено:

| Проверка | Результат |
|---|---|
| MiKTeX `latex` + `tikz` + `pgfplots` без сети (`-disable-installer`) | компилируется, exit 0 |
| `dvisvgm` → SVG | работает, 14 КБ SVG за 1,3 с |
| Полный цикл на страницу | ≈ 3 с (1,8 с latex + 1,3 с dvisvgm) |
| Бесконечный цикл `\loop … \repeat` под таймаутом 10 с | убит, exit 124, **процессов-сирот не осталось** |
| Исчерпание памяти (рекурсивные `\def`) | TeX прерывается САМ за 1 с (внутренний лимит `main_memory`) |
| `-no-shell-escape` | `\write18` заблокирован |

То есть три из четырёх требований брифа (таймаут, отсутствие сети,
запрет shell-escape) выполнимы, а лимит памяти на Windows недоступен
средствами ОС (`setrlimit` — Unix-only, нужны Job Objects), но
компенсируется внутренним лимитом самого TeX — замерено выше.

## Настоящий блокер — не песочница

**Скомпилированный SVG физически некуда положить.** Конвейер показа
`problems/rendering.py` пропускает разметку через `nh3` со строгим
allow-list, и в нём нет ни `img`, ни `svg`, а `attributes={}` снимает
вообще все атрибуты с любого тега. Замерено:

```
allowlist: br, code, em, li, ol, p, pre, strong, table, tbody, td, th, thead, tr
render_markdown('<img src="/media/plot.svg">')
    -> '<p>&lt;img src="/media/plot.svg"&gt;</p>'      (экранировано в текст)
render_markdown('![график](/media/plot.svg)')
    -> '<p>![график](/media/plot.svg)</p>'             (правило image даже не включено)
```

Даже если бы `img` попал в allow-list, `attributes={}` срезал бы `src`.

Значит компилятор графиков сегодня произвёл бы артефакт, который
невозможно показать. Дописать его «на всякий случай» и отчитаться о
готовности — ровно тот сценарий, из-за которого прежний шлюз считал
себя готовым, а аудит потом нашёл 43,5 % сломанных карточек.

## Решение

**Компилятор TikZ→SVG в этой сессии не пишется.** Вместо него карточки
с сырым TikZ/PGFPlots получают машинный код `PLOT` в новом шлюзе и
остаются на `content_format='plain'`, попадая в очередь ручного
разбора. Это не регресс: сейчас они и так на `plain`.

## Что нужно от владельца, чтобы разблокировать

Два пути, и выбор между ними — решение владельца, а не Claude Code:

1. **Отдельный блок шаблона для графиков (рекомендуется).** Картинка
   хранится в `FileAsset`, шаблон задачи рисует её собственным тегом
   ВНЕ санитайзера markdown. Граница XSS остаётся нетронутой: allow-list
   не расширяется, а изображение приходит из базы, а не из текста задачи.
2. **Расширение allow-list `nh3` до `img` с атрибутом `src`.** Проще в
   реализации, но это изменение границы безопасности показа: любой текст
   задачи получает право вставлять изображение по произвольному URL
   (трекинг-пиксели, внешние запросы из браузера ученика). Требует
   отдельного разбора по `weco-security-boundary-review`.

После выбора пути компиляция добавляется отдельной сессией — её
техническая часть уже проверена цифрами выше, переизобретать не придётся.

## Отвергнуто

- **Показывать сырой TikZ-код в раскрываемом блоке** — аудит прямо
  против: «Исходный код можно оставить только в раскрываемом техническом
  блоке, но не вместо визуального результата». Сейчас ученик видит именно
  код, и это тот дефект, который чинят.
- **Расширить allow-list молча, раз это «всего один тег»** — граница
  безопасности показа меняется решением владельца, не по ходу дела.
