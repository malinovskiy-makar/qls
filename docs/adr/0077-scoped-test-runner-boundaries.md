# ADR 0077. Быстрый круг тестов (`--scope-from-git`): где узит, где нет, и почему рабочие деревья не делят Postgres

**Нумерация:** файл перенумерован из 0017 при синхронизации веток 05.09.2026 (номер был занят)

**Источник:** сессия «быстрый круг тестов», 25.08.2026, ветка
`feat/scoped-test-runner` (рабочее дерево `qls-scoped-tests`, отдельное от
`C:\Users\shipu\qls`, где параллельно шла сессия рендерера Markdown —
[docs/TESTING.md](../TESTING.md), «Быстрый круг сессии»). Задача — Notion,
https://app.notion.com/p/3c7b11c92bc18131be47c10eb55aa7d8; каденция
(быстрый круг во время работы, ПОЛНЫЙ прогон один раз перед сдачей) —
решение от 21.08, https://app.notion.com/p/3c3b11c92bc181deb4b9d5feeb41f6cf,
этой ADR не трогается.

## Контекст

Нужен детерминированный способ по списку изменённых путей получить набор
тестовых лейблов `manage.py test`. Задача сама предложила эвристику: если
задет `problems/` — сузить нельзя (там модели всего проекта), кроме
`problems/management/commands/`, «если она реально изолирована» — и явно
попросила это проверить кодом, а не поверить на слово.

## Решение 1: `problems/` — блэнкет, но с узкими исключениями внутри

Код-чек (`grep -rn "from problems" catalog student teacher game calc2` +
обратный обход) подтвердил: `catalog`, `student`, `teacher`, `game`,
`calendar_stub` реально импортируют `problems` напрямую; `calc2` — нет, ни
в одну сторону. Значит правка `problems/models.py`, `rendering.py`,
`hw_generator.py` и т.п. уходит в лейблы `problems` + все пятеро
(`scripts/scope_from_git.py`, `BLANKET_PROBLEMS_DEPENDENTS`).

Но `problems/management/commands/` — 150+ разовых скриптов импорта и
починки, и по факту наружу используется ровно один —
`apply_topic_mapping.py` (`CANONICAL`, читают `catalog`, `teacher`, `game`).
Блэнкет здесь убил бы весь смысл быстрого круга: это самая часто правимая
директория в проекте. То же нашлось у `problems/tests/` — снаружи нужен
только `problems/tests/factories.py` (`catalog/tests` собирает через него
тестовые задачи).

**Решение: два поддерева-исключения, сопоставление в них — узкое**, по
факту прямых импортов (`build_reverse_import_index` сканирует все семь
приложений один раз за прогон, ищет `from <модуль> import`/`import
<модуль>`). Если для конкретного файла зависимых не нашлось — лейбл только
`problems`.

**Отвергнуто:**
- **Захардкоженный список известных исключений** (`apply_topic_mapping.py`
  → catalog/teacher/game, и т.п.). Работал бы сегодня и протух бы завтра:
  список не обновляется сам при переезде импортов, а git-hook на каждое
  изменение списка никто не заведёт. `build_reverse_import_index`
  пересчитывается заново на каждом прогоне — не может протухнуть.
- **AST-разбор вместо текстового поиска импортов.** Точнее (поймал бы
  `import problems.models as m; m.Problem`), но не ловит главную дыру
  ВСЁ РАВНО: `ForeignKey('problems.X', ...)`, сигналы по строке, миграции —
  связи НЕ через `import`. Раз транзитивные Django-связи всё равно не
  видны текстовым поиском, усложнение AST не окупается — отсюда и
  блэнкет-режим для `problems/` вне двух исключений (см. docstring
  `scripts/scope_from_git.py`).

## Решение 2: `docs/` — НЕ блэнкет, только `docs/TESTING.md`

Первая версия отправляла ЛЮБУЮ правку `docs/*.md` в полный набор («сигнал
широкого эффекта» по тексту задачи). Проверка зубастости (шаг 2 — правка
`docs/DATA.md`, документация по данным, к тестам отношения не имеющая)
поймала это как ложную тревогу: `docs/DATA.md` тестового следствия не
имеет вообще, а не «полный набор впрок». Оставлен точечный триггер —
`docs/TESTING.md` (сам описывает методику прогона) — и `CLAUDE.md`
(governance) наравне с `config/`, `manage.py`, `requirements/*`,
`docker-compose*.yml`, корневыми `templates/*.html`.

## Решение 3: рабочие деревья не делят Docker-стенд

`git worktree` — правильный способ работать двум сессиям Claude Code в
одной папке одновременно (P0-правило CLAUDE.md), но он делит **`.git`**, а
не «всё окружение». `docker-compose.dev.yml` — единственный контейнер
Postgres на 55432, общий на всю машину независимо от рабочего дерева. Два
`manage.py test --settings=config.settings_test_pg` одновременно (эта
сессия + сессия рендерера Markdown) наперегонки создают/клонируют/сносят
`test_qls` — то же «Правило 3» из решения от 21.08 («параллельных
прогонов не запускать»), но теперь оно бьёт через границу рабочих
деревьев, которую сам git не видит.

**Решение:** `docker-compose.scoped-tests.yml` — второй, полностью
изолированный стенд (Postgres+Redis) на портах 55433/56380, свои
контейнеры и тома, специально для этого рабочего дерева.

**Отвергнуто:**
- **Общий Postgres + координация по времени** (спрашивать владельца перед
  каждым прогоном, не идёт ли тест в соседней сессии). Хрупко, перекладывает
  бремя на человека при каждом запуске.
- **SQLite для быстрого круга.** Рассматривался, но собственный Postgres
  дешевле координации и не проигрывает в скорости (docker-compose поднимает
  контейнер за секунды, healthcheck ждёт готовности).

## Отдельная, ещё не закрытая находка

Полный двухшаговый прогон (10–25 мин, `--parallel auto`) в фоне — даже
против ПОЛНОСТЬЮ изолированного стенда — иногда получает вперемешку строки
в формате `scripts/test_timing.py` из процесса, которого не видно в списке
процессов ни до, ни после. Короткие/средние прогоны (до ~3,5 мин, включая
браузерный `calc2` шаг B) — чистые, воспроизводимо, несколько раз подряд.
Причина не установлена (не общая БД — проверено; не длина команды, не
`--summary`/фон по отдельности — короткие прогоны в тех же режимах
чистые). Полный прогон без флага пока не подтверждён численно в этом
рабочем дереве — см. docs/TESTING.md, «Проверка зубастости», пункт 4.
