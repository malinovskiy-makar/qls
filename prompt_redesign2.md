## Этап 1. Фундамент данных: вид ответа, статус ученика, уровень темы

### Фаза 1.1 — Аудит корпуса (только чтение) и разбор ответов
- Команда `problems/management/commands/audit_answer_kinds.py` (только чтение, никаких записей): по видимым задачам считает распределение видов ответа по правилу ниже и печатает: сколько тестов, сколько «число» (из них с подпунктами), сколько «качественная», сколько «файл», сколько «без ничего» (нет ни числа, ни разбора, ни вариантов); плюс 30 случайных числовых ответов в исходной записи и в разобранном виде, и 20 ответов, которые в число НЕ разобрались, с причиной. Вывод — в журнал целиком. Это первый инвариант этапа: доли должны быть правдоподобны (тестов около 1 465 из 5 090 — известно из фильтров).
- `problems/answer_check.py`: функции `numeric_answer(text) -> Decimal | None` и `answer_kind(problem) -> 'test' | 'number' | 'qual' | 'file'`.
  - `numeric_answer`: принимает «1800», «1 800», «1800 руб.», «1800р», «20 %», «0,5», «-0.5», «1/3» (как 0.3333…), «2 тыс.» (2000), «≈ 40», «40 (ед.)»; отвергает «P = 40 − 0,5Q», «да», «60; 30; 1800» (несколько чисел без подпунктов → не число), «x = 3 или x = 5». Правило: из строки вырезаются единицы и служебные слова из фиксированного списка, затем в ней должно остаться ровно одно число. Если исходная запись содержит «%», сохраняется признак `percent`.
  - `answer_kind`: тест → `problem_type` начинается с «тест» и есть варианты; иначе «число» → у задачи без подпунктов `numeric_answer(problem.answer)` не пуст, у задачи с подпунктами — у каждого подпункта с непустым ответом число (подпункты с пустым ответом не считаются полями); иначе «качественная» → `problem.character == 'qual'`; иначе «файл».
  - Сравнение `numeric_match(user, ref, percent)`: относительный допуск 0,5 % и абсолютный 0,005 для чисел меньше 1; если эталон в процентах — принимаются и «20», и «0,2».
- Тесты: все записи выше как параметризованный тест; десять задач из аудита с известным исходом (взять реальные тексты ответов в фикстуру); зубастость.

### Фаза 1.2 — Статус задачи у ученика и уровень темы
- Модели в `problems/models.py`:
  - `UserProblemStatus`: `user`, `problem`, `status` (`tried` / `solved` / `opened`), `first_try_correct` (Bool null — нет результата), `attempts` (int), `best_score` (int null), `first_at`, `last_at`, `solved_at` (null). Уникальность (user, problem). Строки нет = «не трогал».
  - `TopicProgress`: `user`, `topic`, `attempted` (задач с любой попыткой), `with_result` (задач с известной первой попыткой), `first_try_correct` (число), `solved`, `level` (`none` / `work` / `weak` / `sure`), `last_at`. Уникальность (user, topic).
  - Чекпоинт → `makemigrations problems` → текст в отчёт → `migrate`.
- Сервис `problems/progress.py` с одной точкой входа `record(user, problem, *, kind, correct=None, score=None, opened=False, first=None)`, которую вызывают все проверки: число (по каждому подпункту отдельно, задача «решена», когда все подпункты верны), тест, файл/текст/строка (решено при `score >= 8`), открытие решения, ответы в домашках (при выставлении оценки в `Submission` — верно при ≥ 80 % максимума), ответы в Wecon Rush (первый ответ игрока по вопросу — как первая попытка). Правила:
  - первая попытка фиксируется один раз: `first_try_correct` ставится при первом результате и больше не меняется;
  - `opened` до первого результата ставит `status='opened'` и `first_try_correct=False` («подглядывание — ошибка в доле», решение владельца);
  - после `solved` статус не понижается;
  - для каждой темы задачи пересчитывается `TopicProgress` (одним запросом по статусам темы, не инкрементами — так нельзя разойтись);
  - уровень: `none` — `attempted == 0`; `weak` — `with_result >= 5` и доля верных первых < 40 %; `sure` — `solved >= 5` и доля ≥ 80 %; иначе `work`. Уровень блока — теми же порогами по сумме тем блока, считается на лету из `TopicProgress` (пять сумм, без таблицы).
- Команда `rebuild_progress` (сухой прогон / `--apply`): пересобирает `UserProblemStatus` и `TopicProgress` из истории — `CatalogAttempt` (по времени, первая попытка = самая ранняя), `Submission` с оценками, результаты игры (если хранятся по игроку и вопросу — посмотреть в `game/`, если нет — пропустить с записью в отчёт). Идемпотентна: второй прогон ничего не меняет. Инварианты: после пересборки на локальной базе число строк статусов = число пар (пользователь, задача) в источниках; журнал.
- Гость: попытки числа и тестов живут в `request.session['catalog_guest']` по ключу задачи (`attempts`, `solved`, `first_correct`) — только для отображения на странице; в уровни не идут; при входе не переносятся.
- Тесты: сценарии таблицей — «число верно с первой» → `solved`, `first_try_correct=True`; «неверно, потом верно» → `solved`, `first_try_correct=False`; «открыл решение, потом верно» → `opened`→`solved`, `first_try_correct=False`; подпункты: два из трёх верно → `tried`; «файл 8/10» → `solved`; «файл 6/10» → `tried`; уровни на фикстуре 6 задач: 5 верных первых из 6 → `sure`, 1 из 6 → `weak`, 3 из 6 → `work`, 2 попытки без результата → `work`, ничего → `none`. Зубастость.

## Этап 2. Страница задачи: карточка «Ответ» по данным, контекст, статус, плашка чата
Спецификация — `problem_page_v2_mockup.html`. Текущая страница — из этапов 4–7 первого редизайна (`problem_detail.html`, партиалы попытки, подсказок, теста). Карточка `.sv` с большим текстовым полем заменяется карточкой `.ans`.

### Фаза 2.1 — Эндпоинты ответа
- `POST /catalog/api/answer/<problem_id>/` JSON `{"part": "<метка или null>", "value": "<строка>"}` — число. Гость допускается. Ответ: `{"correct": bool, "attempt": n, "first_try": bool|null, "solved_all": bool, "parts": {"а": "ok"|"bad"|"open", …}, "status_html": "<партиал статуса>", "done_html": "<партиал завершения или ''>"}`. Проверяет через `numeric_match`, пишет `progress.record` (или сессию гостя). Задача с `answer_kind != 'number'` → 400 с человеческим текстом.
- `POST /catalog/api/answer-string/<problem_id>/` JSON `{"value": "..."}` — строка формулой/словом, только вход: профиль `catalog_answer_string` в `problems/ai/prompts.py` (сравнить ответ ученика с эталонным ответом задачи; схема `{match: bool, comment: str}`; наружу — только условие, эталонный ответ и строка ученика), лимит общий с остальными вызовами. Ответ `{"correct", "comment", "status_html", "done_html"}`. Верно → `record(kind='string', correct=True, score=10)`.
- Существующие эндпоинты попытки (файл/текст), подсказок, теста — остаются; в них добавляется вызов `progress.record` (файл/текст — по баллу, тест — по факту, показ ответа теста — как `opened`).
- Эндпоинт «дальше»: `GET /catalog/problem/<id>/next/?track=<id>&pos=<n>` и `?session=topic:<topic_id>` → редирект на следующую задачу (дорожка: следующая позиция; сессия: следующая нерешённая темы по порядку дорожки, а если дорожки нет — по ключу сортировки из фазы 4.3); нечего дать → редирект на тему с `?done=1`, экран темы показывает «Все задачи темы решены» только при этом параметре И реальном факте.
- Тесты: число верно/неверно/подпункты; строка с фейковым поставщиком; гость → сессия; `next` для дорожки и сессии; зубастость.

### Фаза 2.2 — Карточка «Ответ» четырёх видов
- Партиал `_answer_card.html` выбирает вид по `answer_kind`:
  - **число**: `.ans` → `.nf-group` (одна рамка, подложка `--surface-2`), строка `.nf` на подпункт: метка «а)», текст подпункта (первое предложение подпункта, не длиннее 90 знаков, дальше «…»), поле `.num` (`inputmode="decimal"`), знак `.m`. Без подпунктов — одна строка `.nf--single` без метки. Под группой `.nf-kbd`: «Enter в поле — проверить этот пункт · кнопка — все заполненные». Ряд `.ans-row`: «Проверить» (выключена, пока ни одно поле не заполнено, сосед «заполните хотя бы одно поле»), справа тихие «Подсказка 1 из N» (только при подсказках) и «Показать решение» (только при решении или ответе). Скрипт: Enter → проверить один пункт; кнопка → все заполненные и незамороженные; верный пункт замораживается (`disabled`, `is-ok`, строка `is-ok`), неверный трясётся и остаётся, красная рамка снимается при первом вводе; после проверки фокус — в первое незамороженное поле; сообщения `.ans-msg--ok / --bad` («Верно! Все N пунктов сошлись — с первой попытки, идёт в уровень темы» / «со 2-й попытки, засчитано как решено»; «Частично. Верных пунктов k из N» / «Не сходится»); счётчик «попытка n» в шапке карточки. Склонения: «с первой», «со 2-й», «с 3-й» и далее.
  - **файл**: главное действие `.drop` «Загрузить решение — PDF или фото тетради», после вложения появляется «Проверить решение» → существующий поток (распознавание, разбор по шагам); ниже `.ans-or` «или ответ формулой» и `.str` со строкой + «Проверить» (сверяет ИИ, подпись про одну короткую проверку). Гость: вместо загрузки — `.need` «Проверка решения по файлу — нужен аккаунт. Число и тесты проверяются без него» + «Войти и вернуться сюда» (`?next=` на эту задачу); строка гостю тоже недоступна (та же плашка, одна на карточку).
  - **качественная**: `.sv-field` текст «Ваш ответ и обоснование» + «Фото или файл» + «Отправить на проверку» + лимит; гость — `.need`.
  - **тест** — как на этапе 7, плюс после верного — блок завершения.
  - Задача, у которой нет ни числа, ни разбора, ни вариантов и она не качественная: вид «файл», и в шапке карточки честно: «Эталонного решения у этой задачи нет — проверим по условию, уверенность модели будет не выше средней».
- **Блок завершения** `.ans-done` (непрозрачный, с рамкой) после «решено»: текст об уровне — только если он посчитан: «Уровень по теме: в работе → уверенно ещё через k верных первых попыток» (k считается из `TopicProgress` и порогов; если посчитать нельзя — фразы нет); кнопка «Дальше: n из N» при контексте дорожки/сессии, иначе «Следующая по теме» (ссылка на `next` с `session=topic:<id>`). У гостя — «С аккаунтом ответы копятся в уровень по теме» и «Войти».
- **Подсказки и решение — только по запросу**: никакой автоподсветки после ошибок. «Показать решение» до первого результата — мягкое подтверждение («Открыть решение до ответа? Тогда эта попытка не пойдёт в уровень темы» / «Открыть» / «Ещё подумаю»); открыл → `record(opened=True)`, поля и кнопки проверки замораживаются, статус «решение открыто»; после «решено» — без подтверждения. Ответ и решение — раздельно, как в первом редизайне.
- **Фон**: `.sol`, `.ans-done`, результаты `.chk` — непрозрачные поверхности (`--surface`); узор страницы сквозь них не виден.
- **Иконки** — только SVG (лампочка у подсказки, документ у вложения, галочка/крест в знаках пунктов); никаких эмодзи нигде в каталоге и на странице задачи — тест-сторож на диапазон эмодзи по шаблонам `catalog/` и `problems/`.
- Тесты: у задачи с тремя числовыми подпунктами рендерятся три `.nf`; у задачи с ответом-формулой — `.drop` и `.str`, без `.num`; у качественной — `textarea`; у теста — `.opt`; у гостя на «файле» — `.need` и нет `.drop`; после «решено» — `.ans-done`; после «opened» — поля `disabled`.

## Этап 3. Дорожки и задача дня

### Фаза 3.1 — Модели и сборка дорожек
- `Track` (`kind`: `topic` / `olympiad`; `topic` FK null; `training_set` FK null — на модель тренировочного набора из приложения олимпиад, посмотреть её имя; `title`; `slug`; `is_active`; `built_at`; `order_key` — по чему отсортировано: `stars` / `first_try` / `format`), `TrackItem` (`track`, `position`, `problem`, `stage`: `warmup` / `core` / `olymp`). Уникальность (track, problem). Миграция `problems`.
- Команда `build_tracks` (сухой прогон / `--apply` / снимок): для каждой видимой темы — пул задач с проверкой (тест, число, или разбор для файла); ступени: «Разогрев» — тесты, «Основа» — число, «Олимпиадный уровень» — файл с разбором; в ступень попадает 4–5 задач по ключу сложности: (1) звёзды, если есть; (2) доля верных первых попыток по всем ученикам, если по задаче не меньше 20 результатов; (3) иначе формат и длина условия (короче — раньше). Ступень существует при ≥ 4 задачах её формата; дорожка — при ≥ 2 ступенях. `order_key` дорожки — худший из использованных ключей (если хоть одна задача отсортирована по формату — `format`). Олимпиадные дорожки — по одной на активный тренировочный набор, позиции = порядок набора. Повторный прогон обновляет состав без дублей; снимок прежнего состава — в файл, путь в выводе.
- Прогресс по дорожке — не хранится: считается из `UserProblemStatus` по её задачам (решено / всего, первая нерешённая).
- Страница дорожки `/catalog/track/<slug>/`: название, ступени заголовками, строки 72 px со статусами, «Продолжить» → первая нерешённая с `?track=…&pos=…`; у гостя — «Начать».
- Тесты: тема с 5 тестами, 6 числовыми, 2 файловыми → две ступени, дорожка есть; тема с 3 тестами и 4 числовыми → одной ступени мало → дорожки нет; порядок внутри ступени по звёздам; повторный `--apply` не дублирует; `order_key` честный.

### Фаза 3.2 — Задача дня
- `DailyProblem` (`date` уникальна, `problem`, `rule` — текст, почему выбрана). Выбор — команда `pick_daily_problem` (сухой/`--apply`) с детерминированным правилом от даты: видимая задача вида «число» или «тест» с разбором, сложность 2–4 если известна, не бывшая задачей дня последние 365 дней, блок — по кругу (сегодня micro, завтра macro…), чтобы не подряд одна тема. Если на дату строки нет — первое обращение к каталогу за день создаёт её тем же правилом (атомарно, `get_or_create` с блокировкой). Нет кандидатов — задачи дня нет, карточка не рендерится.
- Статистика в карточке — только из данных дня: «решили сегодня N» = число пользователей и гостевых сессий с верным ответом на эту задачу за дату; «с первой попытки X %» — по `first_try_correct` среди результатов дня; показывать обе, только если N ≥ 1 (иначе строка отсутствует). Серия «N дней подряд» — число подряд идущих дат до сегодня, в каждую из которых пользователь решил задачу того дня; показывать при N ≥ 2. «Следующая — через k ч» — до полуночи по времени сервера.
- Партиал `_pod.html` — та же карточка «Ответ» в компактном виде (число → поле; тест → ссылка «решать тест» на страницу задачи, плитки в карточку не тащим); эндпоинт `GET /catalog/api/pod/` отдаёт HTML карточки для кнопки на других экранах.
- Тесты: правило выбора детерминировано; 365-дневный запрет; статистика на пустом дне отсутствует; серия считается верно на фикстуре трёх дней; карточка не рендерится без кандидатов.
