## 2. Ключ GLM в окружение сервера

Умный поиск зовёт модель, и без ключа он молча уходит на базовый порядок.

```bash
cd /srv/weconomics/app/deploy && sudo nano .env
```

Добавить строку `GLM_API_KEY=` со значением, которое лежит в локальном
`.env` под именем `GLM_API_KEY_PROD`. Проверить, что строка ровно одна:

```bash
grep -c "^GLM_API_KEY=" /srv/weconomics/app/deploy/.env
```

⚠️ Имя переменной на сервере — **`GLM_API_KEY`**, а не `GLM_API_KEY_PROD`:
именно его читает поставщик (`problems/ai/providers.py`). В локальном `.env`
боевой ключ лежит под именем с суффиксом, чтобы не путать его с ключом
экспериментов; на сервере путать не с чем.

Сам умный поиск включается отдельной строкой — **решение владельца**:

| переменная | значение | зачем |
|---|---|---|
| `SMART_SEARCH_RERANK` | `1` | включить сортировщик для ВСЕХ посетителей |
| `SMART_SEARCH_RERANK_LEGS` | `bm25` | пока не поднят контейнер `search` (см. §7) |
| `SEARCH_RERANK_DAILY_CAP_USD` | `0.5` | суточный потолок; умолчание и так 0,5 |

Без `SMART_SEARCH_RERANK=1` всё остальное просто не включится, и это
нормальное состояние для первой выкатки.

| четыре формата теста | `/catalog/?type=test` | под «Тест» четыре строки с числами |
| умный поиск | поиск из каталога | в ответе `X-Smart-Search: rerank` |
| поиск без входа | тот же в режиме инкогнито | тоже `rerank`, а не `off` |
| расход виден | админка → «Расходы на ИИ» | строки `search_rerank`, автор пуст |
| Econ Rush | `/game/` | все четыре режима отдают вопросы |
| картинки задач | задача с рисунком из новых | рисунок виден, а не пустое место |

Заголовок смотрится так:

```bash
curl -sI "https://weconomics.site/catalog/?q=монополия" | grep -i x-smart-search
```

Значения: `rerank` — сортировщик отработал; `fallback` — упал и ушёл на
базовый порядок (причина в логах контейнера); `off` — флаг выключен.

## 7. Развилка: плотная нога поиска — РЕШЕНИЕ ВЛАДЕЛЬЦА

Контейнера `search` на боевом сервере **нет и сегодня**. Это не поломка, а
нынешнее устройство: смысловой поиск выключен флагом
`SEMANTIC_SEARCH_ENABLED=0` ещё решением ADR 0012.

**Вариант 1 — оставить как есть (работает сразу, ничего не решать).**
Умный поиск собирает пул одной ногой bm25 и отдаёт его модели. Замер живым
прогоном 13.09.2026: пул 50 кандидатов, одна пачка, **$0,00134 за запрос**,
задержка 4,7–8,1 с. При потолке $0,50 в сутки это 370 запросов. Качество
сортировки именно на этом пути владелец глазами ещё НЕ принимал — это и
есть первая вещь на приёмку.

⚠️ Разовая плата, которую стоит знать: **первый** поисковый запрос после
перезапуска контейнера собирает bm25-индекс по всему видимому корпусу.
Локальный замер на 14 082 задачах — 24,9 с. На проде корпус будет меньше
(8 438), то есть быстрее, но первый запрос всё равно будет заметно
медленнее остальных. Дальше индекс живёт в памяти процесса.

**Вариант 2 — поднять контейнер `search`.** Тогда пул собирается двумя
ногами и дорастает до потолка 150, то есть трёх пачек: **около $0,004 за
запрос**, 125 запросов в сутки при том же потолке. Цена вопроса — память:
модель BGE-M3 занимает **2,12 ГБ** в процессе сервиса. Это ОДИН процесс, а
не девять воркеров (ради этого сервис и вынесен, ADR 0008), но 2,12 ГБ на
сервере надо иметь свободными. **Сколько их там сейчас — эта сессия не
мерила: на сервере выполнялось только чтение состояния.** Перед решением
стоит посмотреть `free -h` и `docker stats`.

Недоступный сервис больше не наказывает поиск задержкой: с 13.09.2026 в
клиенте стоит короткоживущий выключатель — первый отказ закрывает дверь на
30 секунд, и всё это время поиск уходит по словам мгновенно. Так что
вариант 1 безопасен, а не просто «пока сойдёт».
