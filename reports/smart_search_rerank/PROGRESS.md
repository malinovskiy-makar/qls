## Инструкция владельцу: как проверить локально

**1. `.env` теперь подхватывается сам.** `config/settings.py` читает
`.env` из корня проекта ДО остальных настроек (`_load_dotenv_if_present`),
если файл существует — `runserver` и любая команда `manage.py` видят
`GLM_API_KEY` без ручных танцев. Прод это не задевает: там `.env`-файла в
контейнере нет, переменные приходят через `docker compose` как раньше;
уже выставленная в оболочке переменная сильнее файла.

**2. Включить локально:**

```bash
SMART_SEARCH_RERANK=1 venv313/Scripts/python.exe manage.py runserver
```

(в PowerShell — `$env:SMART_SEARCH_RERANK=1` отдельной строкой перед
запуском). Видит только сотрудник (`is_staff=True`) при поиске в каталоге.

**3. Плотная нога (dense) требует Docker:**

```bash
docker compose -f docker-compose.dev.yml up -d search
```

⚠️ Но с текущей раскладкой (Django вне Docker, `search` без `ports:`
намеренно) этого одного шага НЕ ХВАТИТ — сервис останется недостижим с
хоста. Как именно вы обычно достаёте до него локально (другой compose,
override с портом, Django тоже в контейнере) — сессия не выяснила, спросите
или пришлите свою раскладку, и Фазу 4/5 можно домерить по dense+bm25.

**4. Отличить bm25-only от dense+bm25 по строке лога.** Каждая строка в
консоли и в `reports/smart_search_log.jsonl` содержит `pool_by_leg` —
словарь `{'dense': N, 'bm25': M}`. `dense: 0` — плотная нога не сработала
(сервис недоступен или выключена настройкой); `dense: >0` — сработала.
Пример строки:

```
умный поиск: запрос='...' пул={'dense': 0, 'bm25': 50} пачек=1 модель=5.05с
всего=7.77с стоимость=$0.0014 итог=rerank
```

Здесь `dense: 0` — прогон шёл без плотной ноги (Фаза 4 этой сессии).
Появление `dense: >0` в той же строке будет означать, что плотный поиск
заработал по-настоящему.
