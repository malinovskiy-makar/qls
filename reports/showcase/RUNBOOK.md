# Рунбук: демо-ученик для витрины на бою (`seed_showcase_student`)

> **Владелец документа:** Claude Code · **Дата:** 2026-09-21 · **Выполняет:** владелец.
> Claude Code на боевой сервер не ходит: ни ssh, ни scp, ни docker.
> Образец по форме — `docs/SERVER.md`, «Синхронизация банка на бою». Журнал и таблица «факт против цели» — `reports/showcase/JOURNAL.md`.

Команда заводит на бою пять демо-аккаунтов и историю ученика `demo` за 90 дней, чтобы экран
`/profile/stats/` был заполнен целиком: **`demo`** (ученик), **`demo-tutor`** (репетитор),
**`demo-2`, `demo-3`, `demo-4`** (одноклассники; без них таблица группы и матрица «ученики × темы»
читаются как поломка). Миграций нет. Пишет ТОЛЬКО под эти пять логинов; пересчёт геймификации
идёт по одному ученику (`--user-id`), никогда без ключа.

⚠️ Порядок: **код → бэкап → сухой прогон → запись → проверка экранов.**

## 0. Что нужно решить и подготовить до запуска

1. **Пароль.** Один на все пять аккаунтов, обязательный аргумент `--password` (значения по умолчанию нет,
   репозиторий публичный). Придумайте сильный и нигде в репозитории не записывайте: аккаунты живут на боевом
   сайте. Чтобы пароль не остался в истории оболочки, начните команду с пробела (при `HISTCONTROL=ignorespace`)
   или очистите историю после. Ниже он везде записан плейсхолдером `<ПАРОЛЬ>`.
2. **Код.** Мерж ветки в `main` и выкатка — только по вашему «да»: «Обновить сайт до свежего кода»
   (`docs/SERVER.md`: `git pull` → `docker compose build web` → `docker compose up -d web`). Миграций у сессии нет.
3. **Справочник достижений.** Без `seed_achievements` награды не выдаются вообще, а ни миграция, ни деплой его
   не вызывают. Проверьте, что он на бою заполнен (ожидается **29**):

   ```bash
   cd /srv/weconomics/app/deploy
   docker compose exec web python manage.py shell -c "from problems.models_gamification import Achievement; print(Achievement.objects.count())"
   ```

   Если меньше — команда заведёт справочник сама и **громко об этом предупредит**. Он общий для платформы:
   награды включатся и у настоящих учеников. Это решение за вами; если не хотите, заведите его отдельно и заранее.
4. **Свежая копия базы** (бэкап в 03:20 мог устареть):

   ```bash
   sudo /srv/weconomics/app/deploy/backup.sh
   ```

## 1. Сухой прогон (в базу ничего не пишется)

Всё считается по-настоящему внутри транзакции, которая откатывается: числа в таблице — те, что получатся при записи.

```bash
cd /srv/weconomics/app/deploy
docker compose exec web python manage.py seed_showcase_student --password '<ПАРОЛЬ>'
```

Что должно быть в выводе:

- строка `Банк: видимых задач с темой N, из них с реальной сложностью M, каноничных тем K` — на копии из
  `db.sqlite3` дома было **2146 / 279 / 19**. Если N меньше 1500, будет предупреждение «Банк тонкий»;
- таблица «Факт против цели» с отметками ✓/✗ и итог **«Все цели достигнуты.»**
  Строка про источники (`catalog/homework/exam`) без отметки: цель ≈45/40/15 недостижима вместе с «10–12 работ по
  5–8 задач» (см. Д1 в журнале), ожидается около **90/7/3**;
- время работы — секунды дома (SQLite), на PostgreSQL ожидайте до пары минут (даты достижений считаются
  пересчётами по префиксам истории, до ~40 проб на ученика).

Если какая-то строка с ✗, **не записывайте**: попробуйте другое зерно (`--seed 1`, `--seed 42`, …) и снова сухой
прогон. Зерно детерминировано: те же аргументы — те же числа.

Справочные значения, которые получились дома на 21.09.2026 (зерно по умолчанию): активных дней 62; решено верно
613; доля верных 78,3 %; сложных 59; уровень 18 (7208 XP); серия 18 / 36; тем mastered/confident 4/12; слабых тем 3;
достижений 23 из 29 (не получено 6); сдано работ 11, проверено 9; контрольных 2; игра 200 событий, 4 режима.

## 2. Запись

```bash
docker compose exec web python manage.py seed_showcase_student --password '<ПАРОЛЬ>' --apply
```

В выводе будет `группа «Демо · Олимпиадная экономика, 10 класс» (id N)` — запомните `N`. Идентификаторы можно
получить и позже:

```bash
docker compose exec web python manage.py shell -c "from problems.models import User, StudentGroup; print('ученик', User.objects.get(username='demo').pk, 'группа', StudentGroup.objects.get(name__startswith='Демо').pk)"
```

Идемпотентность: тот же `--apply` повторно даёт **ту же таблицу** и ничего не дублирует (содержимое демо-аккаунтов
пересобирается с нуля).

## 3. Проверка экранов (глазами)

Войдите на `https://weconomics.site` (или `.ai`) под `demo` и паролем из п. 0:

- `/profile/stats/` — 14 блоков заполнены: шапка (уровень, серия 12–25 дней, недельная цель 60–100 %), четыре карточки,
  карта тем (есть «мастер», «разобрался» и «стоит подтянуть»), сильные/слабые, радар из пяти разделов, карта
  сложности, активность по часам и дням недели, динамика уровня, «Где решаешь», достижения (получено ~23 из 29;
  есть неполученные), рекорды, «Стоит вернуться», «Что отмечает преподаватель», игра. Нигде нет текстов «Пока нет
  данных», «Ты ещё не играл», «Реши первую задачу», «нет ответов».

Войдите под `demo-tutor` (тот же пароль):

- `/teacher/groups/<N>/?tab=overview` — таблица из 4 учеников, матрица «ученики × темы», блок «Требуют внимания» с
  отставшим `demo-4` («нет активности 16 дней»);
- `/teacher/student/<id ученика>/progress/` — карточка без редиректа: «верно решённых задач … / …», «средняя
  сложность работ 5,9 из 10», история работ (12 домашек и 2 контрольные), заметка репетитора.

## 4. Перед показом (обязательно)

Серия «дней подряд» и недельная цель привязаны к дню запуска: серия жива, только если история доходит до сегодня
или вчера. **Повторите `--apply` в день показа, лучше утром** (минута работы, числа те же, даты сдвинутся к
сегодняшнему дню; кэш статистики демо-аккаунтов команда сбрасывает сама). Если показ не в день запуска — без
повтора карточка «дней подряд» может показать 0.

## 5. Откат (единственный путь)

```bash
docker compose exec web python manage.py seed_showcase_student --password '<ПАРОЛЬ>' --purge
```

Удаляет пять аккаунтов и **всё, что на них ссылается**: события, сводки, профили прогресса, достижения, рекорды,
владение темами, работы репетитора (со сдачами, проверками и попытками контрольных), оценки сложности, навыки,
заметку, группу. Пароль при `--purge` требуется формально (любое значение). Общие справочники (`Achievement`,
`MistakeTag`, `Skill`) не удаляются: они не ссылаются на логины и общие. Повторный `--purge` — «нечего удалять».
Крайний случай — восстановление из бэкапа п. 0 (`docs/SERVER.md`, «Как восстановиться»).

## 6. Что затрагивает на бою (решать вам)

- **Редкость наград у настоящих учеников.** Знаменатель «этого добились X % учеников» — число профилей с опытом > 0
  (`models_gamification.rarity_map`). Четыре демо-профиля попадут в него, а у демо-ученика ~23 награды, поэтому
  проценты у всех вырастут. Кэш `achv_rarity_map` (10 мин) команда сбрасывает.
- **Аналитика беты.** События команды — это `LearningEvent`; `analytics_export` читает другую модель (`Event`), и в
  экспорт события команды **не попадают**. Но когда кто-то заходит под `demo` и открывает страницы, его действия
  пишутся в `Event` как у обычного пользователя — при разборе беты исключайте логины `demo*`.
  У каждого события команды есть метка `payload['demo_showcase'] = true`.
- **Публичная таблица рекордов игры не затронута:** `GameResult` команда не создаёт (решение владельца). Блок «Игра»
  на экране статистики берёт данные из событий.
- **Справочники.** Метки ошибок и навыки, которых на бою нет, создаются (`get_or_create` по имени) и после
  `--purge` остаются.
- **Аккаунты публичны.** Логины `demo`, `demo-tutor`, `demo-2/3/4` предсказуемы: пароль обязан быть сильным
  (`lockdown_dev_accounts` гасит аккаунты с известными дев-паролями и логины `admin/teacher1/student1`; сильный пароль его не заденет, слабый — заденет).

## 7. Параметры

| Аргумент | Смысл |
|---|---|
| `--password` | обязательный; один пароль на все пять аккаунтов |
| `--apply` | записать; без него — сухой прогон с откатом |
| `--purge` | удалить всё демо и выйти |
| `--username` | логин витринного ученика (по умолчанию `demo`; остальные — `<логин>-tutor`, `<логин>-2/3/4`) |
| `--first-name` / `--last-name` | имя витринного ученика (по умолчанию «Демо» / «Ученик») |
| `--seed` | зерно случайности (фиксированное по умолчанию `20260921`) |
| `--days` | глубина истории (по умолчанию 90) |

## 8. Ограничения проверки

Команда проверена на локальной SQLite и тестами (`problems/tests/test_showcase_student.py`, 17 тестов); на PostgreSQL
17 не запускалась. Опора на общие свойства ORM: `bulk_create` возвращает pk (SQLite ≥ 3.35 и PostgreSQL),
`bulk_update` не вызывает `auto_now_add`, `savepoint` внутри `atomic`. Сухой прогон на бою — это и есть проверка:
он гоняет весь код в откатываемой транзакции. Если на PostgreSQL что-то упадёт, сухой прогон упадёт до записи.
