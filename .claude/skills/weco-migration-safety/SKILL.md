# Безопасность миграций

Ты проверяешь, что изменение схемы базы разворачивается с нуля, накатывается на
существующую базу и не оставляет мин на будущее.

## Когда запускаться

Любое из:
- изменён `models.py` или `models_*.py`;
- добавлен, изменён или перенесён файл в `*/migrations/`;
- миграции переносятся между ветками или сливаются ветки, где схема разошлась;
- готовится развёртывание на чистую базу.

## Запрещено

- **`migrate --fake`** — без явного письменного разрешения владельца. Он не
  чинит расхождение, а прячет его: состояние базы и состояние графа расходятся
  молча, и вскрывается это на чужой машине через месяц.
- **Удалять или склеивать существующие миграции.** Номер, который кто-то уже
  применил, занят навсегда.
- **`makemigrations`** в ветке, где часть файлов миграций отсутствует. Django не
  знает про существующие номера и сочинит свою миграцию под занятым — две разные
  миграции с одним номером не сводятся никогда.
- **`migrate` против продакшена.** Прод мигрирует своим `startCommand` при
  выкатке. Ручной прогон — только с явного разрешения владельца.
- Трогать боевую базу и боевой `.env`.

## Обязательная последовательность

1. **Граф целостен.** Нет двух миграций с одним номером в приложении, нет
   разрыва в цепочке зависимостей, у каждой ветки графа один листовой узел.
   ```bash
   manage.py showmigrations <app>
   ```
   Приложения, где номера идут не подряд, назвать явно.

2. **Модели и миграции сходятся.**
   ```bash
   manage.py makemigrations --check --dry-run
   ```
   Обязан сказать `No changes detected`. Любое предложение создать миграцию —
   красный флаг: значит либо забыли сгенерировать, либо в ветке нет части файлов.

3. **Развёртывание с нуля.** На **чистой** базе, не на рабочей.
   ```bash
   # временные настройки с отдельным файлом базы
   PYTHONPATH="<scratch>;$PWD" DJANGO_SETTINGS_MODULE=zero_settings \
     manage.py migrate --no-input
   ```
   Если проект едет на PostgreSQL — прогнать и на пустой PostgreSQL: часть
   ошибок (отставшие sequence, различия в ограничениях) на SQLite не
   воспроизводится в принципе.

4. **Путь обновления.** На **копии** существующей базы накатить новые миграции.
   Развёртывание с нуля и накат на существующую — разные пути, и ломаются они
   по-разному.

5. **Обратимость.** Проверить, что миграция откатывается (`migrate <app> <prev>`),
   либо явно назвать её необратимой и объяснить почему.

## Особые случаи

**Данные в миграции.** `RunPython` обязан иметь обратную функцию либо
`migrations.RunPython.noop` с комментарием, почему откат не нужен. Миграция
данных на 30 тысячах строк — это минуты простоя при выкатке; сказать об этом.

**Перенос миграций между ветками.** Файлы миграций неотделимы от моделей,
которые они описывают. Перенести одни файлы — получить миграции без моделей:
`makemigrations --check` тут же потребует обратных операций. Проверить, что
вместе с файлами едет код моделей.

**PostgreSQL sequence.** Заливка строк с явными id не двигает счётчик таблицы —
следующая вставка без id получает занятый номер. На SQLite не воспроизводится.
После массовой заливки — `sqlsequencereset`.

## Отчёт

По каждому пункту: **свидетельство** (команда и её вывод) → **находка** →
**серьёзность** → **конкретный файл или шаг**.

Пример: «`makemigrations --check` предложил создать `game/0007` → в ветке нет
файлов 0007–0012, они на `feat/econ-rush-figure` → блокирует развёртывание →
перенести файлы **вместе с моделями** или не трогать `game` в этой ветке».

Не писать «миграции в порядке» без вывода команд. Проверка без свидетельства —
это мнение, а не проверка.
