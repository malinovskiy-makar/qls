# CLAUDE.md — точка входа

Платформа задач по олимпиадной экономике. Владелец — преподаватель, не
программист: он ведёт проект и принимает решения, код пишет Claude Code.
Объяснять простыми словами, комментарии в коде — по-русски.

**Где что лежит (важно):**
- `CLAUDE.md` (этот файл) — ТОЛЬКО техника: стек, структура, модели, команды,
  движки, деплой, дизайн-токены, известные ловушки. Держим коротким.
- **Notion-штаб** — ВСЁ остальное: задачи, баги, идеи, решения, результаты,
  стратегия, дорожная карта.
  Главная: https://app.notion.com/p/39ab11c92bc181f7bbe1efa8a89e38a9
- `CLAUDE_ARCHIVE.md` — история завершённых сессий. Справка «как это было сделано».
- `STRATEGY.md`, `PRODUCT.md` — ЗАМОРОЖЕНЫ. Актуальные версии — в Notion.
- `DESIGN.md` (в корне) — **КАНОН дизайна** «Язык дизайна платформы ЭкЗадачи»,
  части 0–5. Спецификация для Claude Code: правило → значение → проверка →
  одна строка «почему». Содержание в CLAUDE.md НЕ дублируется — читать оттуда.
  ⚠️ Есть ещё отдельный, более старый и короткий `docs/DESIGN.md` («Графитовый
  блокнот», июнь 2026, английский) — самостоятельный документ с main, канону
  не переписан. Два файла по смежной теме не сведены — решение за владельцем.

**Этот файл короткий и таким остаётся.** Он говорит, что запрещено, как
запустить, где границы приложений и куда идти за подробностями. Всё остальное —
в профильных документах ниже.

## P0 — запрещено всегда

- **`git push --force`** и **`git rebase`** на общих ветках.
- **`migrate --fake`** без явного разрешения владельца.
- **Массовая правка `statement` / `answer` / `solution` моделью.** ИИ дописывает
  НОВЫЕ поля, существующие не трогает. Причина: свип Батча 2 испортил 233 поля в
  195 задачах — [ADR 0005](docs/adr/0005-ai-writes-new-fields-only.md).
- **Пуш в `main` без явного «да» владельца.** Пуш в `main` = выкатка на прод.
- **Две параллельные сессии Claude Code в одной папке** — только через
  `git worktree`.
- **Отправка полей профиля пользователя в модель.** Наружу уходит только текст
  задачи, текст решения и рубрика; список разрешённых полей — в `problems/ai/`.
- **Установка чужих skills пачкой.** Только собственный проверенный список.
- **Второй контейнер `web` НА БОЕВОЙ БАЗЕ.** `entrypoint` накатывает
  миграции при старте без блокировки: два процесса пойдут мигрировать
  одновременно и развалят схему. Масштабирование — только `GUNICORN_WORKERS`
  внутри одного контейнера. [docs/SERVER.md](docs/SERVER.md).
  ⚠️ `web-dev` площадки под запрет НЕ подпадает: у неё ДРУГАЯ база
  (`weconomics_dev`), и мигрирующий процесс у каждой базы ровно один.
- **`makemigrations` без явного имени приложения.** У `game` цепочка
  0001–0015 на `main` непрерывна (`feat/wecon-rush` влита 02.09); новые
  миграции `game` — с 0016. У `problems` номера 0050–0054 намеренно
  ДВОЙНЫЕ (две ветки, склеены `0054_merge_…` — решение Notion 05.09):
  автодетектор без имени приложения и без `showmigrations` перед ним
  сочинит миграцию под занятым номером.
  [game/CLAUDE.md](game/CLAUDE.md) · [ADR 0004](docs/adr/0004-game-migrations-split.md).

## Простота и хирургическая правка

- Не додумывать самому: неясно — зафиксировать предположение явно или
  спросить, не тащить молча дальше по логике «наверное, имелось в виду».
- Простота вместо избыточности: минимальный код, который решает задачу,
  без абстракций и параметров «на будущее», которые никто не просил.
- Точечная правка: менять только то, что нужно для задачи; не трогать
  соседний код и чужие комментарии без причины — даже если «заодно так
  лучше».
- Цель, а не рецепт: превращать задачу в проверяемый критерий («тест X
  зелёный»), не просто механически выполнять шаги промпта.

## Уровень усилия (`/effort`) — не High по умолчанию на всё

High/Max — для сложных архитектурных фаз и трудной отладки, как и
раньше. Medium или Low — для механических фаз: чекпоинт-коммит, прогон
уже написанных тестов, применение уже расписанного в промпте плана без
развилок. Thinking-токены считаются как output — снижение effort там,
где рассуждение и не требовалось, экономит именно их, без потери
качества на сложных фазах.

### Проверки перед сдачей работы

⚠️ **Перед сдачей сессии прогоняются ВСЕ ПЯТЬ джобов из `.github/workflows/ci.yml`,
поимённо, а не только `scripts/run_tests.py`.** 24.08 red-джоб «Безопасность»
прожил незамеченным четыре ночные сессии подряд: каждая докладывала «полный
прогон зелёный», проверив только джоб `tests` (пятую часть). «Полный прогон»
означает эти пять команд, и отчёт о сдаче обязан назвать статус каждой:

```bash
# 1. lint — стиль (ruff)
ruff check .

# 2. security — статический разбор и уязвимости зависимостей
bandit -r problems catalog teacher student game calc2 config olympiads vp -ll
pip-audit -r requirements/base.txt

# 3. migrations — схема с нуля (нужен пустой PostgreSQL 17, см. docker-compose.dev.yml)
python manage.py migrate --noinput --settings=config.settings_test_pg
python manage.py makemigrations --check --dry-run --settings=config.settings_test_pg

# 4. tests — полный набор на PostgreSQL (см. ниже про два шага)
python scripts/run_tests.py problems catalog teacher student calc2 game calendar_stub config olympiads vp legal \
  --settings=config.settings_test_pg --verbosity 2

# 5. deploy-check — боевые настройки глазами Django (переменные окружения — см. ci.yml, джоб deploy-check)
python manage.py check --deploy --fail-level WARNING
```

```bash
manage.py check                              # 0 ошибок
manage.py makemigrations --check --dry-run   # ничего не предлагает создать

venv313/Scripts/python.exe scripts/run_tests.py       # ПОЛНЫЙ ПРОГОН, два шага
```

**Прогон идёт в ДВА ШАГА, и запускать надо именно скрипт.** Шаг A — 5 352
теста в `--parallel auto`; шаг B — 8 тестов, помеченных `serial`,
последовательно. Скрипт нужен ради кода возврата: две команды подряд легко
написать так, что виден код только второй.

⚠️ **`scripts/run_tests.py ... | tail` съедает код возврата скрипта** — в
конвейере виден код `tail`, то есть всегда 0. 13.09 это выдало красный
прогон за зелёный; поймали только по строке «общий код возврата: 1» в самом
выводе. Писать в файл (`> лог 2>&1`) и читать код сразу после команды.

Числа замерены полным прогоном на PostgreSQL на ветке
`integration/sync-20260905` (2026-09-06, девять приложений вместе с
`olympiads`): шаг A — 5 352 теста (замер 08.09: 111,8 мин на SQLite, `skipped=14`), шаг B — 8 за
~4,5 мин (`skipped=4`: три `BitExactEncodingTests` требуют локально
скачанную модель BGE-M3, четвёртый — браузерная регрессия calc2, если
node-раннер не уложился в 180 с).

**Быстрый круг во время сессии — `scripts/run_tests.py --scope-from-git`**
(без аргумента — с последнего коммита): узит прогон до тестовых лейблов,
задетых изменениями, и печатает сводку вместо полного `verbosity=2`.
Механизм и границы — [docs/TESTING.md](docs/TESTING.md), раздел «Быстрый
круг сессии». Каденция (быстрый круг во время работы, ПОЛНЫЙ прогон один
раз перед сдачей) — решение от 21.08 в Notion, не меняется.

⚠️ **На 13.09 полный прогон на PostgreSQL красный в ТРЁХ модулях, и только
в них** (замер на `main` перед выкаткой корпуса: шаг A — 5 837 тестов за
30,7 мин, `skipped=1`; шаг B — 8 за 5,4 мин, `skipped=1`, код 0). Разбивка
падений: `test_embeddings_transfer` 10, `test_embedding_formula` 6,
`test_corpus_diagnostics` 2:
- `problems.tests.test_corpus_diagnostics`, `test_embedding_formula`,
  `test_embeddings_transfer` — **14 падений и 4 ошибки**. Причина одна:
  тесты жёстко зашиты на активную спецификацию отпечатка `v1`, а активна
  `v2_focus_repeat` (решение 09.09). Число совпало с прежним замером до
  единицы. Карточка в Notion «Надо».

Четвёрка падений от 08.09 БОЛЬШЕ НЕ КРАСНАЯ, и запись о ней снята:
`test_deploy_dump` и `test_deploy_dump_bank_only` зелёные (блокер заливки
корпуса снят коммитом `1ea306b` ещё 07.09), `test_pilot_enrich_v2` зелёный,
браузерные `calc2` и `test_design_canon` проходят — `playwright` установлен.

⚠️ **Метка `serial` ставится ТОЛЬКО с записанной причиной.** «Помечу, чтобы
проходило» — запрещено: метка не чинит тест, а прячет его от параллельности.
Падение из-за общего состояния между тестами — это баг теста, и чинится он
изоляцией в `setUp`. Метка законна, только когда тест делит внешний ресурс,
который нельзя разделить: порт, браузер, живой сервер, настоящий Redis.
Сегодня таких четыре класса, причина у каждого — комментарием в коде, список —
в [docs/TESTING.md](docs/TESTING.md).

⚠️ **Кэш на шаге A уходит в память процесса.** Django даёт каждому воркеру
свою базу, но Redis один на всех, а `cache.clear()` у Redis — это `FLUSHDB`.
Префиксом ключей не разделить (FLUSHDB чистит базу целиком), своей базой на
воркера тоже (баз 16, четыре заняты, а воркеров по числу ядер). Настоящий
Redis остаётся на шаге B.

⚠️ **`--keepdb` локально бесполезен:** SQLite по умолчанию в памяти,
сохранять нечего. Помогает только на PostgreSQL. После него следующий
прогон **без** `--keepdb` попросит удалить базу и в CI упадёт с `EOFError` —
лечится одним прогоном с `--noinput`.

Без `REDIS_URL` проверки Redis честно пропускаются. В CI переменная задана,
и там же стоит тест, который краснеет, если её забыли, — иначе проверки
пропускались бы вечно, а джоб оставался бы зелёным.

**Зелёный прогон на SQLite больше не считается доказательством** — прод живёт
на PostgreSQL. Подробности и найденные расхождения — [docs/TESTING.md](docs/TESTING.md).

Плюс визуальная проверка человеком того, что менялось на экране. «Тесты зелёные»
доказывает математику и разметку, а не то, что красиво.

## Боевой сервер — коротко

Живёт на `https://weconomics.site` и `https://weconomics.ai` (один сервер,
два имени; Selectel VDS, Москва). Подробности,
команды и ловушки — [docs/SERVER.md](docs/SERVER.md), здесь только главное:

- Клон репозитория — `/srv/weconomics/app`, доступ к GitHub **отдельным
  deploy key только на чтение**. Все команды `docker compose` — из
  `/srv/weconomics/app/deploy`, и только оттуда.
- Обновление: `git pull` → `docker compose build web` → `docker compose up -d web` →
  **`docker compose restart nginx`** (nginx помнит старый адрес web — иначе 502).
- **gunicorn — gthread, 4 воркера × 8 потоков** (ADR 0140): вопрос к ИИ не занимает
  сайт. Откат — `GUNICORN_WORKER_CLASS=sync` в `/srv/weconomics/.env`; при sync
  entrypoint ставит один поток (иначе gunicorn сам вернёт gthread).
- ⚠️ **Команды Django на бою — ВНУТРИ контейнера** (`docker compose exec web python
  manage.py …` из `/srv/weconomics/app/deploy`): на хосте нет ни окружения, ни
  `/srv/weconomics/.env` в переменных, и команда ушла бы не в ту базу или упала.
- **Откат к заглушке одной командой** — раздел «Откат» в `docs/SERVER.md`.
  Команда проверена дважды на живом сайте, а не написана по памяти.
- Бэкапы: ежедневно 03:20 МСК, 30 копий, восстановление проверено.
  Внешнего хранилища пока нет — копии у того же провайдера.
- Бот стены ходит в Telegram через обратный SSH-туннель, который открывает посредник за рубежом:
  `TELEGRAM_API_BASE=https://api.telegram.org:18443`, в `web` и `tgbot` `extra_hosts: api.telegram.org:host-gateway`
  (на хосте `172.17.0.1:18443` – сквозной TLS до Telegram). [deploy/tg_relay/README.md](deploy/tg_relay/README.md).
- **Вход для VPN** на той же машине tg-relay: 443/80 → боевой 8443/8080 с PROXY protocol, адрес — `WEB_RELAY_IP`
  в `.env`. [docs/SERVER.md](docs/SERVER.md), раздел «Вход для VPN (на tg-relay)».
- Смысловой поиск выключен флагом `SEMANTIC_SEARCH_ENABLED=0`:
  [ADR 0012](docs/adr/0012-semantic-search-flag-off-in-prod.md).
- В базе smoke-набор 505 задач, не весь корпус.

## Кэш и сессии: Redis

Переменная **`REDIS_URL`** (`redis://[:пароль@]хост:порт`, **без номера базы**).
Есть — кэш и сессии идут в Redis; нет — LocMemCache и предупреждение в stderr.
В **боевых** настройках её отсутствие роняет старт: тихий LocMemCache на
девяти воркерах — это девять независимых кэшей.

| База Redis | Что там живёт |
|---|---|
| 0 | кэш приложения (алиас `default`) |
| 1 | сессии (алиас `sessions`) |
| 2, 3 | Celery и WebSocket — зарезервировано |
| 7 | векторы поисковых запросов (алиас `search`, С4) |
| 13, 14, 15 | только прогоны тестов |

⚠️ **Кэш и сессии обязаны жить в разных базах:** `cache.clear()` у Redis —
это `FLUSHDB`, он вычищает базу целиком. Рядом с кэшем сессии умирали бы при
каждом сбросе. По той же причине у двух `LocMemCache` разные `LOCATION`.

⚠️ Движок сессий — **`cached_db`**, не чистый `cache`: у Redis на сервере
политика `allkeys-lru`, и чистый `cache` разлогинивал бы людей под нагрузкой.
Источник правды — база, Redis только ускоряет чтение.
Обоснование — [ADR 0011](docs/adr/0011-redis-cache-and-sessions.md).

Индекс поиска (`catalog/semantic.py`) сверяет версию через общий ключ
`semantic:index_version`, иначе `invalidate_index()` дошёл бы до одного
воркера из девяти.

## Ручное ревью и видимость каталога

Каталог показывает **только проверенное человеком** (ветка
`feat/human-review-gate`, влито 2026-08-20). Миграции **0040–0042**:
`Problem.human_review` (`approved` / `defect` / пусто), `Problem.hidden_pending_review`
(булево), категория `fixed_wrong`, `ReviewVerdict.quotes`.

**ЧЕТЫРЕ РАЗНЫХ механизма скрытия, не путать:** `status='hidden'` — убрано
руками; `needs_quality_review` — скрыто как ПЛОХОЕ (детекторы качества);
`hidden_pending_review` — скрыто, потому что человек ЕЩЁ НЕ СМОТРЕЛ (это не
оценка качества); `content_status` — скрыто, потому что ТЕКСТ битый и его
надо доработать ([ADR 0092](docs/adr/0092-content-status-separate-from-hidden.md),
заведено 03.09.2026). Счётчик каталога после применения шлюза:
**18 865 → 5 090** видимых.

⚠️ Общей функции «видимая задача» в проекте нет — четвёрка признаков
повторяется по месту в 16 запросах. Пятый признак заводить нельзя, пока
четыре не сведены в одну функцию. Подробности и числа чистки —
[docs/DATA.md](docs/DATA.md).

Правило старшинства: **брак сильнее идеального** — одобрить сломанное хуже,
чем задержать хорошее. Исключение — **`SUPERSEDES`**: повторное ревью (например,
после починки задачи) отменяет прежний вердикт, иначе починенная задача
осталась бы скрытой навсегда.

```bash
human_review_mark [--apply|--revert]     # approved/defect по вердиктам ReviewVerdict
pending_review_gate [--apply|--revert]   # скрыть непроверенное (обратимо)
content_cleanup [--apply --allow-delete] # состояние текста задачи (обратимо,
                                         # кроме удаления — см. выгрузку)
publication_holes_check                  # только читает — дыры в одобренных
defect_review_export                     # пакет разбора дефектов для ревьюера
import_review_verdicts <file>            # понимает форматы вердиктов v1–v3
```

⚠️ **Категории ревью** — `problems/review_categories.py`, единственная точка
правды (10 штук: `perfect`, семь дефектных, `disputed`, `trash`). Полная
история сессии (числа, ловушки Windows, волна починки АА) — `CLAUDE_ARCHIVE.md`.

## Протокол сессии

**В начале.** Прочитать этот файл. Прочитать в Notion базу «Задачи» (статусы
«В работе» и «Надо») и 5 последних записей в «Решения». Если Notion недоступен —
**сказать об этом вслух**, работать по блоку «Текущий фокус» и предупредить, что
данные могут быть устаревшими. Не молчать и не делать вид, что всё в порядке.

**В конце.**
1. Изменилась техника → правка **профильного файла в `docs/`**, не этого.
2. Приняли решение → ADR в `docs/adr/` + карточка в Notion «Решения»
   (что решили, почему, какие варианты отвергли).
3. Задача сделана → статус «Готово»; нужна визуальная приёмка → «На проверке».
4. Нашёлся баг → карточка в «Задачи», статус «Надо».
5. Что-то выкатили или посчитали → запись в «Результаты».
6. История сессии → `CLAUDE_ARCHIVE.md`.
7. Перегенерировать блок «Текущий фокус».
8. В отчёте показать **отдельным списком**, что записано в Notion.

**Работа с Notion.** Никогда ничего не удалять — только менять статусы и
добавлять. Перед созданием карточки — поиск по названию, дубли не плодить. Не
заводить новые базы и значения select без спроса. Чужие карточки не переписывать —
добавлять комментарий. Массовая запись (больше 5 карточек) — только после показа
списка владельцу.

**Блок «Текущий фокус»** генерируется между маркерами NOTION-SYNC: дата, ссылка
на штаб, «В работе» (все), «На проверке» (все), «Надо» (до 7), «Последние
решения» (3). Руками не правится — Notion истина.
