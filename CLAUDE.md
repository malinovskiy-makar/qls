# CLAUDE.md — рабочая память проекта (техническая)

Платформа задач по олимпиадной экономике (российской). Этот файл — **актуальный
рабочий контекст** для сессий Claude Code: стек, структура, модели, команды,
текущее состояние, рабочие памятки и ближайшие планы.

**Где что лежит (важно):**
- `CLAUDE.md` (этот файл) — ТОЛЬКО техника: стек, структура, модели, команды,
  движки, деплой, дизайн-токены, известные ловушки. Держим коротким.
- **Notion-штаб** — ВСЁ остальное: задачи, баги, идеи, решения, результаты,
  стратегия, дорожная карта.
  Главная: https://app.notion.com/p/39ab11c92bc181f7bbe1efa8a89e38a9
- `CLAUDE_ARCHIVE.md` — история завершённых сессий. Справка «как это было сделано».
- `STRATEGY.md`, `PRODUCT.md` — ЗАМОРОЖЕНЫ. Актуальные версии — в Notion.
- `DESIGN.md` — живой, техническая дизайн-система. В Notion лежит зеркало.

**Правило: одно и то же не пишем в двух местах.** Планы, статус, баги и
обоснования решений — только в Notion. Техника — только здесь.

Преподаватель (не программист) ведёт проект и принимает решения; код пишет Claude
Code. Объяснять простыми словами, комментарии в коде — по-русски.

## Стек

- Python **3.9** + Django 4.2 (LTS) + SQLite локально / **PostgreSQL на проде**.
- Проект: `config/`. Основное приложение: `problems/`. Локальная база — `db.sqlite3`.
- Кастомный пользователь `problems.User` с ролью (teacher / student / parent — план).
- Виртуальное окружение в `./venv/`. Все команды — через `./venv/bin/python manage.py …`.

⚠️ **Совместимость Python 3.9.** Синтаксис `int | None` (union через `|`) появился
только в 3.10 и даёт `TypeError` при импорте. Всегда использовать
`from typing import Optional` → `Optional[int]`. Никогда не писать `int | None`.

## Как запустить

```
./venv/bin/python manage.py runserver
```

⚠️ **Браузер для проверки У НАС ЕСТЬ.** В `node_modules` стоит **playwright**
(`package.json`), браузеры скачаны (`~/Library/Caches/ms-playwright/`, chromium).
Значит фронтенд можно проверять НЕ на глаз: поднять `runserver` на свободном порту,
прогнать сценарий скриптом (`node script.js` — запускать из корня проекта, иначе
`require('playwright')` не разрешится), снять скриншоты, прочитать консоль
браузера. Так на ветке `feat/econ-rush-lives-results` нашлись два бага, которых
не видели ни `check`, ни тесты. Это НЕ отменяет визуальную приёмку преподавателем —
вкус и «красиво ли» тесты не проверяют.
⚠️ `runserver --noreload` не перечитывает python-код: правишь `views.py` во время
прогона — перезапусти сервер, иначе браузер проверяет СТАРЫЙ бэкенд (шаблоны при
этом перечитываются на каждый запрос, и расхождение выглядит как «мистика»).
Сайт: http://127.0.0.1:8000/ → главная. Админка: `/admin/`.
Логины (тестовые): `admin/admin12345`, `teacher1/teacher12345`, `student1/student12345`.
Наполнить примерами: `./venv/bin/python manage.py seed_demo` (без дубликатов).

## Движки и команды (всё локально, без внешнего API)

**Эмбеддинги (семантика):**
- Модель **`BAAI/bge-m3`** (sentence-transformers, русский, CPU, ~1.4 ГБ). Имя
  вынесено в единую константу `EMBEDDING_MODEL_NAME` в `problems/embedding_config.py`
  — все команды и поиск обязаны импортировать оттуда.
  ✅ Полный пересчёт на BGE-M3 выполнен 2026-07-04: **31 472 вектора**, кэш похожих
  перелит (105 245 связей). Лог — `reports/recompute_2026-07/recompute.log`,
  замер «после» — `reports/bge_benchmark/after_bge_m3.txt`.
  ⚠️ На Mac с BGE-M3 обязательно `--device cpu`; на 8 ГБ RAM — `--encode-batch 8`.
- `build_embeddings` — строит эмбеддинги батчами. `--limit N` (первые N без
  эмбеддинга), `--reset` (пересчитать все).
- `night_embeddings --ids-file <файл>` — пересчёт по списку id (см. ловушку ниже).
- `find_similar --problem-id N --limit 10` — топ-N похожих по косинусу.
- `cache_similar` — заливает похожие в M2M `similar_problems` (прод работает по кэшу,
  без модели).

**Дедупликация:** `find_duplicates` — `--threshold 0.95` (по умолч.), `--reset`.
Заполняет `DuplicateCandidate`; разметка через админку (подтвердить/отклонить).

**Темы:** `auto_assign_topics` (kNN по эмбеддингам, порог 0.70), `apply_topic_mapping`
(21 каноническая тема).

**Шлюз качества:** `quality_gate --apply` / `--revert` (обратимый). Детекторы читаются
из `reports/quality_audit/gate_*.txt` и смежных. Прячет зафлагованные задачи из
публичной выдачи (`needs_quality_review`).

## Как строятся эмбеддинги

**Формула `problem_to_text`** (в `build_embeddings.py`), 7 блоков:
`title` + `statement[:500]` + подпункты `ProblemPart.statement` (≤500 символов
суммарно) + `«Темы: …»` (канонические, кроме технической «Тест») + `«Навыки: …»`
+ `ai_blurb[:400]` (суть из Батча 1) + `«Теги: …»` (только канонические из
`CANONICAL_TAG_NAMES`). Решение и ответ в отпечаток НЕ входят. Пустые блоки не
добавляются. Требует `prefetch_related('parts', 'topics', 'skills', 'tags')`.
Все 31 472 эмбеддинга в базе посчитаны именно этой формулой (пересчёт 2026-07-04).

⚠️ **Ловушка done-файла (ВАЖНО).** `night_embeddings` вычитает из очереди все id, уже
записанные в `reports/night_session/embeddings_done_ids.txt`. Если у задачи изменился
текст, но её id уже в done-файле — повторный запуск **молча пропустит её** (вывод
«осталось 0» обманчив). Флага `--force` нет. Правильный порядок:
1. Удалить нужные id из done-файла.
2. Запустить `night_embeddings --ids-file <файл>`.

```bash
# Удалить id из done-файла перед пересчётом:
python3 -c "
parts = set(open('ids_to_recompute.txt').read().split())
kept = [l for l in open('reports/night_session/embeddings_done_ids.txt') if l.strip() not in parts]
open('reports/night_session/embeddings_done_ids.txt', 'w').writelines(kept)
print('removed', len(parts))
"
```

После любого патча, меняющего `statement` или `parts`, обязательно пересчитать
эмбеддинги изменённых id (иначе поиск похожих хуже для разбитых задач).

## calc2 — собственный графический движок

Стратегия: свой движок на открытых библиотеках вместо переламывания Desmos.
Старый Desmos (`graphs/`, `/desmos/`) НЕ тронут.

**Стек:** D3.js v7 (рисование SVG, оси, перетаскивание) + Math.js 12.4.3 (разбор/
вычисление формул, численные методы). Без npm/сборки — всё в одном шаблоне через
`<script src>`. Приложение `calc2`, страница `/calc2/` (`Calc2View`, TemplateView,
`@login_required`), шаблон `calc2/templates/calc2/calc2.html`. **Моделей/миграций
НЕТ** (сохранение графиков — будущее).

**Принципы:**
- Кривые задаются как **P = f(Q)** (Math.js принимает Q и x). Только первая четверть
  (Q≥0, P≥0); оси/сетку рисуем сами через D3; кривые/заливки обрезаются `clipPath`.
- Вся экономика **численная**: равновесие D=S — сканирование сетки + **бисекция**;
  площади CS/PS — **метод трапеций** (∫), а не формула треугольника. Так нелинейные
  кривые работают без переписывания.

**Сцены/режимы:** равновесие, налог/субсидия, потолок/пол, монополия (с областями),
издержки фирмы, КПВ (одна и сумма двух стран), торговля (КТВ), рынок труда (с МРОТ),
неравенство. Редизайн «Окно сценариев + рабочее место Сцена».

**Живой пульт (ветка `feat/calc2-live-pult`, готова к слиянию):** панель
«Инструменты» свёрнута по умолчанию; ключевые регуляторы — в горизонтальной
ленте-пульте `#pult` у нижнего края графика. Перетаскиваемые панели (`makeDockable`),
реестровый перенос DOM-узлов (`syncPultRegulators` — `appendChild`, не clone, чтобы
сохранить listeners). Слайдер пульта и drag кривой используют один сеттер
`setCurveFreeTerm`. Слайдеры строятся только для линейных кривых (`c.linear !== null`).
Плавность осей — `animateRanges` (твин через requestAnimationFrame, ~0.45с),
дебаунс/тротл, уважается `prefers-reduced-motion`. Frosted-glass панели.

**Как проверять без браузера:** `manage.py check` (0 ошибок) + рендер `/calc2/` → 200.
JS-математика — node-харнесс: извлечь инлайн-скрипт, подгрузить с заглушками DOM/D3 и
настоящим Math.js, вызвать реальные функции (`findEquilibrium`/`integrate`/`recompute`)
на контрольных числах. Тесты математики — в `calc2/tests/calc2_math.mjs`.
**Визуальную проверку (перетаскивание, заливки, темы) всегда делает преподаватель
в браузере.** «Тесты зелёные» доказывают математику, НЕ внешний вид.

**Контрольные числа (эталон математики):** `100-Q`@30=70; равновесие D:100-Q,S:Q →
Q*=50,P*=50; нелинейное D:100-Q,S:Q²/100 → Q*≈61.80; CS=PS=1250; налог t=20 →
Q1=40,Pb=60,Ps=40,Tx=800,DWL=100; субсидия s=20 → Q1=60,расход −1200,DWL=100.

## Econ Rush — игра на скорость (`game`, `/game/`, ветки `feat/game-modes` → `feat/game-generators` → `feat/econ-rush-lives-results`)

Публичная (без логина) игра-таймер по тестовым вопросам — инструмент привлечения.
**Четыре режима** (как контроли времени в шахматах), параметры — `game/config.py::MODES`
(значения = предмет тюнинга):

| Режим | Ключ | Тип вопроса | Время | Верно | Жизни |
|---|---|---|---|---|---|
| Пуля | `bullet` | `boolean` — данетка Верно/Неверно | 60 с | +2 с | 3 |
| Блиц | `blitz` | `single` — один из вариантов | 120 с | +5 с | 3 |
| Рапид | `rapid` | `multi` — несколько из вариантов | 300 с | +15 с | 3 |
| Классика | `classic` | `numeric` — числовой ответ вводом | 600 с | +30 с | 3 |

⚠️ **Наказание — ЖИЗНЬ, а не время** (с ветки `feat/econ-rush-lives-results`).
`time_wrong = 0` и `time_skip = 0` у всех режимов: за ошибку минус жизнь и комбо
в ноль, время НЕ трогаем (одно наказание, не два); пропуск полностью бесплатный
(жизнь цела, комбо цело, время цело) — иначе угадать выгоднее, чем честно
пропустить. Третья ошибка завершает забег.

Очки одинаковые во всех режимах: 100×комбо-множитель (×2/×3/×4 на сериях 3/6/9).
Неверный ответ рвёт комбо; **скип комбо НЕ рвёт**. Рапид засчитывается только при
полном совпадении множества выбранных с правильным. Классика: точное равенство
значений через `fractions.Fraction` (`views.py::parse_exact_number` — целые,
десятичные с запятой/точкой, дроби a/b; 0,1 = 0.1 = 1/10 верно, 1/3 ≠ 0.33;
мусорный ввод = неверно, не 500).

⚠️ **Кто что считает (изменилось).** Раньше очки/комбо/время считал КЛИЕНТ, сервер
отдавал только дельту времени. Теперь **очки, комбо и жизни считает сервер** и
отдаёт готовыми числами — клиент их только рисует. Иначе серверный журнал и
`GameResult` разошлись бы с экраном (урок «Штриха» v1: две записи одного и того же
всегда разъезжаются). У клиента остался **только таймер** — сервер не тикает,
поэтому конец по времени (`reason: 'time'`) сообщает клиент, но перебить сервер
не может: закрытый по жизням забег остаётся `'lives'`.

**Состояние забега** (Django session, бэкенд `db` — `SESSION_ENGINE` не задан,
куки бы не вместили): `econ_rush` = `{mode, topic, seen, answered, lives, score,
streak, best_streak, ended, log, queue?, result_code?}`; `econ_rush_seen` =
`{режим: [id]}` между забегами; `econ_rush_last` = `{mode, log}` завершённого
забега (переживает старт нового — с него живёт работа над ошибками).

**Журнал и сводка.** `state['log']` — запись на каждый сыгранный вопрос
(`question_id, number, topics, difficulty, question_type, outcome, elapsed_ms,
running_score, running_combo, lives_after`); темы и сложность берутся из
`GameQuestion` (денормализованы) — сводке не нужно ходить в базу за вопросом,
которого может уже не быть. `build_summary(state)` — **чистая функция журнала**:
точность, разбивка по темам, группы сложности, макс. комбо, кривые счёта и комбо,
гистограмма времени, причина конца, жизни. Отдельных счётчиков не заводим —
разошлись бы с журналом. **Точность считается от ПОПЫТОК** (верные+неверные):
пропуск не ответ и точность не портит. `elapsed_ms` шлёт клиент (он знает момент
показа карточки) из единой точки `postAnswer`; мусор/отрицательные/огромные → 0.

**Работа над ошибками** (`GET api/session/start_mistakes/`): целевой забег из
`config.MISTAKES_RUN_SIZE` (10) вопросов по темам ошибок ПРЕДЫДУЩЕГО забега,
в пропорции по сырому числу ошибок, **методом наибольшего остатка**
(`allocate_quotas`; контроль: 2 ошибки в A и 1 в B → 7/3). Режим — тот же
(разбирать ошибки «Пули» вопросами «Классики» бессмысленно). Дальше это ОБЫЧНЫЙ
забег с курированным пулом (`state['queue']` + `_pick_from_queue`).
- Вопрос с двумя темами даёт ошибку ОБЕИМ: какая подвела — неизвестно, делить
  пополам = выдумка.
- ⚠️ Вопросы без тем в работу над ошибками не идут (целиться в «Без темы» нечем).
  Поэтому сводка отдаёт **`mistake_topics`** — ровно то, что соберёт сервер, тем
  же подсчётом; экран рисует полосу пропорции оттуда и НЕ фильтрует сам, иначе
  обещал бы разбор темы, которой не будет. В `topic_rows` «Без темы» при этом
  есть — это честная строка точности. Инвариант держится тестом.
- Недобор: сначала из других тем ошибок, потом из любых вопросов того же типа;
  меньше 10 в пуле — забег короче, это не ошибка.

**Экран результатов** — порядок блоков = порядок важности: чем кончилось (сердца +
«выбыл на вопросе N» / «время вышло») → метрики → **работа над ошибками**
(единственный акцентный блок) → точность по темам → свёрнутые графики → шеринг →
кнопки. Рисуется целиком из серверной сводки. Ошибок нет → зелёное «Чисто!»
с предложением режима сложнее.
- ⚠️ Экран красится РОВНО один раз (из колбэка `finish`): второй проход
  проиграл бы count-up счёта заново, а бейдж рекорда, уже записанного в
  localStorage, перестал бы быть рекордом сам себе. Рекорд считается в `endRun` —
  это событие, а не состояние.
- Сеть отвалилась — остаётся запасная сводка из счётчиков клиента (`localSummary`,
  поле `offline`): не второй расчёт, а те же числа, что прислал сервер. Разбивок
  и графиков в ней нет — их честно считает только сервер.

**Графики** (`Подробная статистика`, свёрнуты, строятся лениво при раскрытии):
динамика счёта + комбо ступенькой, гистограмма времени, кольцевая сложностей,
сравнение с прошлыми играми. ⚠️ **Библиотеки НЕТ, SVG рисуем руками** — не ради
размера: цвета идут через `var(--rush-*)`, поэтому переключатель темы сайта
перекрашивает графики сам; canvas-библиотека потребовала бы перерисовки на каждую
смену темы и держала бы цвета в JS в обход токенов. Янтарь в кольцевой — в своём
законном смысле (шкала сложности).

**localStorage:** `econ_rush_best_<режим>` (рекорд; старый общий ключ
`econrush_best` мигрирует в блиц) и **`econ_rush_history`** (последние 30 забегов
`{mode, score, accuracy, at}` — истории раньше не было вообще). График сравнения
показывает 12 последних забегов ТОГО ЖЕ режима (счёт «Пули» и «Классики»
несравним). Целевой забег в историю не пишем.

**Публичная страница результата** `/game/r/<код>/` (`GameResult`, миграция 0005):

  игрока). Смысл один — у ссылки, которой делятся, должно быть что показать.

  тексте `og:title`. Картинка превью **статичная одна на все результаты**:

  `files` НЕЛЬЗЯ класть `text`/`url`: системное окно «Поделиться» на десктопе

## Генераторы вопросов Econ Rush (`game/generators/`, ветка `feat/game-generators`)

Параметрические генераторы «архетипов»: сначала сэмплируется «красивый»
ответ (целое в ≥80%, иначе дробь со знаменателем ≤10 / десятичная с одним
знаком), параметры условия вычисляются обратным ходом — ответ верен по
построению, ИИ в математике нет. Стиль текстов — по памятке
`reports/generators/style_notes.md` (манера ВсОШ-региона, дословных
заимствований нет).

**Эталон качества (утверждён 2026-07-16, решение в Notion; пример —
монополия «Аквалайн»).** Переработанные архетипы обязаны держать планку:
сюжет солидным абзацем с мотивацией; **БИБЛИОТЕКА сюжетов** (у каждого свой
текст, а не один шаблон с подставленными словами); ровно ОДИН числовой
вопрос в Классике; полное решение с рассуждением «почему так», единицами и
смыслом; целочисленные/просто-дробные ответы; график у графических.
⚠️ **Единицы, товары и вид вмешательства берутся ИЗ СЮЖЕТА** (кофе меряют в
кг, паром продаёт поездки, «субсидия на газировку ради борьбы с ожирением» —
бессмыслица). Сюжет выбирается в `sample()` и кладётся в `params['story']`,
иначе движок выберет обёртку ПОСЛЕ единиц и они разъедутся.
**На эталоне 4 из 17:** `monopoly`, `equilibrium`, `tax_subsidy`, `ppf_single`
(список продублирован в `test_generators.py::ETALON_ARCHETYPES` и
`preview_generated.py::ETALON_KEYS`). Остальные 13 — прежние, банальные,
ждут переработки; держатся выключенным флагом. Планка проверяется тестами
`EtalonQualityTests` (длина сюжета, один вопрос с единицами, глубина решения,
точность ответа, разнообразие сюжетов, единицы из сюжета, валидность чертежа).

- **Движок** `game/generators/base.py`: `Archetype` (методы `sample(rng)`,
  `solve(params)`, `error_variants(params, solved, asked)`, `wrappers()`,
  `asked_values(params)`, `solution(...)`, `figure(...)` — необязательный);
  преобразование в 3 типа вопросов (numeric/single/boolean) — в движке один
  раз (`generate_question`/`generate_batch`). Дистракторы только вычисленные,
  уникальные, ≠ ответу, неотрицательные; <3 красивых → пересэмплирование.
  Всё точно на `Fraction`.
- ⚠️ **Сложность задаётся ЯВНО** — `Asked(difficulty=1..5)`, по экономической
  глубине вопроса. Без неё работает старая оценка по числу шагов решения
  (`_difficulty`), и это неверно для развёрнутых решений: подробный разбор
  «почему так» длиннее не потому, что задача труднее — все переработанные
  архетипы стали бы сложностью 5. **Многословность ≠ сложность.** Старое
  поведение оставлено фолбэком для непеределанных архетипов.
- **График — только к numeric** (его смотрят в разборе, где есть место; в
  карточке Блица/Пули он был бы лишним). Схема — `game/generators/_figure.py`:
  ДЕКЛАРАТИВНАЯ геометрия (линии/заливки/точки/засечки в координатах задачи,
  роли вместо цветов). Питон считает числа, браузер рисует SVG. Добавить
  график новому архетипу = вернуть геометрию из `figure()`, рисователь не
  трогается.
- **Реестр** `game/generators/registry.py` — 17 архетипов (Блок А:
  equilibrium, shift_equilibrium, tax_subsidy, price_control,
  elasticity_point, elasticity_arc, surplus; Блок Б: costs_tc, comp_firm,
  monopoly, perfect_price_discrimination; Блок В: ppf_single, ppf_joint,
  comparative_advantage; Блок Г: mpc_multiplier, labor_minwage, price_index).
  Недоделанный архетип в реестр не включать — это и есть исключение из боя.
- **Хранение:** миграция 0002 — у `GameQuestion` появились `is_generated`
  (индекс), `generator_key`, `gen_params` (JSON), `gen_solution`; FK
  `problem` → nullable (только для сгенерированных). Миграция **0006** —
  `figure` (JSON, nullable): параметры чертежа. `build_game_pool`

## Дизайн-токены и правила публичных страниц

Акцент сайта — **малиновый** (`#BE185D` светлая / `#FF4D94` тёмная). Токены — в
`templates/_tokens.html` (подключается ПЕРВЫМ в `<head>` каждой публичной базы:
`catalog/base.html`, `student/base.html`, `teacher/base.html`, login, calendar_stub).
`:root` (светлая) + `[data-theme="dark"]` + анти-мигание (скрипт ДО CSS ставит
`data-theme` по `localStorage['theme']`). Переключатель тем ☾/☀ — в `_nav.html`.

⚠️ `/calc2/` имеет СВОЙ изолированный мир токенов (`--curve-*`, `--cost-*`, свой
bootstrap темы) — не трогать его общими токенами. Единый ключ темы для всего сайта —
`localStorage['theme']` (calc2 тоже на него переведён).

**Правила (соблюдать на любой новой публичной странице):**
- Каждый цвет — через `var(--…)`. Хардкод hex ломает тёмную тему (исключение — цвета
  типов событий календаря и `rgba(0,0,0,…)` тени).
- **Сигналы священны:** амбер = звёзды сложности, зелёный = «решение ✓». Никогда не
  делать их акцентом. (`--green #1d7e45`, `--amber #b26b00` — затемнены под WCAG AA.)
- **Кнопки «Сцены»:** крупные действия (отправить/создать/сохранить/найти/скачать) —
  графитовые `var(--btn-bg)` + `var(--on-btn)`. Малиновый сплошной — ТОЛЬКО на
  мелочах/активном (логотип, активный nav, фильтр, ссылки, фокус-кольца, чипы).
  Акцент ≤ ~10% экрана.
- **Иерархия поверхностей:** страница — серая (`--bg`); карточки-контент — белые
  (`--surface`); `--surface-2` — только рецессивное (рельсы, инпуты). Карточка без
  явного `background` сольётся с фоном — задавать `var(--surface)`.

## Семантический поиск — проработка + Стадия 1 (АКТИВНАЯ ветка)

Фича: пользователь описывает задачу словами → система возвращает похожие задачи из
банка по смыслу. **Главный сдвиг в позиционировании:** это НЕ «найди ровно ту самую
задачу» (недостижимо и не нужно), а «**подбери 15–20 похожих**» для подборки/листка —
и в этом качестве уже работает. Фича названа «Подобрать похожие задачи».

**Путь:** ввод (текст + фильтры) → (опц.) HyDE → эмбеддинг локальной моделью →
косинусный поиск (грубый перебор numpy по ~31к векторов — векторная БД не нужна) →
жёсткие фильтры (тема/сложность/решение) ранжируют → карточки.

**Две стороны проблемы качества (диагностика из ручных тестов):**
- *Сторона запроса:* сухое описание ≠ форма олимпиадного условия. Лечится **HyDE**
  (дешёвая модель придумывает гипотетическое условие как «магнит»; доказано — подняло
  задачу с «не найдено» до 88%). Эффективен на «чистых» задачах, слабее на сюжетных.
- *Сторона задачи:* олимпиадные условия НАМЕРЕННО сюжетные (бабушка, ресторан) — это
  неустранимое свойство домена, не дефект данных. Сюжет забивает экономический смысл в
  отпечатке. Лечится **ИИ-резюме сути** (сухая строка «о чём задача», эмбеддить её) —
  это **главный рычаг**. Разовая трата ~$20–65 на корпус, сначала пилот 300 задач за <$1.

## Протокол сессии (обязательно)

### В начале каждой сессии
1. Прочитать этот файл.
2. Прочитать в Notion базу «Задачи»: всё со статусом «В работе» и «Надо».
3. Прочитать 5 последних записей в «Решения».
4. ЕСЛИ Notion недоступен — сказать об этом ВСЛУХ, работать по блоку «Текущий
   фокус», предупредить, что данные могут быть устаревшими (указать дату блока).
   Не молчать и не делать вид, что всё в порядке.

### В конце каждой сессии
1. Изменилась техника (новая команда, поле модели, ловушка) → правка CLAUDE.md.
2. Приняли решение → карточка в Notion «Решения»: что решили, почему,
   какие варианты отвергли.
3. Задача сделана → статус «Готово». ЕСЛИ нужна визуальная проверка владельцем →
   статус «На проверке».
4. Нашлась новая задача или баг → карточка в «Задачи», статус «Надо».
5. Что-то выкатили или посчитали → запись в «Результаты».
6. Перегенерировать блок «Текущий фокус».
7. В итоговом отчёте показать ОТДЕЛЬНЫМ СПИСКОМ, что записано в Notion.

### Правила работы с Notion
- НИКОГДА ничего не удалять. Только менять статусы и добавлять.
- Перед созданием карточки — поиск по названию. Не плодить дубли.
- Не заводить новые базы, разделы и варианты select без спроса владельца.
- Не переписывать чужие карточки — добавлять комментарий.
- Массовая запись (больше 5 карточек) — только после показа списка владельцу
  и его подтверждения.

### Как генерировать блок «Текущий фокус»
Между маркерами NOTION-SYNC:START и NOTION-SYNC:END:
- строка «Обновлено: ГГГГ-ММ-ДД»
- ссылка на штаб
- «В работе:» — все задачи со статусом «В работе» (название + ответственный)
- «На проверке:» — все со статусом «На проверке»
- «Надо (ближайшее):» — до 7 задач со статусом «Надо»
- «Последние решения:» — 3 последних из базы «Решения»
Блок только читается из Notion и никогда не правится руками. Notion — истина.
